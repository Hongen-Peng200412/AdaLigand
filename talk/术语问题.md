# Stage1 / BOX 审阅：术语与解释性问题

> 审阅对象是当前工作树中的 `文档/讨论/BOX-level数据契约.md`、`文档/规划文档/Stage1训练实现计划.md`、`文档/规划文档/Stage1训练与多阈值推理.md`，并交叉核对 Pocket Plus 当前代码、A–G 执行资料与 Codex 任务 `019f4a1b-80c2-7c73-afee-758a28335dbd` 的本地记录。本文只报告和建议，不回写正式规格。

## 结论

主计划已经有一张较好的术语表，但它主要覆盖多阈值/selector；最容易让实现者误解的恰好是三块：Pocket Plus 遗留模块、BOX 坐标语义，以及评价指标。这里有些不只是“缺少全称”，而是同名词在两套代码中代表不同数学量；这类问题应在开工前解决。

优先级含义：

- **P0**：不澄清就可能实现错、训练错或评测错。
- **P1**：会造成不同 agent 各自补全出不同实现。
- **P2**：主要影响冷读、自包含性和维护成本。

## P2：自包含性与书写问题

1. `Stage1训练实现计划.md` 应补一张缩写表，至少含 GT、IoU、BCE、CE、KL、PR-AUC、H2D、LRU、DDP、FLOPs、MAP。主计划已经在正文定义 DP（`:896-900`），所以 **DP 不是缺失定义问题**，无需重复误报。
2. `infered_box` 是历史冻结拼写，不是规范英文。BOX 契约 `:149-150` 已明确不接受别名；建议术语表再写一句“有意保留的 schema 字面值，代码不得自动纠正为 `inferred_box`”。
3. `shape_zyx`、`voxel_size_xyz`、`bbox_max_zyx` 的形状符号应在每份可独立执行的文档首次出现处声明 `D/H/W`、`X/Y/Z` 的对应关系，而不只写“不要混用”。
4. `target_available` 在实现计划 `:117` 恒为 True，却被描述成一个有语义的字段；更清楚的方式是 collator 对 targets 的整体存在性断言，不给恒真标量制造“可能为 False”的错觉。
5. `probability` 一词应区分窗口 sigmoid 概率、整图融合概率、P token probability、receptor binding probability 与 selector gate probability；run manifest 字段应使用完整前缀。
6. “同一个 Find checkpoint”应解释为**模型权重 hash + 影响 forward 的配置 hash**，不只是某个路径字符串；否则局部物化与全图推理可能同权重、不同 forward 配方。
7. “可选择”“合法”“有效”在组件、CLG、门控三个层面含义不同。建议固定 `node_selectable`（几何/体积合法）、`clg_oracle_positive`（GT oracle 非空）、`clg_gate_pass`（网络推理通过）。

## 建议新增的最小解释物

与其继续把解释散在段落里，建议正式修订时新增三张小表即可解决大部分问题：

1. **对象生命周期表**：component node → CLG candidate → selected proposal → Stage2 blob view。
2. **Pocket Plus 适配表**：旧模块/字段/损失 → Find 基线的保留、冻结、删除、重命名。
3. **指标契约表**：输入对象、匹配准则、阈值、聚合单位、空样本政策、输出字段名。

这三张表比再扩写散文更能防止不同 agent 对同一个词各自作出合理但互不兼容的解释。
