# unet_c1 A800 与 H100 吞吐差异定量诊断

## 文档状态

- 状态：已完成。
- 诊断对象：第二版 BOX 池 A800 运行 `pencounkdual-111/AdaLigand_Stage1/dvc1ubk4` 与第一版 BOX 池 H100 运行 `pencounkdual-111/AdaLigand_Stage1/3a323sl8`。
- 目标：解释训练首个验证点前、验证期间和验证后的吞吐差异，区分 GPU 计算、数据分布、DataLoader、共享存储和偶发运行状态的影响。
- 边界：本次只进行只读历史分析和独立 CPU 复放；不修改或暂停两个训练，不修改模型、数据、配置或正式脚本。
- 临时证据根：`/storage/penghongen/tmp/unet_c1_throughput_audit_20260806`。

本文把“直接观测”“受控复放”“推断”和“结论”分开记录。三个 CPU 对照均已完成，本文结论不依赖仍在运行的临时任务。

## 一、两个运行的可比性与已确认差异

两次运行都使用单卡、每卡批量 6、梯度累积 8、全局批量 48、20 个 DataLoader worker、512 MiB 每 worker 完整图缓存、学习率 `1e-4` 和 `warmup_ratio=0.005`。两个 Slurm 作业也都分配了 24 个 CPU：

| 运行 | GPU | 节点 | 节点 CPU/内存 | 作业分配 CPU | BOX 池 |
|---|---|---|---:|---:|---|
| `dvc1ubk4` | NVIDIA A800-SXM4-80GB | `gnode09` | 64 CPU、约 1 TiB | 24 | 第二版 `0 center + 5 bias + 5 context` |
| `3a323sl8` | NVIDIA H100 PCIe | `hnode02` | 96 CPU、约 2 TiB | 24 | 第一版 `1 center + 5 bias + 3 context` |

两个 validation 使用相同的 200 个 PDB，身份和顺序完全一致，但请求数不同：

- 第二版：32,810 个请求，即 16,405 个 bias 和 16,405 个 context。
- 第一版：29,529 个请求，即 3,281 个 center、16,405 个 bias 和 9,843 个 context。
- 第二版请求数是第一版的 1.111 倍。

源码与配置不是逐字节相同。当前已发现的非 BOX 池差异包括返回特征键、checkpoint/调度监控指标、标签排除字段和运行标签；后续用“当前代码读取旧数据”的受控复放单独检查代码与数据贡献。因此本文不采用“唯一差异就是 BOX 池”的未经验证假设。

事实来源：Slurm `sacct/scontrol`、两个运行的 `wandb-metadata.json`、冻结 `config.yaml`、两个 validation selection NPZ，以及临时证据中的 `analysis/release_source_diff.txt` 和 `analysis/validation_locality.json`。

## 二、W&B 时间线的直接观测

### 2.1 首个验证点之前

| 指标 | A800 `dvc1ubk4` | H100 `3a323sl8` |
|---|---:|---:|
| 首个 validation step | 1461 | 1315 |
| 验证前平均训练速度 | 273.784 step/h | 151.853 step/h |
| 验证前 GPU 利用率均值 | 96.049% | 41.616% |
| 验证前 GPU 利用率中位数 | 98.000% | 42.470% |
| 验证前活跃 CPU 核中位数 | 10 | 2 |

直接解释：A800 运行在首个验证点前不是靠更强的 GPU 算力胜出，而是该时间段的数据供应足以让 A800 长时间满载；旧 H100 运行只有约 42% 的 GPU 中位利用率，已经被输入供应限制。更快的 H100 在训练随机读取阶段反而更容易等待数据。

### 2.2 首次 validation

| 指标 | A800 `dvc1ubk4` | H100 `3a323sl8` |
|---|---:|---:|
| validation 到首个指标的时间 | 25,779.669 s（7.161 h） | 13,337.953 s（3.705 h） |
| 每个 validation 请求时间 | 0.786 s | 0.452 s |
| 每请求时间比 A800/H100 | 1.740 | 1.000 |
| validation GPU 利用率均值 | 92.642% | 89.570% |
| validation GPU 利用率中位数 | 98.870% | 90.470% |

validation 中两张 GPU 都被持续使用，输入不再是主要瓶颈。第二版请求数仅多 11.1%，但 validation 总时间多 93.3%；按请求归一后 A800 仍慢 74.0%。因此 validation 的反转主要是 H100 相对 A800 的实际模型前向计算优势，而不是 BOX 请求数本身。

### 2.3 A800 在首次 validation 后看似“极慢”

- 从 validation 指标落盘到下一条训练记录：1,842.722 s，即 30.71 分钟。
- validation 后观测平均速度：58.867 step/h。
- 排除至少 5 分钟的离散长间隔后：193.638 step/h。
- 三个 step 的时间间隔中位数：39.593 s，折算为约 272.778 step/h，与验证前 273.784 step/h 基本相同。
- 共发现 12 个至少 5 分钟的非 validation 长间隔，合计 25,185.766 s，即 6.996 小时；最长两次为 6,480.274 s 和 4,340.879 s。

所以 W&B 的“验证后极慢”不是每个训练 step 都永久变慢，而是正常 step 速度基本未变，但少数批次出现了数分钟到数小时的尾延迟，拉低了整段平均速度。

长间隔中的系统指标进一步排除了持续 GPU 计算：

- 多数长间隔 GPU 利用率中位数为 0%–0.5%。
- 活跃 CPU 核中位数通常为 0–1。
- 训练进程常驻内存稳定在约 11.8–12.1 GiB，没有持续增长。
- 首次 validation 指标到下一训练记录期间 GPU 利用率均值和中位数都为 0%。

这组事实不支持“validation 改变模型执行图”“A800 算子突然变慢”或“进程内存泄漏”，而符合训练主进程等待 DataLoader 或底层文件读取的状态。

事实来源：`job335495/timeline_stats.json`、`job335495/system_phase_analysis.json`、W&B 完整历史与系统指标。

## 三、训练请求的独立 CPU 复放

### 3.1 同一第二版数据的四个时间位置

每个窗口固定复放 240 个训练请求，单 worker、512 MiB 缓存；测试不运行模型前向。

| 第二版窗口 | 请求/s | 单请求中位数 | p95 | 最大值 | cache miss/hit |
|---|---:|---:|---:|---:|---:|
| baseline | 0.2681 | 3.413 s | 7.874 s | 15.813 s | 960/0 |
| validation 前 | 0.2543 | 3.618 s | 8.365 s | 13.743 s | 960/0 |
| validation 后 | 0.2713 | 3.355 s | 7.892 s | 16.313 s | 960/0 |
| 较晚位置 | 0.2689 | 3.605 s | 7.651 s | 12.221 s | 960/0 |

关键结果：第二版数据在 validation 后的独立复放没有变慢，四个位置的吞吐只在约 7% 范围内波动。validation 后 W&B 出现数小时停顿，不能由“后半段请求天然更重”解释。

单 worker baseline 中，读取实验密度累计 264.191 s，读取配体距离图累计 511.251 s，两者合计占 895.109 s 总时间的 86.6%。主要成本在完整图文件读取，不在 BOX 裁剪或 Python 控制流。

### 3.2 第一版数据对照

| 第一版窗口 | 请求/s | 单请求中位数 | p95 | 最大值 | cache miss/hit |
|---|---:|---:|---:|---:|---:|
| baseline | 0.3200 | 2.771 s | 6.963 s | 24.393 s | 956/4 |
| validation 后 | 0.2936 | 3.023 s | 7.017 s | 23.061 s | 960/0 |

同一诊断时段内，这两个第一版单 worker 窗口比第二版四个窗口快约 9%–26%。但稍后的 16-worker 首轮中，第一版反而只有 3.464 请求/s，低于第二版的 3.857 请求/s，说明共享存储的时间变化已经足以改变这种小幅排序。因此可以确认 BOX 池或源码存在一到两成量级的基础差异，却不能把某一轮的正负方向稳定归因给 BOX 池；无论取哪个方向，量级都不足以解释 A800 validation 后 6.996 小时的离散停顿。

### 3.3 多 worker 结果与顺序混杂

每项复放 960 个请求。结果按实际执行顺序列出：

| 对照 | 请求/s | batch 等待 p95 | batch 等待 p99 | cache hit/miss |
|---|---:|---:|---:|---:|
| 第二版，16 worker，512 MiB | 3.857 | 13.882 s | 31.151 s | 0/3840 |
| 第二版，8 worker，512 MiB | 3.829 | 11.913 s | 19.859 s | 0/3840 |
| 第二版，16 worker，4 GiB | 6.184 | 9.379 s | 15.030 s | 0/3840 |
| 第一版，旧代码，16 worker，512 MiB | 3.464 | 17.344 s | 32.086 s | 0/3840 |
| 第一版，当前代码兼容配置，16 worker，512 MiB | 2.691 | 22.209 s | 30.505 s | 0/3840 |

这些吞吐不能被当作严格的 worker/cache 因果排序。前三项连续读取完全相同的第二版窗口，后一次会受节点页缓存和 Lustre 客户端缓存预热影响；最后两项也连续读取完全相同的第一版窗口。4 GiB 项虽然最快，但应用层仍然 0 次命中，因此它的提速不能归因于 worker LRU。8 worker 与 16 worker 接近也受到相同的执行顺序混杂，不能据此直接把正式 worker 数减半。

能够不依赖顺序效应成立的事实是：

- 五项合计 19,200 次资产访问全部 miss；512 MiB 和 4 GiB 的 worker 私有 LRU 都没有复用任何资产。
- 第二版首个冷复放为 3.857 请求/s。当前训练 273.784 step/h、全局批量 48 对应约 3.650 请求/s，供给余量只有约 5.7%。
- 即使多数 batch 已被预取掩盖，冷复放的等待 p95 和 p99 仍为 13.9 秒和 31.2 秒，足以在训练中造成 GPU 空转。
- “当前代码+旧数据”需要临时删除旧配置中当前 Dataset 已不接受的 `excluded_pdb_ids` 字段；这是诊断配置兼容处理，不是正式训练改动。其吞吐同时受代码、兼容配置、执行顺序和存储时变状态影响，只用于证明“代码版本并非严格相同”，不单独归因。

因此当前管线在共享存储状态良好时可以喂满 A800，但余量很窄；任何文件读取长尾都会直接让 GPU 空转。若以后需要精确决定 worker 数，必须采用交叉顺序或冷数据窗口对照，不能复用本次顺序测试的原始吞吐排序。

事实来源：`job336466/*/result.json` 及各 worker JSONL。

## 四、请求局部性与缓存为何在 train/validation 中表现相反

### 4.1 训练请求

对第二版和第一版多个 480 请求窗口逐项检查：

- 相邻请求属于同一 PDB 的比例为 0%。
- 按 20 个 worker 的实际批次轮转近似重建后，同一 worker 的相邻请求属于同一 PDB 的比例也为 0%。
- 第二版四个窗口各自包含约 458–464 个不同 PDB。
- 9%–13% 请求引用的完整资产总文件大小超过 512 MiB，约 1%–2.3% 超过 1 GiB。

当前 LRU 是 worker 私有缓存。训练请求几乎没有短距离 PDB 复用，512 MiB 又小于不少单项完整图，因此缓存持续 miss 和淘汰是设计与请求顺序共同造成的必然结果。

### 4.2 validation 请求

| 局部性指标 | 第二版 | 第一版 |
|---|---:|---:|
| 相邻请求同 PDB | 98.784% | 97.971% |
| 按 20 worker 轮转后，同 worker 前一请求同 PDB | 87.843% | 85.566% |

validation 按 PDB 成组，天然适合缓存；训练近似随机打散，天然不适合当前 worker 私有小缓存。这解释了同一任务为何在 validation 中主要体现 GPU 计算差异，而在 training 中主要体现数据供应和共享存储波动。

## 五、存储格式的直接事实

- `/storage` 是 Lustre，共约 1.4 PiB，当前使用率 90%；22 个 OST 的使用率约为 88%–92%。
- 抽查的 1.3–1.6 GiB `exp.npz` 和约 780 MiB `ligand_dist.npz` 都只有 1 个 Lustre stripe，stripe size 为 1 MiB。
- 这些 NPZ 内的大数组使用 ZIP method 0，即不压缩；但 NumPy 从 `.npz` 取数组时仍不能像独立 `.npy` 那样使用 `mmap_mode` 只映射需要的 80³ BOX。当前 Dataset 会先读取完整数组，再裁剪 80³ 区域。
- 精确复查两个最长停顿附近的请求窗口，每个全局优化步对应的逻辑文件量约为 8.23–13.81 GiB，没有发现单个异常请求突然膨胀几个数量级。
- 对活跃 Job 336558 进行 60.4 分钟只读 Slurm 累计计数采样：`MaxDiskRead` 增加 13,497,113,162 字节，即 13.50 GB，平均约 3.72 MB/s；写入只增加约 0.34 MB。这里的 47.8 TB 是作业从启动至采样时的累计读取总量，不能误写成一小时读取量。

上述事实共同表明：训练每步需要从许多随机 PDB 的大 NPZ 中读取完整数组，且每个文件只落在单个 OST 上；多数时候 20 worker 的并发能够掩盖延迟，但共享 Lustre 的尾延迟会把某个 batch 的最慢请求放大成 GPU 空转。

事实来源：`analysis/storage_layout.txt`、`analysis/npz_zip_layout.json`、`analysis/live_sampler_summary.json` 和两个长间隔请求窗口的 metadata 结果。

## 六、当前根因判断

### 已有直接证据支持的结论

1. **validation 的 A800/H100 反转是 GPU 计算差异。** validation 的 PDB 局部性很高，两张 GPU 利用率都约 90% 或更高；按请求归一后 A800 用时为 H100 的 1.74 倍。
2. **H100 首个验证点前较慢是输入饥饿，不是 H100 算力较弱。** 旧 H100 验证前 GPU 中位利用率只有 42.47%，而 A800 为 98%。
3. **A800 validation 后的极慢平均速度由少数 I/O 长尾造成。** 典型三步间隔折算速度与验证前几乎相同；12 个长间隔累计占 6.996 小时，间隔内 GPU 和 CPU 基本空闲、进程内存稳定。
4. **第二版 BOX 池只造成次要基础吞吐差异。** 单 worker 复放显示第一版通常快约一到两成，但第二版 validation 后窗口本身并不比 validation 前或 baseline 慢。
5. **当前训练缓存基本无效。** 训练请求缺乏 PDB 局部性，16-worker 复放 3,840 次资产访问全部 miss；512 MiB 还装不下不少单项完整图。
6. **完整 validation 不会可重复地让训练 DataLoader 退化。** 无 validation 控制组、第二版完整 validation 对照和第一版完整 validation 对照的后置训练窗口分别比前置窗口快 2.9%、8.2% 和 7.0%；历史 A800 的 30.71 分钟恢复空档不是 validation 生命周期的固定成本。

### 阶段切换因果对照

三个对照都使用 16 个 worker、512 MiB 每 worker 缓存、批量 6，并在独立 CPU allocation 中只执行 Dataset/DataLoader，不执行模型前向：

| 对照 | 前置训练 2,400 请求 | validation | 后置训练 2,400 请求 | 后置相对变化 | 后置批次最大等待 |
|---|---:|---:|---:|---:|---:|
| 第二版，无 validation | 869.56 s | 不运行 | 844.42 s | -2.89% | 44.46 s |
| 第二版，完整 32,810 请求 validation | 935.66 s | 4,170.16 s | 859.29 s | -8.16% | 50.38 s |
| 第一版，完整 29,529 请求 validation | 875.70 s | 3,290.87 s | 814.49 s | -6.99% | 48.78 s |

第二版和第一版对照在 validation 后都于下一次约一分钟检查前进入后置训练；更严格地说，后置 400 个批次中的最大单批等待分别只有 50.38 秒和 48.78 秒，因此首批恢复等待不可能达到历史 A800 的 1,842.72 秒。无 validation 控制组的后半段同样没有自然退化。由此可以排除以下解释：

- validation 固定销毁或永久污染训练 DataLoader；
- validation 后的训练请求序列天然更重；
- 训练时间推移本身必然使第二版请求变慢。

两套完整 validation 对照在同一 `cnode01` 上并行，绝对 validation 吞吐会受到相互竞争，因此不能用这两次 CPU 总时长重新估计 A800/H100 算力差；GPU 算力结论仍来自两次 W&B 系统指标。该并行不影响各自前置/后置训练窗口的成对判断。

综合 W&B、Slurm 系统指标和 CPU 复放，历史 A800 在 validation 后的直接故障机制是训练数据供应出现离散长尾：长空档期间 GPU 为 0%、CPU 基本空闲、进程内存稳定。底层风险来源是共享 Lustre、单条带大 NPZ、完整数组物化和随机训练顺序的组合；但仅凭现有证据无法把某一次 30.71 分钟空档唯一归因到某个 OST、某个外部作业或某个节点瞬时事件。

## 七、可以从本次观察中学到的优化方向

下列建议按预期收益和科学侵入性排序；本次诊断不直接实施。

1. **先改存储表示，再讨论换 GPU。** 把完整大数组改为可局部读取的独立 `.npy` 加 memory map，或使用按空间分块的 Zarr，使 Dataset 在物化完整数组前只读 80³ 所需区域。这直接减少随机训练每步 8–14 GiB 的逻辑全图读取。
2. **train 与 validation 使用不同缓存策略。** train 当前短距离复用为零，小缓存只产生 miss/淘汰；validation 局部性约 86%–88%，适合更大缓存。不能把一个缓存值机械地同时用于两个阶段。
3. **为更快 GPU 提供更大的数据供给余量。** 16-worker 实测供给只比当前 A800 的顺畅训练需求高约 5.7%；H100 的计算更快，更容易被同一输入管线饿住。增加 worker/CPU 只能作为短期缓解，并需要同时观察 Lustre 尾延迟，不能盲目堆并发。
4. **考虑 PDB 局部的微分组采样。** 先打乱 PDB，再让每个 PDB 连续提供少量请求，可以让 worker 私有缓存真正命中；它会改变相邻样本相关性，必须作为明确的科学实验，而不是静默工程优化。
5. **对固定 validation 做节点侧暂存或专用大缓存。** validation 只有固定 200 个 PDB且高度成组，适合在不改变数值契约的前提下减少重复 Lustre 读取。
6. **未来生成大文件时考虑多 stripe。** 当前大文件都是单 stripe；对 1 GiB 级以上顺序读取文件可以在创建前设置 4 或 8 个 stripe。它不能替代局部读取格式，但可以降低单 OST 成为瓶颈的概率。
7. **监控要区分中位吞吐和尾延迟。** 只看 W&B 区间平均 step/h 会把“典型 step 正常、少数 batch 停数小时”误判为模型整体变慢。后续至少同时记录 batch 获取 p50/p95/p99、GPU 空转比例和累计读取增量。
