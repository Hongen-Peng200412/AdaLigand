# AdaLigand 的控制力、阅读边界与 AI 协作长期规划

> 文档性质：长期策略讨论稿  
> 适用范围：AdaLigand 当前阶段，以及今后由 AI agent 深度参与的研究代码项目  
> 核心目标：在不明显拖慢项目推进的前提下，让项目负责人重新掌握科学定义、关键数据流、实验行为和主要代码结构，而不是被迫阅读全部实现细节。

## 一、当前处境的判断

现在出现的矛盾是真实的，而且不是简单的“有没有认真读代码”。AI agent 已经能够一次完成过去需要拆成多个 `.py` 文件、多个函数和多轮人工指导的工作。实现速度提高以后，人类的理解速度并没有同比提高，于是出现了两类积累：

- **理解债务**：代码和系统已经向前推进，但项目负责人还不能用自己的语言解释其中的重要数据流、科学假设和失败方式。
- **所有权缺口**：项目负责人仍然决定研究目标，却越来越难判断一项具体实现究竟是必要机制、偶然写法，还是 AI 为潜在情况预先建立的复杂框架。

这不是能力退化，也不意味着必须重新回到“每个函数都由自己规划”的工作方式。真正发生的是：项目的执行能力已经超过了个人可用于阅读和审查的认知带宽。解决办法不是平均地阅读更多代码，而是把有限精力集中到最影响科学结果和后续决策的位置。

因此，本项目今后不以“项目负责人是否读过全部代码”衡量控制力，而以以下问题衡量：

1. 能否准确说出一个实验读取了哪一版正式数据和配置？
2. 能否解释一个真实样本从磁盘文件到模型损失的完整过程？
3. 能否指出哪些定义会改变科学结论，哪些只是实现细节？
4. 能否在训练异常或结果反常时定位到正确的系统层次？
5. 能否阻止未经确认的接口、标签、损失或运行身份变化进入正式实验？

只要这五点成立，即使部分底层数据处理代码被当作黑盒，项目负责人仍然拥有有效控制力。

## 二、把“控制力”分成五个层级

不同组件不需要相同的阅读深度。为避免“要么全部读完，要么完全交给 AI”的二元选择，后续统一使用以下五个层级。

| 层级 | 项目负责人需要掌握的内容 | 典型证据 |
|---|---|---|
| 科学目标控制 | 为什么需要该组件，它对应什么研究问题，允许改变什么、不允许改变什么 | 研究假设、标签定义、评价指标、实验对照 |
| 契约控制 | 输入、输出、字段、形状、单位、坐标系、缺失值、对齐关系和失败语义 | README、字段表、代表性产物、契约测试 |
| 实验控制 | 正式数据身份、模型配置、学习率、损失权重、随机种子、checkpoint 和运行目录 | resolved 配置、代码快照、W&B、作业记录 |
| 实现控制 | 关键调用链、主要状态转换、核心算法和重要边界条件 | 纵向代码阅读、学习注释、单元测试 |
| 运行控制 | 作业是否使用正确资源和版本，失败后如何恢复，哪些目录禁止覆盖 | Slurm 状态、日志、锁文件、完成标记 |

这里没有默认的“最高层级最好”。正确做法是根据组件的科学重要性、稳定程度和未来修改概率，选择最低但足够的控制层级。

## 三、AdaLigand 各组件采用不同控制模式

| 组件 | 建议控制深度 | 原因 | 当前策略 |
|---|---|---|---|
| A–G 数据处理管线 | 科学目标、契约、正式产物身份 | 已完成端到端整理；实现复杂但后续修改频率应较低 | 作为契约级黑盒，不安排系统性源码阅读 |
| Stage1 数据组织与训练 | 科学目标、契约、实验、关键实现 | 直接决定训练样本、五项监督和模型行为 | 按一次 BOX 的生命史纵向精读 |
| Stage1 Find 主干 | 实验和关键实现 | 正式训练已经运行，继续改动会破坏基线稳定性 | 冻结科学行为面，只补阅读材料和等价测试 |
| 推理管线 | 契约和关键实现 | 决定 checkpoint 如何变成正式预测产物，仍有结构调整空间 | 先读契约，再进行可读性优先的有限重构 |
| Selector | 科学目标、契约，必要时读关键算法 | 决定候选如何评分和选择，尚未正式全量生产 | 先掌握输入输出与选择语义，再决定源码深度 |
| 服务器脚手架和临时运维 | 运行控制和可审计性 | 对科学定义影响小，逐行阅读的收益低 | 要求边界明确、可追溯，不要求人工精读 |

这种分配承认一个现实：人的精力不能覆盖所有细节，但可以覆盖所有会改变研究结论的决策点。

## 四、A–G 数据管线：有边界的黑盒

### 4.1 接受只读一个 README

项目负责人只系统阅读：

`C:\Users\15919\Desktop\AdaLigand\Data_Preprocessing\Ori_Data\README.md`

需要掌握的内容限于：

- 正式服务器数据根目录是 `/storage/penghongen/AdaLigand/Ori_Data`。
- 根目录下有哪些正式文件和目录，每类文件由什么实体作为主键。
- 每个数组或结构化字段的形状、数据类型、单位和意义。
- XYZ 世界坐标、ZYX 数组索引、体素原点、体素大小和体素中心之间的关系。
- 同一个 `pdb_id` 或配体实例在不同文件之间如何对齐。
- 缺失值、无穷距离、跳过、已知失败和未知失败分别表示什么。
- 哪些文件是训练正式输入，哪些只是质量分析、诊断或运行记录。

已知服务器根路径由项目负责人自行掌握，因此不要求为了这一点修改 A–G README。README 仍然可以使用相对于 `--root` 的路径表达。

### 4.2 黑盒不等于放弃科学责任

“实现正确性交给 AI 交叉检验”可以成立，但应准确理解为：项目负责人不承担逐行证明实现正确的责任，AI agent 和自动化测试承担主要的实现核验工作。以下决定不能一并交出去：

- 什么是正确的科学定义。
- 哪些输入样本应当存在，哪些失败可以接受。
- 正式数据版本和发布位置是什么。
- 字段、单位、坐标和对齐契约是否符合训练需求。
- 一项差异是否会改变后续实验解释。

因此，A–G 黑盒需要以下支撑条件：

1. README 必须能够脱离代码说明完整产物契约。
2. 关键字段具有可执行的形状、类型、有限性和对齐检查。
3. 至少保留少量代表性 PDB 的人工可解释核验记录。
4. 正式产物不得被新运行原地覆盖。
5. 未解释异常不能被伪装成正常跳过。
6. 重要重构应由独立 agent 做产物等价或契约等价审计。

这里不要求项目负责人阅读哈希身份、确定性排序、并发写入和外部工具适配的全部代码。它们属于基础设施层；只有当这些机制导致数据身份无法解释、失败无法定位或正式产物无法复现时，才需要进入人工阅读范围。

### 4.3 对复杂机制的长期态度

现有管线中的哈希运行身份、平局裁决、嵌套抽象和相互引用，不应仅因为“已经写出来”就自动成为今后项目的默认范式。判断它们是否值得保留，应使用三个问题：

1. 它是否防止了一个已经出现过、后果明确的问题？
2. 它是否位于基础设施内部，而没有增加科学主线的理解成本？
3. 删除它以后，契约、正式产物身份或并发安全是否会实质下降？

三个问题都不能得到肯定答案时，新任务不应复制这种复杂度。已经稳定运行且有充分测试的旧代码也不必仅为审美立即重写；它可以继续作为黑盒存在。

## 五、Stage1：沿一个样本纵向阅读

Stage1 是当前最值得投入阅读精力的部分，因为它连接数据定义、样本选择、模型输入、辅助监督、损失、指标和正式训练。阅读目标不是熟悉每一个工具函数，而是能够亲自解释一个 BOX 如何从正式数据变成一次梯度更新。

### 5.1 阅读主线

```text
final_keep_list
    ↓
train / validation split
    ↓
box_pool/manifest.json 与 validation_selection.npz
    ↓
训练 epoch 请求或固定验证请求
    ↓
ResolvedStage1Crop
    ↓
Stage1Dataset 读取、裁剪和标签构造
    ↓
Stage1BatchCollator 组成批次
    ↓
模型主输出与四个辅助输出
    ↓
五项损失加权
    ↓
W&B 指标、checkpoint 与 CPC 阶段切换
```

Stage1 preparation 的当前正式根目录是：

`/storage/penghongen/AdaLigand/Ori_Data/stage1_preparation/adaligand_stage1_20260721T024000`

其中应优先辨认：

- `inventory/final_keep_list.jsonl`
- split 产物
- `box_pool/manifest.json`
- `box_pool/validation_selection.npz`
- `box_pool/verification.json`
- `box_pool/_COMPLETE`

这些文件属于 Stage1 样本组织，不要求塞进 A–G README 的产物字段表。

### 5.2 推荐阅读顺序

第一阶段只建立地图：

1. 阅读 `Pocket_Plus/src/datasets/README_STAGE1.md`。
2. 对照一份真实的 `final_keep_list.jsonl`、`manifest.json` 和 `validation_selection.npz`。
3. 画出一个 PDB、一个配体实例、一个 BOX 请求和一个批次之间的数量关系。

第二阶段跟踪样本选择：

1. 阅读 `stage1_split.py`，理解 PDB 级别的集合划分和不可跨集合约束。
2. 阅读 `stage1_box_pool.py`，理解 center、bias、context 三类合法 BOX 起点如何进入候选池。
3. 阅读 `stage1_requests.py`，理解训练每个 epoch 的选择、验证固定选择以及 `box_sample_fraction`。

第三阶段跟踪物化和批处理：

1. 阅读 `stage1_dataset.py` 的主要入口和一个样本的返回字段。
2. 重点跟踪密度、原子、配体区域、结合区域、配体距离和蛋白/核酸主链标签的来源。
3. 阅读 `stage1_collate.py`，理解定长体素数组和变长原子表怎样进入同一批次。

第四阶段跟踪模型和损失：

1. 先读短文件 `auxiliary_supervision.py`，确认辅助输出头和初始化约定。
2. 阅读 `stage1_voxel_backbone.py` 的输入输出契约。
3. 对 `stage1_model.py` 只先读 `forward()` 主链及其直接调用，不从文件第一行顺读到最后一行。
4. 阅读 `voxel_point_stage1_losses.py` 中五项损失的定义和体素平均方式。
5. 阅读 wrapper 中汇总总损失、记录指标、保存 checkpoint 的路径。

第五阶段才读训练入口：

1. 使用一个正在运行或已经完成的 resolved 配置作为索引。
2. 阅读 `src/train.py` 中配置实例化、随机种子、代码快照、恢复和 trainer 创建的主链。
3. 对照 W&B 中的真实字段确认配置最终生效值，而不是只看默认 YAML。

不要从 `src/train.py` 或两千余行的 `stage1_model.py` 开始。那样会先进入框架和分支细节，反而看不清样本的科学主线。

### 5.3 人类理解验收

完成阅读后，项目负责人应当能够不看代码回答以下问题：

1. 一次训练 BOX 最初来自哪份正式 PDB 和配体实例清单？
2. center、bias、context 的 1:5:3 是怎样形成的？
3. `box_sample_fraction=1.0` 时为什么每个 epoch 可以变化，小于 `1.0` 时为什么复用固定子集？
4. 模型读取的密度和原子特征分别来自什么文件？
5. 输入体素通道是怎样形成的，原子信息在哪里进入模型？
6. ligand area、ligand distance、binding area、protein mainchain 和 nucleic mainchain 五个 target 分别来自哪里？
7. 蛋白和核酸原子如何通过 Gaussian 方式进入体素标签？
8. 五项损失在哪里计算、怎样按体素平均、怎样加权形成总损失？
9. CPC1 和 CPC2 各自训练或冻结哪些参数？
10. validation 请求在哪里固定，为什么不同 epoch 可以比较？
11. checkpoint 怎样关联代码快照、resolved 配置和恢复入口？
12. 遇到异常曲线时，如何区分数据、标签、模型、损失和运行身份问题？

能回答这些问题，就已经拥有 Stage1 的有效控制力。没有必要记住缓存、日志格式、所有辅助函数或每个防御性检查。

## 六、冻结 Stage1 Find 的正确方式

“冻结”不等于再也不能改文件，而是冻结会改变科学行为或实验可比性的表面。

### 6.1 默认冻结

- train、validation 的样本选择语义。
- 五种 target 的定义和体素化方式。
- Find 主干、体素骨干和输出头架构。
- 五项损失的公式、平均口径和权重。
- 评价指标、BEST 判定和 checkpoint 恢复语义。
- 正式实验的学习率、warmup、批量、随机种子和 CPC 切换。

### 6.2 可以继续补充

- 不改变运行行为的中文注释和 Docstring。
- 面向个人学习的纵向阅读笔记。
- 对现有行为做断言的契约测试和回归测试。
- 从真实配置和 checkpoint 生成的只读检查工具。

### 6.3 必须单独审批

- 修复会改变输出数值或训练轨迹的缺陷。
- 改变样本选择、标签、损失或指标。
- 为统一结构而移动核心代码。
- 为推理或 Selector 的需求反向修改正在训练的模型代码。

这类修改需要复现证据、影响范围、兼容方案和新的实验身份。不能把它们夹在注释整理或可读性重构中。

## 七、推理与 Selector：允许为理解而重构

推理和 Selector 与正在运行的 Stage1 不同：它们已经有实现和部分测试，但尚未形成不可轻易改变的正式全量生产历史。因此，可以把“人类能否读懂”作为正式生产前的验收条件。

### 7.1 推理管线

先读契约，不先读实现。项目负责人至少要明确：

- 输入 checkpoint 如何定位自己的 `src_snapshot` 和 resolved 配置。
- 输入地图和候选实体怎样与 Stage1 训练时的坐标契约对齐。
- calibration、threshold、components 和 centered 各阶段接收什么、输出什么。
- 阈值、连通域和中心化规则分别改变什么结果。
- 完成标记、续跑和失败记录怎样避免半成品被当作正式产物。

完成契约阅读后，再判断是否重构。重构应优先做到：

- 一个正式入口能顺着少量明确函数走到最终产物。
- 科学转换和文件运行管理分层。
- checkpoint 快照加载集中在一个边界，不在多个模块重复判断。
- 每个阶段的输入输出使用明确的数据结构，减少隐式字典和跨层字段拼接。
- 用一个真实 checkpoint 和一个真实样本写出 golden path，即可复查的标准完整路径。

### 7.2 Selector

Selector 首先需要掌握：

- 一个候选由哪些字段唯一确定。
- 输入特征分别来自密度、Stage1、推理或其他来源的哪里。
- 可变体素通道如何接入 Selector，而不把某个 Stage1 通道数写死。
- score、calibration 和 final selection 的语义区别。
- 精确反链动态规划等关键算法解决的具体约束是什么。
- 输出怎样回指原始 PDB、候选和推理产物。

如果这些契约已经清晰，底层算法可以选择性阅读；如果入口、字段和阶段边界仍然难以说明，则应在正式生产前重构。

推理和 Selector 的重构必须在独立实现分支进行，并用既有 checkpoint、固定输入清单和产物等价检查保护 Stage1 已经形成的行为。不得为了结构整齐而修改旧训练快照。

## 八、这是否是 AI 时代的普遍问题

这是 AI 辅助开发中很常见的问题，但不是不可避免的结果。过去团队的瓶颈通常是实现速度；当 AI 能快速完成跨文件任务后，瓶颈转移为：

- 人类能否审查生成的行为，而不是只审查语法。
- 谁拥有跨模块契约和科学定义。
- 代码变化是否仍然能被团队成员解释。
- 测试是否验证了真正重要的不变量。
- 新代码的复杂度是否超过未来维护者的认知预算。

社区常见的应对方式包括：

- 使用小批次变更和明确的代码所有权。
- 用架构决策记录说明“为什么这样做”。
- 用数据契约、类型和可执行不变量约束模块边界。
- 保留一条短而完整的标准调用路径。
- 用固定样本、快照和 golden test 验证行为。
- 保存 resolved 配置、依赖和代码快照，使实验可以被追溯。
- 对高风险行为设置人工审批门，而不是平均审查所有代码。
- 让 AI 生成解释和审计报告，但让测试与正式产物提供证据。

这些实践的共同点不是“写更多文档”，而是让解释、测试、配置和真实产物互相对应。没有测试和真实入口支撑的文档很容易再次变成理解债务。

## 九、让 AI agent 写出更适合人类阅读的代码

以后给 AI agent 的任务，不只应规定功能，还应规定人类理解成本。下面的约束可以直接进入任务说明或审计清单。

### 9.1 开始实现前

- 写清项目负责人必须亲自理解的科学主线。
- 写清哪些模块可以作为黑盒，哪些必须适合纵向阅读。
- 指定本次变更允许触碰的行为面和禁止改变的契约。
- 如果没有第二个真实用例，不为“以后也许会需要”建立通用框架。
- 先给出最短可行调用链，再决定是否需要抽象。

### 9.2 实现过程中

- 一个公开入口对应一条主要调用链，避免多套等价入口。
- 科学计算、数据契约、文件读写和运行编排分层，但不为了分层而增加空转包装。
- 哈希、原子写入、锁、并发和复杂确定性规则集中在基础设施边界，不能散入 Dataset、模型和损失主线。
- 数据结构优先使用有名字、有字段说明的类型，减少靠约定传递的大型字典。
- 函数名称描述实际动作，避免 `process`、`handle`、`manager` 等无法说明职责的名称。
- 注释解释数组形状、坐标系、科学含义和不明显的原因，不复述代码表面动作。
- 配置最终必须产生一份完整 resolved 配置，默认值不能隐藏在多层回退中。

### 9.3 交付时

- 用一个真实或最小代表性样本解释从入口到输出的全过程。
- 列出新增的文件、公开入口、配置字段和正式产物。
- 区分科学行为变化、实现等价重构和运行管理变化。
- 报告没有覆盖的情况，不能用笼统的“测试通过”代替。
- 核心重构需要端点等价、产物等价或明确批准的差异证据。
- 独立审计 agent 优先检查契约漂移、隐藏默认值和过度工程，不要求它重新实现同一套代码。

### 9.4 复杂度预算

复杂度预算不是死板限制代码行数，而是在新增结构前要求给出收益。可以采用以下默认规则：

- 新增一层抽象必须减少真实重复、隔离一个确切变化源，或匹配已有稳定模式。
- 新增运行身份或确定性机制必须说明它防止的具体事故。
- 新增配置项必须有当前实验用途，不能只服务于假想未来。
- 一个核心行为如果需要跨越过多文件才能追踪，应补充统一入口或纵向说明。
- 为可读性进行的简化，不应牺牲正式产物身份、并发安全或实验可追溯性。

## 十、未来四周的建议节奏

这里的时间是优先级顺序，不是硬性截止日期。训练监控、故障处理和必要实验可以并行进行。

### 第一阶段：建立 Stage1 全景

- 阅读 Stage1 Dataset README 和正式 `final_keep_list`、split、box pool 产物。
- 画出一次 BOX 的生命史和五种 target 的来源。
- 不深入模型内部，不修改正式训练代码。

完成标准：能够解释样本从正式 PDB 清单到 Dataset 返回值的过程。

### 第二阶段：理解模型输入和五项损失

- 跟踪一个批次进入体素骨干、Find 主链和辅助输出头。
- 核对五项损失的公式、体素平均方式、权重和 W&B 字段。
- 对照真实 resolved 配置和 checkpoint，确认正在运行的实验行为。

完成标准：能够解释一次梯度更新及主要曲线的含义。

### 第三阶段：形成个人 Stage1 控制页

- 用自己的语言写一份短笔记，只保留主线、关键路径和十余个验收问题的答案。
- 不复制大段 README，不追求成为第二套正式文档。
- 把仍然无法解释的地方列为具体问题，再让 AI 做定点说明。

完成标准：遇到异常时能够先判断应检查数据、标签、模型、损失还是运行身份。

### 第四阶段：推理与 Selector

- 分别阅读两者的正式契约和一条标准运行路径。
- 在正式生产前完成有限的可读性审查。
- 只有确实阻碍阅读或维护的结构才重构，并使用固定输入做等价验证。

完成标准：能够从 checkpoint 追踪到推理产物，再追踪到 Selector 最终选择。

## 十一、不建议做的事情

- 不为了缓解失控感而从仓库第一行开始逐行阅读全部代码。
- 不把“读过多少行”当作掌握程度。
- 不在正式训练运行期间重构 Stage1 Find 的科学行为面。
- 不因为现有 A–G 实现复杂，就立即发起第二次大规模重写。
- 不要求每个运维脚本都达到核心科学代码相同的阅读标准。
- 不用更多抽象解决抽象过多带来的问题。
- 不让 README、测试、配置和真实产物各自描述不同版本的系统。
- 不把 AI 的交叉审计当作科学目标和验收标准的替代品。

## 十二、长期原则

这个项目不需要在“全部亲自掌握”和“全部交给 AI”之间选择。更可持续的状态是：

- 项目负责人掌握科学目标、正式契约、实验身份和关键数据流。
- AI agent 承担大量实现、机械核验、边界检查和独立审计。
- 核心训练链路保持稳定、可解释、可追溯。
- 非核心基础设施允许作为经过验证的黑盒存在。
- 尚未正式生产的组件可以为未来维护者的理解成本继续改进。
- 每次阅读都围绕真实样本、真实配置和真实产物，而不是脱离运行事实阅读抽象代码。

最终追求的不是“对每一行代码都有印象”，而是项目负责人可以在有限精力下持续作出正确决定：知道什么已经被证明，什么只是暂时可用；知道一项变化会影响哪里；知道何时应该信任自动化，何时必须亲自介入。这种选择性的、由证据支撑的理解，比无差别地阅读整个项目更接近真正的控制力。
