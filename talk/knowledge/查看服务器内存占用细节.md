# 面向 AI Agent 的服务器空间探测技术

> 本文讨论的是服务器文件系统的**磁盘/存储空间占用**，不是进程 RAM、显存或操作系统内存。
>
> 目标是在检测范围相同的前提下，提高探测速度、测量精度、结果可复核性，并降低对 Lustre 等共享文件系统的元数据压力。

## 1. 适用范围与目标

本文供 AI agent 执行以下任务时使用：

- 快速查看 `/home`、`/storage` 或指定目录的总体占用；
- 将几十 TiB 的 quota 逐级归因到具体目录、文件类型和数据类别；
- 对高对象数、深目录或元数据响应缓慢的目录进行可复核估算；
- 使用多个 AI agent 并行探测互不重叠的目录树；
- 诊断删除文件后 `lfs quota` 没有按预期下降的问题；
- 在目录持续被训练、预处理或同步任务修改时，给出带时间戳的动态快照。

最终报告必须区分：

1. **精确值**：完整递归扫描所得；
2. **抽样估计**：按明确样本方案推算所得；
3. **用户先验估计**：依赖用户提供的业务事实；
4. **quota 残差**：总 quota 减去已测类别后的差值；
5. **动态快照**：目录在审计期间发生变化，结果只对应某个时间窗口。

这些结果不能混写成同一种确定性。

## 2. AI Agent 的安全边界

### 2.1 默认只读

空间探测默认只允许运行读取类命令，例如：

- `lfs quota`、`lfs df`；
- `find`、`stat`、`du`、`ls`；
- Python `os.scandir()`、`os.stat()`；
- `lsof`、`findmnt`、`lfs getstripe`；
- `ps`、`pgrep`，用于区分用户任务与 agent 自己启动的查询。

不得修改服务器文件、训练任务、调度任务、锁文件或用户正在运行的命令。

### 2.2 不得擅自删除

本文后面的“删除空间诊断协议”由 AI agent 执行，但其中的删除步骤只有在用户明确授权了**精确目标路径和删除动作**时才能执行。

如果用户已经自行删除文件，agent 进入“事后诊断模式”，不能为了复现实验而再次创建或删除数据。

### 2.3 只清理 agent 自己的查询

用户在当前任务中声明的更严格边界优先于本节默认规则。如果用户禁止发送任何信号、暂停、终止或修改进程，那么即使某个查询可以确认由 agent 启动，也只允许识别、报告并等待其自然结束，不能执行 `kill`、信号型 `timeout`、优先级调整或其他进程控制操作。

如果工具窗口中断导致 `du`、Python 或 SSH 子进程失去回传通道，并且用户允许清理 agent 自己的查询，agent 才可以：

1. 用 `pgrep -a -u "$USER"`、`ps` 和完整命令行识别进程；
2. 只终止命令、PID 和路径均能证明由本次 agent 启动的查询；
3. 不终止带用户终端的命令，不根据“看起来像扫描”猜测进程归属；
4. 清理后再次检查是否存在残留。

### 2.4 获授权清理必须使用 fail-closed manifest

本节只适用于已经获得用户明确清理授权的独立执行 agent；只读审计 agent 不执行清理。清理前 manifest 至少记录绝对路径、device、inode、文件类型、逻辑字节、实际分配字节、`mtime_ns`、`nlink`、分类理由、快照时间和 manifest 版本。

apply 前逐项重新 `lstat`：路径缺失记为 `already_missing`，inode/device/类型或关键属性变化记为 `identity_drift`，二者都不能计作本次成功删除；路径变成软链接时不得跟随或删除。出现未预期 live-tree drift 时暂停整个 apply，先排查是否有旧的 SSH 超时后仍运行的扫描/清理者。旧 manifest 不得扩大范围或用模糊规则临时补选，同一 manifest 只能有一个执行者；apply 后生成独立 after manifest、结果分类和 quota 时间序列。

**inventory/audit 与 apply 必须是两个独立、显式启动的阶段。** 只读 inventory 程序不得在扫描结束后自动进入删除循环；长扫描即使已经运行数小时、SSH 已断开，也只能原子写出候选 bundle 后退出。apply 必须由新的执行者读取已验收 bundle，在重新核对锁、执行者唯一性与 live-tree identity 后显式启动。禁止“扫描完成便自动删除”的单进程串联设计，因为回传超时会让用户和其他 agent 误以为它已停止，并造成多个清理执行者冲突。

## 3. 两级探测：总体探查与细节探查

### 3.1 总体探查

总体探查回答：

- 当前 quota 是多少？
- 有多少文件对象？
- 一级目录有哪些？
- 哪些一级目录值得进入细节探查？
- 审计期间总量是否正在变化？

基准命令：

```bash
date -Is
for p in /storage "$HOME"; do
    lfs quota -u "$USER" "$p"
done
```

记录：

- `kbytes`；
- `files`；
- 时间戳；
- quota/limit 是否为 0；
- `/home/.../storage` 等路径是否只是指向 `/storage` 的软链接。

一级清单应避免跟随软链接和跨文件系统：

```bash
find "$root" -xdev -mindepth 1 -maxdepth 1 -print
```

### 3.2 细节探查

细节探查回答：

- 一个大目录的空间来自哪些子目录？
- 主要是什么文件类型？
- 是少数大文件还是大量小文件？
- 哪些值是精确的，哪些是估计的？
- 抽样误差和未归因残差有多大？

细节探查只展开总体探查发现的主要类别和无法解释的 quota 残差，不应无目的地遍历所有文件。

## 4. 标准工作流

> 本章描述的是决策框架，不是一组必须逐字执行的固定命令。AI agent 应根据目录结构、文件系统响应、活动任务、SSH 传输链和工具时间窗口选择等价的只读探针。可以改变探针顺序、拆分命令或改用更轻量的方法，但必须保留同一检测范围、统计口径、时间戳、证据链和安全边界，并在审计记录中说明偏离默认流程的原因。

### 4.1 第 0 步：建立本地审计记录

AI agent 在本地建立本次审计记录，不在服务器写临时文件。

推荐至少包含：

```text
audit_summary.md
audit_records.jsonl
audit_errors.md
```

也可以使用一个 `tmp.md`，但机器可读的 JSONL/CSV 更适合多 agent 汇总。

每条路径记录以下字段：

```text
path
filesystem
start_time
end_time
direct_files
direct_dirs
direct_symlinks
method                 # exact / sample / user_prior / residual
sample_strategy
sample_n
population_n
allocated_bytes
logical_bytes
confidence_interval
dynamic_change
status                 # pending / running / completed / timed_out
agent
observation_host       # master / login / compute / scheduler
transport_status       # local_parse / ssh / remote_shell / command / success
output_scope           # 输出对象、字段和数量边界
notes
```

记录的作用：

- 避免长任务中遗忘结果；
- 避免两个 agent 重复扫描同一路径；
- 保留超时目录的结构和已有样本；
- 允许在工具中断后继续，而不是从头重扫；
- 为最终 quota 对账提供机器可读数据。

#### 4.1.1 先验证命令传输链

远程探针可能依次经过 PowerShell、`.cmd` askpass wrapper、`ssh` 参数解析和远端 shell。管道、重定向、嵌套引号、`$()`、`&&`、正则中的 `|` 等字符可能在到达服务器前就被本地层解释。

正式诊断前先运行不含特殊字符的只读探针，例如 `date -Is` 或 `hostname`，确认连接与回传正常。复杂命令优先拆成多个独立 SSH 调用。遇到失败时必须区分：

- 本地 PowerShell 或 `.cmd` 解析失败；
- SSH 连接或认证失败；
- 远端 shell 解析失败；
- 远端命令自身失败；
- 命令成功但输出被本地截断。

本地出现“命令无法识别”不等于服务器拒绝或远端执行失败。审计记录应说明失败发生在哪一层，避免反复运行同一个有问题的探针。对于 `.cmd` wrapper，还应单独验证多行命令是否真的逐行传到远端；本次实践中，多行参数只执行了第一行，因此改为原子化单调用。

#### 4.1.2 使用原子探针并限制诊断输出

一个远程调用尽量只回答一个问题。例如 quota、进程列表、open-deleted、Slurm 作业和 OST 分布分别查询，不把它们塞进一条长命令。

优先通过命令自身的选择参数减少输出：`ps`、`pidstat` 只指定目标 PID 和必要字段；`squeue`、`scontrol` 只查询当前用户或目标 job；quota 快照保留原始表格，但不夹带无关目录遍历。不得为了“保险”无边界地输出全部进程、全部文件描述符或全部路径。若 wrapper 对管道或引号不可靠，应拆分探针，不能用更复杂的远端管道补救。

### 4.2 第 1 步：获取前置 quota 快照

开始任何目录扫描前记录：

```bash
date -Is
lfs quota -u "$USER" /storage
lfs quota -u "$USER" "$HOME"
```

总体审计结束后再记录一次相同快照。

如果前后 quota 或对象数变化显著，报告必须写明“目录处于动态变化中”，不能把不同时间取得的目录值当作同一个原子快照直接相加。

建议判断规则：

- 总量变化小于目标精度：可以作为近似静态快照；
- 总量变化大于目标精度：保留开始/结束两个快照；
- 持续快速变化：报告变化速率和时间窗口，不承诺长期稳定的“当前值”。

### 4.3 第 2 步：先探查目录结构

在运行完整 `du` 前，先了解目录的直接结构。

不建议默认使用：

```bash
ls -1 | wc -l
```

原因：可能漏掉隐藏文件、触发排序、不能区分文件/目录/软链接，并可能在 Lustre 上制造不必要的元数据负载。

推荐。这里只输出计数符号，避免把所有路径传回客户端：

```bash
find "$path" -xdev -mindepth 1 -maxdepth 1 -type f -printf . | wc -c
find "$path" -xdev -mindepth 1 -maxdepth 1 -type d -printf . | wc -c
find "$path" -xdev -mindepth 1 -maxdepth 1 -type l -printf . | wc -c
find "$path" -xdev -mindepth 1 -maxdepth 1 -print | head -n 50
```

建议给单层结构探查设置约 60 秒的初始预算。若命令因超时只返回部分计数，必须标记为“部分结果”，不能当作完整对象数。

当需要一次性分类且服务器有 Python 时，优先使用 `os.scandir()`。它通常比 `ls -l` 或对所有对象执行完整 `stat` 更轻量。

结构探查关注：

- 根层是平铺文件还是子目录；
- 子目录是否按 PDB ID、EMDB ID、年份、批次或模型名组织；
- 文件扩展名是否单一；
- 是否存在 `_BOX`、`npz`、`map`、`checkpoint` 等明显类别；
- 是否存在隐藏目录、软链接或挂载点；
- 目录是否正在增加文件或子目录。

#### 自适应递归，而不是强制递归到底

可以继续探查子目录，直到出现以下任一停止条件：

- 当前层已经是平铺文件集；
- 子目录高度同构，例如均以 PDB/EMDB ID 命名；
- 当前层扇出极大，全面展开会明显增加元数据负载；
- 已经能按业务类别解释占用；
- 结构探查自身超过时间预算。

对于高度同构目录，应抽取不同编号段和异常目录作为代表，而不是机械递归全部目录。

### 4.4 第 3 步：做小规模测速和方差预估

在决定精确扫描还是抽样前，先读取 32～128 个代表对象，估计：

- 单次 `stat` 或单目录 `du` 的耗时；
- 文件实际分配空间的均值、中位数、标准差、最小值和最大值；
- 是否存在长尾或极端值；
- 按当前速度完成全量扫描大约需要多久。

不能只依据“文件数少”判断是否适合精确扫描。Lustre 冷元数据可能导致数千个小文件比数百 GiB 的顺序大文件扫描更慢。

### 4.5 第 4 步：选择精确扫描或估算

快速决策表：

| 试探结果 | 推荐方法 |
|---|---|
| 预测全量可在可接受时间内完成 | 精确 `du -x` |
| 平铺文件、大小方差较低 | 系统抽样或随机抽样 |
| PDB/EMDB ID 等高度同构目录 | 按编号段分层，抽取代表目录完整递归 |
| 存在明显极端值或长尾 | 普通层抽样，异常层单独精确测量 |
| 目录持续增长或删除 | 两次结构快照，报告时间窗口 |
| 用户明确告知文件等大小 | 跨类别验证后使用“数量 × 单文件块大小” |

#### 4.5.1 适合精确扫描

满足以下条件之一时优先精确扫描：

- 对象数较少；
- 试探结果表明全量扫描可在可接受时间内完成；
- 目录是最终报告中的主要占用类别，需要更高精度；
- 抽样显示方差或长尾很大，而总体对象数仍可承受；
- 需要验证 quota 残差。

推荐命令：

```bash
ionice -c 3 nice -n 19 du -skx -- "$path"
```

需要一级拆分时：

```bash
ionice -c 3 nice -n 19 du -x -B1 --max-depth=1 -- "$path"
```

其中：

- `-x`：不跨文件系统；
- `nice -n 19`：降低 CPU 调度优先级；
- `ionice -c 3`：尽量降低 I/O 干扰；
- `--`：防止路径被解释为选项。

#### 4.5.2 适合抽样估计

满足以下情况时使用抽样：

- 全量扫描预测需要数小时；
- 目录包含数万至数百万对象；
- 元数据响应存在明显长尾；
- 目录是高度同构的 PDB/EMDB ID 集；
- 用户允许估计，且最终会明确报告误差。

抽样默认测量实际分配空间：

```text
allocated_bytes = st_blocks × 512
```

除非用户明确询问逻辑大小，否则不能只用 `st_size`，因为稀疏文件的逻辑大小可能远大于实际占用。

#### 4.5.3 分层抽样优于简单抽样

对于 PDB/EMDB ID 目录，推荐按以下类别分层：

- ID 首字符或编号段；
- 数据版本；
- 文件扩展名；
- 子目录类型；
- 快速响应与慢响应元数据组；
- 普通值与异常大值。

每层分别计算：

```text
该层估算空间 = 该层对象数 × 该层样本平均实际分配空间
```

总体估算：

```text
总体空间 = 所有层估算空间之和
```

报告样本数、总体数、均值、中位数、范围和近似置信区间。若样本不是随机样本，应注明系统抽样、等距抽样或业务分层可能带来的系统偏差。

#### 4.5.4 极端值处理

如果样本中出现少数远大于中位数的目录：

1. 不删除这些异常值；
2. 将异常目录单独列为一层；
3. 尽量精确扫描异常层；
4. 对普通层重新估算；
5. 同时报告均值和中位数，不能只报告中位数。

#### 4.5.5 “等大小文件 × 数量”规则

该方法**只有在用户主动提供“这些文件大小相同”这一业务先验时才能启用**。

即使用户已经确认，agent 仍应：

- 从名称首部、中部、尾部抽样；
- 跨不同业务类别抽样；
- 检查 `st_blocks`，而不只是 `st_size`；
- 验证样本是否全部一致；
- 报告为“基于用户先验并经抽样验证的估算”；
- 说明是否假设不存在跨文件硬链接。

不得仅因若干样本大小相同就自行推断全目录文件等大。

### 4.6 第 5 步：动态目录的处理

训练输出、预处理缓存和流水线 scratch 可能在审计过程中持续变化。

AI agent 应至少记录两次结构快照：

```text
开始：文件数、目录数、quota、时间
结束：文件数、目录数、quota、时间
```

如果目录对象数发生变化：

- 将结果标为“时间窗口快照”；
- 样本总体数使用相应时点的计数；
- 不把开始时的对象数和结束时的平均大小无说明地相乘；
- 必要时给出上下界或变化速率；
- 不为了获得静态结果而暂停或修改用户任务。

当目标目录正在被大量递归 `rm` 修改时，应避免同时对同一目录树运行完整递归 `du`、`find` 或逐文件 `stat`。只读扫描通常不会破坏文件，但会与删除任务竞争 Lustre 元数据服务，使双方变慢，并产生非原子、途中对象消失的结果。

此时优先使用 quota 时间序列、`lfs quota -v`、浅层结构、目标进程状态和小样本。必须扫描时，应避开正在删除的具体分支，或把结果明确标为“删除期间动态快照”。不得为了获得静态快照暂停或影响删除任务。即使对另一个活跃流水线的 scratch 只查两层，如果响应已经超过工具窗口，也应停止加深并改用代码写入路径、作业进度和 quota 差分等证据；“限定层数”不自动等于“足够轻量”。

#### 4.6.1 scratch 必须区分“正常在途”和“持久残留”

不能把 scratch 总量直接等同于正常 worker 占用。对 attempt/run 型流水线，应结合任务状态、attempt 年龄和公开产物契约，至少分为：

- 当前在途候选：冻结时每个 worker/run 最新的有限数量 attempt；
- 已成功且只剩必要小日志；
- 已有正式产物、但仍遗留大型 transient；
- 没有正式产物、且长期遗留大型 transient；
- 无法判定的异常项。

各类分别报告 attempt 数、文件数、`st_blocks × 512`、典型值和最大值。只有“当前在途候选”可被视为正常瞬时水位；长期存在的大型 MRC/CIF/NPZ 等必须单列为持久残留。若清理由另一个获授权 agent 执行，审计 agent 只消费其冻结 manifest 与前后 summary，不自行删除。

清理清单必须 fail-closed：生成 manifest 后若路径消失、inode/device/size 改变或树仍在漂移，旧 manifest 立即作废；先量化漂移与追查删除来源，再重新冻结清单或使用有完整 journal 的对账流程。不得把“不存在”误当作“本次成功删除”。

#### 4.6.2 动态 `rm` 的时间窗账本

大量递归删除期间，每组测量应绑定独立 `window_id`，记录窗口首尾时间、quota、对象数、各类别对象数、样本取得时间、活跃删除分支、活跃写入 worker，以及本窗口内启动/超时/遗留的 agent 查询。

不同窗口的对象数、平均文件大小和 quota 不得无说明混合。目录在窗口内变化时，以较小/较大对象数乘样本均值下界/上界形成占用包络；完整 `du` 也只是扫描经过整棵树的时间区间，不是原子快照。最终对账应使用最接近分类测量的 quota，或用首尾 quota 给出区间。

### 4.7 第 6 步：多 AI Agent 协作

多 agent 可以明显缩短总体时间，但更多 agent 不一定更快。Lustre 的瓶颈常常是元数据服务，而不是 CPU。

#### 4.7.1 分工原则

- 按一级目录或独立文件系统分片；
- 一个目录树只能由一个 agent 负责；
- 主 agent 维护本地路径认领表；
- 子 agent 不得自行扩大到未分配目录；
- 汇总 agent 只整合结果，不重复扫描；
- 同一高负载目录避免同时启动多个递归 `du`。

建议并发数根据元数据响应调整，通常先从 2～4 个低优先级扫描开始，而不是无限增加 agent。

#### 4.7.2 统一回报格式

每个 agent 回报：

```text
负责范围
明确排除范围
结构摘要
精确结果
估算结果
样本方案
误差与假设
动态变化
超时目录及已有结果
是否存在遗留查询进程
是否触碰服务器状态（正常应为否）
```

#### 4.7.3 超时不等于跳过

目录超时后应：

1. 保存已知结构；
2. 先只读确认远端查询是否仍存在；只有用户明确允许进程控制、且 PID/父进程/命令/归属全部精确匹配时，才可考虑停止仅由 agent 自己启动的查询；若用户禁止信号，则让其自然结束；
3. 将目录按直接子目录、ID 前缀或文件类型拆分；
4. 继续精确测量小分支；
5. 对剩余高成本分支抽样估计；
6. 最终报告中保留“为什么超时”和采用的替代方法。

高耗时通常代表高对象数或冷元数据，但不必然代表高空间占用。

#### 4.7.4 SSH/工具超时不保证远端进程结束

本地工具窗口结束、SSH 断开或没有收到 stdout，都不能作为远端 `du`、Python 扫描或清理程序已经退出的证据。agent 应：

1. 在启动前记录远端 PID、父 PID、命令摘要和开始时间；
2. 超时后用 `ps -o pid,ppid,stat,etime,wchan,cmd -p ...` 只读复核；
3. 未确认旧进程结束前，不对同一目录启动重复全扫；
4. 将仍存活的查询计入元数据负载和结果漂移解释；
5. 若结果只写 stdout 且连接已断，承认结果不可恢复，不用第二次同等全扫强行补救；
6. 无信号授权时，只观察自然结束，并在最终报告列出 PID、状态与遗留原因。

为了避免不可恢复输出，长任务应优先拆分成有界原子探针；只有用户明确允许服务器写入时，才能使用服务器侧原子结果文件。默认只读任务仍把记录写在本地。

### 4.8 第 7 步：汇总与 quota 对账

#### 4.8.1 以单根扫描或 quota 为总额基准

独立对子目录运行的 `du` 结果可能因硬链接而重复计数。因此：

- 有可接受时间的单根 `du -x` 时，以单根结果为目录总额；
- Lustre 用户总占用以同一时点的 `lfs quota -u` 为基准；
- 子目录独立 `du` 用于分类，不能无条件相加替代总额。

#### 4.8.2 计算残差

```text
quota 残差 = 同时点 quota - 已归因精确值 - 已归因估算中央值
```

残差可能来自：

- 尚未扫描的目录；
- 抽样误差；
- 动态写入或删除；
- 硬链接重复计数；
- open-deleted 文件；
- quota 延迟或不一致；
- 扫描和 quota 的时间点不同。

不能在没有证据时把残差平均分配给多个目录。若用户限制了某些目录的扫描范围，应将残差整体标为该范围下的“未细分残差”。

#### 4.8.3 用历史消失分类做量级对账

当对象数大幅下降、目录已从 namespace 消失、但 quota 与当前可见树存在巨大正残差时，可以把“历史上已知删除的完整类别”作为残差候选。方法是：

1. 列出已消失的版本/目录及删除时间下界；
2. 用仍存活的同构版本估计其删除前量级，并保留区间；
3. 将候选合计与 quota 残差比较；
4. 只报告“量级吻合/不吻合”，不得冒充 inode/FID 级归因；
5. 若吻合持续数小时或数天，升级检查 OST object destroy、open-unlinked 和服务端 quota accounting。

动态目录的分类值必须带时间戳。不同时间点的 Pocket、scratch、map 和 quota 不应直接相加成伪精确总账；应给中央值、区间和时间漂移方向。

## 5. 删除空间诊断协议（由 AI Agent 执行）

### 5.1 重要原则

看到“删除约 1 TiB 后 quota 没下降”，不能立即断言“同时写入了约 1 TiB”。

只有同时满足以下条件时，才能用 quota 差值反推并发写入：

1. 前后快照严格包围删除操作；
2. 删除对象的实际分配空间已知；
3. 删除已经反映到 quota；
4. 前后使用相同文件系统、用户和 quota 口径；
5. 不存在 open-deleted、硬链接、trash 或 quota 延迟。

否则，“并发写入量”只是一种数学可能，不是已经证实的事实。

如果删除一个普通文件后 quota 对象数减少了数十万，还说明两次快照之间发生了其他目录变化或批量 quota 更新，不能把全部差值归因于该文件。

### 5.2 两种执行模式

#### 模式 A：用户已经删除

AI agent 执行事后只读诊断，从 T3 开始，并尽可能通过日志、quota 历史和 open-deleted 文件恢复证据。

#### 模式 B：AI agent 控制删除实验

只有用户明确授权具体目标后，AI agent 执行完整 T0～T6。删除前必须再次核验绝对路径、文件系统、所有者和目标类型。

### 5.3 T0～T6 协议

#### T0：记录基准 quota 和对象数

```bash
date -Is
lfs quota -u "$USER" /storage
```

AI agent 将原始输出保存到本地审计记录，不能只保留换算后的 TiB。

#### T1：记录待删对象真实属性

删除前记录：

```bash
findmnt -T "$target"
stat -c 'path=%n uid=%u user=%U links=%h logical=%s blocks=%b block_unit=%B inode=%i' -- "$target"
du -B1 -- "$target"
lfs getstripe -v "$target" 2>/dev/null || true
lfs path2fid "$target" 2>/dev/null || true
```

重点确认：

- `du -B1` 的实际占用是否真的约 1 TiB；
- `stat` 的逻辑大小是否只是稀疏文件表象；
- 所有者是否为当前 quota 用户；
- 硬链接数是否大于 1；
- 目标是否确实位于 `/storage`；
- 目标是普通文件、目录还是软链接。

如果 `links > 1`，删除一个路径不会释放数据块；只有最后一个硬链接消失后才释放。

#### T2：执行删除

此步骤要求用户明确授权。

AI agent 在删除前必须输出将要删除的规范化绝对路径，并确认它处于授权范围。不得使用模糊通配符，不得递归删除计算结果未经验证的路径。

如果用户只要求诊断，跳过 T2。

#### T3：立即检查 open-deleted 文件

```bash
lsof -nP -u "$USER" +L1 2>/dev/null | grep /storage || true
```

如果被删除文件仍被进程打开：

- 路径可能已经不可见；
- 数据块会在最后一个文件描述符关闭后才释放；
- agent 只报告持有它的 PID、进程和文件大小；
- 未经用户明确授权，不终止该进程。

若无 `lsof`，可只读检查当前用户的 `/proc/<pid>/fd` 链接，但不得读取无权限进程或修改进程状态。

#### T3.1 明确观测节点与调度边界

在登录节点或 master 上运行的 `ps`、`pidstat`、`lsof` 和 `/proc/<pid>` 只能观察该节点上的进程。它们没有发现写入者，不能证明 Slurm compute node 上不存在写入。

若存在 Slurm 作业，应补充只读检查：

- `squeue`：作业状态和所在节点；
- `scontrol show job -dd <jobid>`：工作目录、命令、输出路径和节点；
- `sstat`：可用时读取作业步 I/O 统计。

调度器统计可能延迟、缺失或只覆盖特定 job step，因此也不能单独作为“没有写入”的证明。报告必须分别写明登录节点、调度器和计算节点的观测范围；未经授权，不使用 `srun` 启动作业步，也不为了诊断改变现有作业。

#### T3.2 正确解释 Lustre 等待通道

若删除进程的 `wchan` 为 `cl_sync_io_wait`，表示它正在等待 Lustre 客户端同步 I/O 完成。这与 unlink、目录项和元数据回收等待相符，但不能单独证明进程正在写入大量文件内容、已经死锁、数据块已反映到 quota，或应当终止该进程。

递归删除主要产生元数据操作，`pidstat` 或 `/proc/<pid>/io` 的普通数据写入速率可能为零。应将等待通道、对象数变化、quota 变化和 OST 差分联合解释。

#### T4：由 AI agent 持续监测 quota

AI agent 每 30 秒获取一次：

```bash
date -Is
lfs quota -u "$USER" /storage
```

建议持续 10～30 分钟。

实现要求：

- 使用产品提供的等待/监控机制或分段执行；
- 不用一个无法反馈状态的长阻塞命令静默等待 30 分钟；
- 每次结果追加到本地记录；
- 记录 `kbytes` 和 `files`；
- 不在服务器创建监控日志。

#### T4.1 使用按 OST 差分定位变化

在 Lustre 上，可在两个或多个时间点只读记录：

```bash
date -Is
lfs quota -v -u "$USER" /storage
```

比较时保留 MDT 对象数和每个 OST 的 `kbytes` 原始值，不只比较总和。解释原则：

- MDT 对象数持续下降，说明命名空间中的删除正在发生；
- 少数 OST 明显上升，可能存在集中于这些 OST 的条带写入，但尚不能直接归因到某个路径或进程；
- 多数 OST 同向变化，可能来自分布式/条带化写入、批量释放或 quota/accounting 更新，仍需其他证据；
- 对象数下降而块占用上升，说明 namespace 与块 quota 的变化不同步，或同时存在其他写入，不能仅凭净差值二选一；
- OST 差分用于缩小原因范围，不等同于目录级归因。

快照必须使用同一用户、同一文件系统和清晰时间戳。不得运行 `sync`、quota repair、cache drop、`quotacheck` 或其他会改变服务器状态的命令来强制刷新显示。

#### T5：比较预期值与实际值

```text
预期释放量 = 删除前对象的实际分配空间
实际 quota 变化 = quota_after - quota_before
未解释差值 = 实际 quota 变化 + 预期释放量
```

解释示例：

- 块占用下降且接近预期：正常释放；
- 对象数下降但块占用暂时不降：优先检查 open-deleted 或 quota 延迟；
- 块占用增加但对象数大幅下降：快照窗口内存在其他变化，或块与 inode quota 更新不同步；
- 文件逻辑大小约 1 TiB、实际 `du` 很小：稀疏文件，不应期待释放 1 TiB；
- quota 完全不变且 `links > 1`：可能仍有硬链接；
- quota 先不变、数分钟后下降：Lustre 异步更新或延迟释放。

#### T6：仍未释放时的分支诊断

按以下优先级继续：

1. **open-deleted 文件**：检查当前用户进程；
2. **实际分配大小**：核对删除前 `du -B1` 和 `st_blocks × 512`；
3. **硬链接**：核对删除前 `st_nlink`，必要时查找其他链接；
4. **错误文件系统或所有者**：核对 `findmnt`、UID 和 quota 用户；
5. **trash/回收站/重命名**：确认删除工具是否只是移动文件；
6. **并发目录变化**：比较对象数、其他大目录和开始/结束 quota；
7. **Lustre 延迟**：延长监测窗口；
8. **按 OST 检查**：尝试只读的 `lfs quota -v -u "$USER" /storage`；
9. **管理员侧异常**：向管理员提供时间、FID、stripe、quota 原始输出和 open-deleted 检查结果。

不得在证据不足时直接归因于“同时写入大量数据”。

只读权限下通常不存在“让 quota 立即显示正常”的安全命令。重新查询、延长监测和按 OST 对比只能观察状态，不能强制 Lustre 完成块回收或修复 quota。若 open-deleted、硬链接和明确并发写入均缺乏证据，且异常持续超过合理窗口，应把时间序列、OST 差分和相关 FID/stripe 信息交给管理员，而不是尝试客户端修复。

若出现一个边界清楚的新删除窗口，应做定量复现判定：已知从 namespace 消失的实际分配空间为 `D`，同期 quota 下降为 `Q`。当 writer 已冻结或其最大写入速率远小于 `D-Q`，且 `Q << D` 时，这比宽时间窗净变化更有诊断力，应作为管理员升级的核心证据。管理员最小只读核验项为：pending OST object-destroy、MDT→OST OSP/import 状态、跨节点 open-unlinked、各 OST 后端 UID quota 与 `lfs quota -v` 一致性、MDS/OSS 版本及相关修复 backport。诊断前不要求管理员执行 repair、LFSCK 或强制 sync。

## 6. 时间与精度优化策略

在检测范围相同的前提下，优化顺序为：

1. 先做结构探查，避免对明显同构目录盲目全扫；
2. 先做小样本测速，再决定精确或估算；
3. 使用 `os.scandir()` 获取轻量结构，不默认 `ls -l`；
4. 平铺文件按文件类型、ID 前缀或大小层分层；
5. 同构 PDB/EMDB 目录抽代表，同时单独处理异常值；
6. 主要占用类别提高样本量，小类别允许较低精度；
7. 已经得到足够窄的置信区间后停止增加样本；
8. 多 agent 只并行独立目录，避免重复元数据读取；
9. 将中间结果实时保存在本地，超时后从已有结果继续；
10. 总体 quota 在审计前后复测，避免把动态变化误认为估算误差。
11. 给所有长时远端查询建立 PID 台账；SSH 超时后先查存活状态，不重复重扫；
12. 大清理前后使用冻结 manifest、实际块数和 quota 时间序列做同窗对比；
13. 可见树与 quota 的 TiB 级残差用历史消失分类做量级交叉验证，但不冒充精确归因。

可将目标精度设为：

- 总体探查：找出主要 TiB 级类别，允许较宽误差；
- 细节探查：主要类别相对误差尽量控制在 10%～20%；
- 删除空间诊断：以删除对象实际分配空间为基准，要求严格时间序列，不使用宽窗口快照直接反推。

## 8. 常见误区

- 把磁盘空间称为 RAM 内存；
- 只看 `ls -lh` 的逻辑大小，不看实际块占用；
- 看到目录耗时长就认定它一定很大；
- 高耗时后直接跳过目录；
- 对高度同构目录仍强制递归所有对象；
- 用一个样本推断所有文件等大；
- 多个 agent 重复扫描同一目录；
- 将不同时间点取得的值直接相加；
- 独立子目录 `du` 相加时忽略硬链接重复计数；
- 用 quota 净变化直接反推出并发写入量；
- 为了完成审计而暂停、终止或修改用户任务；
- 在服务器写临时记录，而不是保存在本地。
- 把本地 PowerShell/`.cmd` 引号解析失败误判为远端命令失败；
- 把多个诊断问题塞进一条带复杂管道的 SSH 命令；
- 无限制回传所有进程或文件描述符，导致关键证据被淹没；
- 用 master 节点的 `pidstat` 或 `lsof` 排除 compute node 写入；
- 把 `cl_sync_io_wait` 直接解释为批量数据写入、死锁或可安全终止；
- 只比较总 quota，不保留 MDT 对象数与 per-OST 时间序列；
- 试图用 `sync`、quota repair 或 cache 操作“刷新显示正常”。
- 把 SSH 断开或本地工具超时当成远端扫描已经退出；
- 旧扫描仍在运行时，对同一目录再次启动等价递归扫描；
- 把 manifest 中已经消失的路径计作本次清理成功，而不先处理 live-tree drift；
- 把 scratch 总量全部解释为正常 worker 在途占用；

## 9. 核心原则摘要

```text
先快照，再探结构；
命令传输先自检，复杂探针拆成原子调用；
诊断输出必须有范围和预算；
先小样本测速，再决定精确或估算；
同构目录分层，异常目录单列；
精确值、估算值、用户先验和 quota 残差严格分开；
多 agent 分片但不重叠；
中间记录只写本地；
动态目录只承诺时间窗口快照；
登录节点、调度器与计算节点的观测结论不能混用；
对象数、总块数、per-OST 差分和进程状态必须联合解释；
删除后 quota 异常必须用 T0～T6 证据链诊断；
工作流允许适配，安全边界、统计口径和证据链不得放宽；
未经明确授权，AI agent 不写服务器、不删除数据、不终止用户任务。
```
