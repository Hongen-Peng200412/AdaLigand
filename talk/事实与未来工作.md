# Pocket_Plus 已核实事实与未来工作

本文记录 2026-07-22 对 Pocket_Plus 模型代码、训练运行目录和推理加载方式的只读核验结果，并保存三个可能在以后开展的工作。本轮已经对三个事项完成只读核验；没有修改 Pocket_Plus 代码，也没有在服务器执行 smoke。本文不是实现计划，后续工作仍需单独决定是否实施。

## 已核实事实

### 当前训练保存模型代码快照

`../../Pocket_Plus/src/utils/experiment_manager.py` 在训练任务建立运行目录时保存 `config.yaml` 和 `train.yaml`，并把当时的整个 `src/model/` 复制到运行目录的 `src_snapshot/src/model/`。

该快照只覆盖模型目录。它不包含 `src/train.py`、`src/wrappers/`、`src/datasets/`、`src/modules/`、`src/inference/` 或完整 Python 环境，因此应称为“模型代码快照”，不能解释为“完整训练与推理代码快照”。

服务器上的三项当前训练已经逐项核验：Job `321107`、`321540` 和 `321743` 的运行目录都存在 `config.yaml`、`train.yaml`、`src_snapshot/src/model/stage1_model.py` 与 `src_snapshot/src/model/stage1_voxel_backbone.py`。这三项训练对应的 checkpoint 已经具备模型代码快照。

### 当前推理尚未使用模型代码快照

`../../Pocket_Plus/src/inference/checkpoint.py` 会寻找 checkpoint 所在运行目录旁的 `config.yaml`，但仍从当前工作区的 `src/model/` 实例化模型，没有读取 `src_snapshot/`。

Pocket_Plus 旧提交 `857a547` 的 `src/inference/get_pred.py` 曾实现以下加载顺序：清除当前进程已经导入的 `src.model` 模块，把 checkpoint 运行目录中的 `src_snapshot/src` 放到 `src` 包的优先导入位置，再根据训练配置实例化模型并严格载入权重。因此，恢复“每个 checkpoint 使用自己的模型代码快照”可以集中修改当前 checkpoint 加载器，不需要重写整条推理管线。

已经确认以后采用以下兼容边界：

- checkpoint 存在相邻的 `src_snapshot/src/model/` 时，推理必须使用该模型代码快照。
- checkpoint 缺少模型代码快照时，默认明确报错；只有用户显式指定后，才允许尝试使用当前工作区模型代码。
- 一个推理进程只加载一套模型代码快照，避免不同快照的 Python 模块在同一进程中互相污染。
- 旧 checkpoint 通过各自的模型代码快照继续推理。新版模型代码不保留旧体素头、旧体素主干或其他旧结构的兼容分支。

这项加载行为尚未在当前正式推理代码中实现。它已经纳入辅助监督端到端任务，由受限 subagent 根据主 agent 固定的完整 `src/` 快照格式实现；主 agent 负责审查、集成和最终验收。

### 最终体素预测头之前已有空间卷积

当前 `voxel_final` 特征形成前已经经过多层空间卷积。紧邻最终特征的计算在 `../../Pocket_Plus/src/model/raunet.py` 中定义，并由 `../../Pocket_Plus/src/model/stage1_voxel_backbone.py` 调用，具体包括：

1. 对同一最高分辨率特征分别执行 `3×3×3`、`5×5×5` 和 `7×7×7` 卷积；
2. 拼接三张输出特征；
3. 对拼接结果再执行一层 `3×3×3` 卷积，得到 `voxel_final`。

编码和解码过程还包含其他 `3×3×3` 卷积。因此，将最终输出头改为 `1×1×1 Conv3d → 激活函数 → 1×1×1 Conv3d` 不等于取消空间信息融合；最终输出头读取的 `voxel_final` 已经混合邻近体素信息。

### 现有 DensityMUNetLite 不是 Stage1 的直接替代项

当前可找到的 MUNet 实现在 `../../Pocket_Plus/src/selector/model/density_munet_lite.py`，服务于 Selector。它目前接收固定形状的单通道密度并返回一张特征图，没有实现 Stage1 体素主干所需的可配置输入通道、命名特征输出、循环精化输入与输出、体素预测结果和特征通道登记。

此外，当前训练只保存 `src/model/`。如果 Stage1 直接导入 `src/selector/model/density_munet_lite.py`，该实现不会进入现有模型代码快照。

## 当前任务、未来工作及已有核验结果

扩大代码快照和升级推理加载已经从未来候选工作移入辅助监督端到端任务。最高分辨率卷积成本与未来体素主干替换仍保留为独立事项；本节已有的只读核验和隔离测量结果继续保留。

### 1. 测量最高分辨率空间卷积的资源成本

在 `80×80×80` 体素网格上，单独测量下列计算的显存、执行时间和训练速度成本：

- 并行的 `3×3×3`、`5×5×5` 和 `7×7×7` 卷积；
- 三张特征的拼接；
- 拼接后的 `3×3×3` 卷积。

后续评估应明确输入与输出通道数、数值精度、批大小、是否计算梯度和使用的 GPU，避免把不同条件下的测量值直接比较。

#### 本轮本地测量

本机没有名为 `Pocket_Plus_windows` 的 Conda 环境，但 `D:\Anaconda` 的 `base` 环境有 PyTorch `2.7.0+cu128`，CUDA 可用；本机显卡为 NVIDIA GeForce RTX 4060 Laptop GPU，显存约 8 GiB。该环境缺少 `lightning`，因此没有执行 Pocket_Plus 完整 wrapper 或完整训练 smoke；我用当前 `Stage1VoxelBackbone` 的真实卷积模块完成了 `80³` 形状 smoke，并用同形状隔离模块测量资源成本。

测量严格采用当前 `stardard.yaml` 的通道数：输入 `c0` 为 `(1,64,80,80,80)`，三路输出各为 32 通道，拼接后为 96 通道，最终 `voxel_final` 为 48 通道。PyTorch CUDA 事件计时，先执行一次预热；推理测量 3 次，训练测量 2 次。显存数值是该隔离块的 CUDA 峰值，不是完整 RAUNet 的显存。

| 模式 | 平均时间 | CUDA 峰值已分配 | CUDA 峰值保留 |
|---|---:|---:|---:|
| FP32 推理 | 153.4 ms | 0.770 GiB | 0.945 GiB |
| 纯 FP16 推理 | 52.4 ms | 0.430 GiB | 0.531 GiB |
| FP32 前向与反向 | 547.6 ms | 1.078 GiB | 1.408 GiB |
| 纯 FP16 前向与反向 | 174.9 ms | 0.550 GiB | 0.820 GiB |

在相同输入下拆开测量，FP32 推理时间约为：`3×3×3` 12.2 ms、`5×5×5` 40.4 ms、`7×7×7` 92.2 ms、拼接与 ReLU 3.5 ms、最后 `3×3×3` 13.7 ms。FP16 推理约为：3.1 ms、10.5 ms、27.0 ms、1.8 ms 和 7.8 ms。拆开测量的总时间与整块测量不完全相加，原因是单独运行时的输入、缓存和卷积算法选择不同。

按乘加次数估算，这个块每次前向约为 582.75 GMAC，若把一次乘加计为两次浮点运算，约为 1.165 TFLOP。其中 `7×7×7` 分支约占 61.7%，是四项卷积计算中最大的部分。作为对照而非最终设计结论，`48→32→48` 的两层 `1×1×1` 体素 MLP 在同一显卡、同一网格上的隔离 FP32 推理约 3.9 ms，FP16 约 1.9 ms。

**结论**：这组多尺度卷积块在 8 GiB 显卡上单独运行不会造成显存溢出，但它确实带来可观的每轮计算时间；完整 RAUNet 还要保留编码器、解码器和循环精化的其他特征，不能把这里的隔离峰值当成完整模型峰值。若目标是降低最高分辨率计算，优先关注 `7×7×7` 分支及其保留的三张高分辨率特征。

### 2. 当前端到端任务：扩大训练代码快照并升级 checkpoint 推理

主 agent 负责把训练代码快照扩大为整个 `src/`，其中包括 `src/train.py`、`src/model/`、`src/wrappers/`、`src/datasets/`、`src/modules/`、`src/inference/` 以及其他项目包；同时保存实际使用的 resolved 配置和来源清单。主 agent 固定快照目录、清单格式、既有快照不可静默覆盖等写入契约。

一个 subagent 根据该写入契约升级推理加载器，使推理根据 checkpoint 所在运行目录选择对应快照，并补充完整快照、旧式仅模型快照、缺少快照和单进程模块隔离等专项测试。subagent 不修改标签、模型、损失或快照格式；主 agent 审查并合入其修改。正式训练必须等这项推理改动合入后提交，使新运行保存的完整 `src/` 本身包含新版推理代码。

#### 本轮核验到的实际依赖范围与工作量

排除 `__pycache__` 和 `.pyc` 缓存后，当前 `src/` 共 103 个文件、96 个 Python 文件，大小约 3.3 MiB；当前 `src/model/` 共 26 个文件、23 个 Python 文件，大小约 2.1 MiB。因此，单纯把快照从 `src/model/` 扩大为整个 `src/`，复制量和磁盘成本都很小。

但当前 Stage1 推理并不只导入 `model`、`wrapper`、`dataset` 和 `inference`。静态导入核验还发现它会使用 `src/artifacts`、`src/component_lineage`、`src/evaluation`、`src/stage1_producers`、`src/selector`、`src/utils` 等包；训练入口还会使用回调、日志、故障恢复数据集和作业环境工具。若只按原文列出的几个目录复制，仍可能得到不完整的快照。

工作量分为两层：

1. **机械复制层：小**。把整个 `src/`、resolved 配置、训练入口和一个源文件清单或哈希清单写入运行目录，代码量不大，存储开销也很小。
2. **可复现验证层：中等**。推理加载器必须让所有 `src.*` 模块从同一份快照解析，而不是只切换 `src.model`；需要清理当前进程已缓存的 `src.*` 模块，或每个 checkpoint 使用独立子进程。还要分别验证旧模型、新模型、Dataset、wrapper、推理产物和 Selector 依赖。

这套快照仍不能保存 CUDA 驱动、PyTorch 等外部包、原始数据和服务器状态；若目标是长期可复现，还要另行记录 Python 环境、代码外部依赖版本和必要的输入契约。因此总体判断为“实现改动小到中等，完整验证中等偏大”，不是简单复制一个目录后即可宣称整条历史运行链路已经复原。

### 3. 评估新的体素主干与可插拔输出头

评估把当前 RAUNet 体素主干替换为近年来表现优秀的三维 U-Net 类架构所需的工作量。候选主干需要适配当前模型的：

- 循环精化，也就是把前一次体素预测形成的信息送入下一次计算；
- 信息融合接口，也就是允许原子、体素或其他分支在指定位置交换特征；
- 当前候选生成和后续模块所需的命名特征及通道信息；
- 模型代码快照和 checkpoint 推理机制。

同时应彻底分离体素主干与最终输出头：体素主干只生成命名特征，配体区域、受体结合区域、结构类别和距离等输出头分别由独立模块实现，并通过明确接口接入体素主干。这样更换体素主干时不必复制或重写各个任务的输出头。

#### 本轮核验到的当前接口与工作量

当前 `Stage1VoxelBackbone` 继承 `SimpleUnet`，并在同一个类中同时负责三件事：生成 `voxel_final` 和其他命名特征、生成 `voxel_logits_aux` 与 `voxel_logits_ligand`、生成下一轮使用的 `voxel_recycle_out`。因此，输出头尚未与主干分离。

`VolumePointStage1Model` 对体素主干有明确的结构接口：

- 调用 `forward(voxel_grid, recycle_in, return_feature_keys)`；
- 读取 `feature_channels_by_name`，按 `return_feature_keys` 构造点—体素融合钩子；
- 读取 `voxel_final` 的通道数，建立候选、原子和稀疏精化模块所需的特征接口；
- 在循环精化中传入上一轮的 `voxel_recycle_out`；
- 要求输出 `voxel_features`、`voxel_logits_aux`、`voxel_logits_ligand` 和 `voxel_recycle_out`。

此外，当前 voxel-only 推理入口固定要求 `enable_recycling=true` 且 `max_recycles=3`，并实际执行三轮体素主干。因此，新主干不能只返回一张密集特征图。当前找到的 `src/selector/model/density_munet_lite.py` 只接收单通道密度并返回一张特征图，不是 Stage1 的直接替代项。

工作量判断如下：

- 若候选三维 U-Net 已经具备 3D 输入、编码—解码特征和可复用的循环状态，只增加 Stage1 适配层，并保持现有命名特征和通道契约，工作量为**中等**；现有 `VolumePointStage1Model` 的融合、候选和点分支可以大部分保持不变。
- 若候选主干的特征尺度、循环状态和融合位置都不同，同时把输出头从 `Stage1VoxelBackbone` 中抽出，工作量为**中等偏大**；需要修改主干接口、Hydra 配置、输出头构造、损失读取、特征融合初始化、checkpoint 键名和训练/推理测试。
- 若还要求重新设计信息融合钩子的语义，或让旧的点分支、候选和稀疏精化直接适应新的特征层级，工作量为**大**，这已经不是单纯替换 backbone。

当前已确认的旧 checkpoint 兼容策略会降低一部分改动压力：旧 checkpoint 由自己的模型快照推理，新版代码不保留旧主干和旧输出头的兼容分支。但新主干的每个训练运行仍必须把它及其 Stage1 适配层放进快照范围，否则未来无法按 checkpoint 复原该模型结构。
