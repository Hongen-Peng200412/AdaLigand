## Decisions

### 已确认的审计边界

- 第一阶段只读审计；唯一允许的项目写入是本 handoff。
- “重跑 A–C”按**达到最新契约完整态**理解，不按“无条件删除/重算所有文件”理解。
- 增量复用是硬约束：已有下载件与仍兼容的旧 C 核心数组应尽量复用；只计算缺失或新契约要求的内容。

### 推荐的增量 C 策略

不要直接对旧 `c_parse.py` 使用单一 `--overwrite` 全开关。原因：它会把 parse 产物和全局去重 LigandObject 的覆盖耦合在一起；多进程下多个 worker 可能重复覆盖同一去重对象，既浪费又增加并发风险。

推荐把“C 解析主干”和“C 契约升级”解耦，并采用 schema-aware 完成判据：

- `centroid_atom`：由现有 `coords_{cid}` + `present_{cid}` 直接派生，原子写回 `ligand_coords.npz`；无需重新下载、无需重建 occurrence。
- 49 维 `feat`：由完整受体的现有 `coords/element/res_type` 计算，追加进 `receptor_tokens.npz`；无需密度图。
- `ligand_descriptors`：由 3,833 份现有 LigandObject 的化学图 + `ref_pos` 去重计算；按 `object_key` 一次一份，不随 22,386 个 PDB 重复。
- 受体键表：必须重新读取对应 mmCIF，才能完整覆盖残基模板内部键、主链/骨架键、`_struct_conn` 交联、二硫键和共价修饰；不能只凭旧 token 无损恢复。生成前应验证重建出的受体行序/基础数组与旧 token 一致，再原子替换完整 `receptor_tokens.npz`。
- 完成判据不能只看文件存在；必须检查必需 key、shape、dtype、行序与 occurrence/candidate_id 对齐。

由于旧 C 全量实跑只用了约 30 分钟，重新读取 22,386 份 mmCIF 本身不昂贵。真正需要避免的是重复下载、重复 LigandObject 物化、无差别覆盖和不带 schema 的 skip。

### Beneficial drift / 新增 scope

- `centroid_atom`、受体键表、49 维特征、配体描述子把下游 Stage1/2 所需的慢或稳定标签前移到正确生产方，边界清晰。

### Neutral drift

- 历史 handoff/工具 README 曾写 B/C 为 6 分片、8 核/7 worker；当前本地 sbatch 是 4 分片、5 核/4 worker，服务器实际也经历了“先 6 分片、后 4 分片补跑”。这是运行配置漂移，不改变数据语义，但文档应在执行阶段统一。
- 服务器同步目录不是可读 Git 工作树，但关键代码 SHA-256 与本地一致，可把本地代码作为其精确来源快照。

### Harmful drift / 风险

- C 的旧 skip 条件会把旧 schema 误当新 schema 完成，是当前最直接的错误风险。
- `Data_Preprocessing/Ori_Data/code/readme.md` 仍描述旧 C schema，已经落后于当前规划。
