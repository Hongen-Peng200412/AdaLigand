Question 1: Find_0 checkpoint 快照激活前过早导入 `src.datasets` 的缺陷应采用什么修复边界？
Decision: 只接受消除错误导入顺序所需的最小修复；不放宽快照保护，不建设历史模型通用兼容层，也不为当前已经较完善的推理管线增加不必要的代码、包装层或运行框架。
Reason: 当前任务只需要可靠运行 Find_0，不能让一次推理任务扩大成复杂的兼容工程。

Question 2: 正式推理的 Dataset 资产缓存上限应采用什么量级？
Decision: 不采用 512 MiB 或约 5 GiB 的小上限；正式配置把上限提高约两个数量级，以约 500 GiB 作为当前目标量级。该数值只是允许缓存使用的上限，不预先分配对应内存。
Reason: 服务器计算节点约有 1 TiB 内存，完整实验密度图和模拟密度图不应因为过小上限反复解压和读取。

Question 3: 本轮如何优先生成 F1-centered，同时保留以后补跑 CLG-centered 的能力？
Decision: 用最小改动增加 calibration、validation 和 train 的 F1-only 命令。本轮只生成 probability、components 和 F1-centered。以后对同一输出根目录执行现有的 `*-f1-clg` 命令，必须复用已有完成产物，只补齐缺失的 CLG-centered。
Reason: 当前运行器已经根据每种产物的 `_COMPLETE` 标记跳过完成内容；无需建立第二套 CLG 生产逻辑。

Question 4: calibration 评估与未来独立评估支线如何划分？
Decision: 当前主线只要求 calibration 集合的阈值、语义评估和实例评估。validation 独立评估与 Li-threshold 评估留在后续支线，不阻塞 Find_0 主线。

Question 5: 推理配置、提交命令和运行产物应采用什么组织方式？
Decision: 参照 `Pocket_Plus/训练与运行` 建立人类可读的正式推理入口，清楚区分一次性运维 smoke 与正式、自成一体的推理。smoke 不作为人类验收入口；正式脚本、配置、命令和产物目录必须可以独立冷读和验收。

Question 6: 正式推理是否需要预先固定 GPU 类型，并禁止混用 A100、A800、H100 与 H200？
Decision: 不预先固定 GPU 类型，也不因不同 GPU 架构可能产生可忽略的数值差异而禁止混用。正式提交前根据当时空闲资源选择卡型和数量。显存参照为 A100 40 GiB，A800 与 H100 80 GiB，H200 112 GiB；完整图推理与 F1-centered 推理分别确定批量大小，因为两者实际执行的模型计算和激活不同。

Question 7: 一次性 smoke、正式推理脚本与服务器提交之间采用什么边界？
Decision: smoke 可以使用为当前排障临时编写的 shell 脚本，在提交时任选一张空闲的 A100、A800、H100 或 H200；全部 smoke 产物写入隔离临时目录。纳入当前范围的全部 smoke 都完成、发现的缺陷都已按最小范围修复后，在 `Pocket_Plus/训练与运行/sh/infer/` 编写一个或多个精简、完善且可独立运行的正式 shell 脚本，并可配套固定 YAML 配置。正式脚本不得依赖 smoke 临时文件，必须逐项详细注释人类需要阅读的字段。正式脚本完成并通过静态检查后，才向用户请求提交授权；得到“你去提交吧”或等效明确授权后才能提交正式 Slurm 任务。

Question 8: 正式 Find_0 推理是否采用由 checkpoint 身份决定、跨 Slurm Job 和失败重试保持不变的输出根目录？
Decision: 采用稳定的 checkpoint 身份目录。当前正式根目录固定为 `/storage/penghongen/AdaLigand_stage1_inference/Find_0-CPC1-ligand_PRAUC_0.675477/`；其中 `inputs/` 保存冻结清单、推理配置与来源记录，`artifacts/` 作为现有推理 CLI 的 `--output-root`。Slurm 日志、release 和 launch 继续由 `/home/penghongen/Feedback/Pocket_Plus/` 管理。同一 checkpoint、清单和推理契约的重试复用该目录，只有这些身份发生变化时才建立新的正式目录。

Question 9: 本轮“全部 smoke 完成”具体覆盖哪些入口？
Decision: 使用同一张临时 GPU 和隔离临时目录，严格加载真实 Find_0 checkpoint；依次 smoke `cal-probability`、`freeze-thresholds`、calibration F1-only、validation F1-only 和 train F1-only。随后在已有 F1-centered 的 smoke 产物上执行现存 `*-f1-clg`，证明它不改写 probability、components 与 F1-centered，只补齐 CLG-centered，并证明再次执行时全部识别为已完成。完整图 `window_batch_size` 与 centered `centered_batch_size` 分别测定并记录卡型和峰值显存；正式脚本依据 A100 40 GiB、A800/H100 80 GiB、H200 112 GiB 设置保守分档。smoke 还必须检查异常退出后的 `_RUNNING` 清理、`_COMPLETE` 发布顺序、同命令续跑和隔离目录碰撞保护。本轮 smoke 不运行 selector，不实现 validation 独立评估或 Li-threshold，也不执行任一完整集合的正式生产。

Question 10: `训练与运行/sh/infer/` 中采用一个分阶段脚本，还是为每个阶段分别建立脚本？
Decision: 不强制把 calibration probability、冻结阈值、calibration F1、validation F1、train F1 和未来的 CLG 补跑塞进同一个带阶段分派逻辑的 `Find_0.sh`。正式入口按照人类实际提交方式自然拆分，优先让每个 shell 脚本直接展示一项明确工作、所用 GPU 类型和人工可修改参数；允许同一项工作由不同 GPU 类型的脚本共同完成。具体文件划分在后续问题中继续确定，不为了减少脚本数量增加通用包装或自动调度。采用更新后的通用任务提交系统：任务根目录内的文件名、相对路径和绝对路径会解析为同一个任务脚本，并随任务根目录进入 release；正式脚本不再因为使用绝对路径而绕过冻结。

Question 11: 正式推理的 `global_shard_count`、`shard_index` 和多种 GPU 之间如何分工？
Decision: `global_shard_count` 和本次提交覆盖的 `shard_index` 由用户在正式 shell 脚本与提交命令中直接填写，不增加自动分片分配器。例如完整工作固定为 16 个分片时，可以先申请 8 张卡并只提交分片 0–7，以后再由相同或另一种 GPU 的脚本提交分片 8–15。多个脚本必须使用相同的 `global_shard_count`、输入清单、checkpoint、推理契约和输出根目录，并使用互不重叠的 `shard_index`；这样不同 GPU 类型的任务可以共同完成同一项正式推理，也可以分多批续跑。

Question 12: 正式 shell 脚本按照什么单位拆分？
Decision: 按“独立工作阶段 × 正式提交时实际采用的 GPU 类型”拆分。每个脚本只执行一项明确工作，例如 calibration probability、calibration F1、validation F1 或 train F1；只为正式提交时实际使用的 GPU 类型创建脚本，不预先生成所有卡型与阶段的排列。GPU 脚本固定该卡型经过 smoke 核定的完整图批量与 centered 批量，直接写明 `global_shard_count`，并用 `SLURM_ARRAY_TASK_ID` 取得当前 `shard_index`；具体覆盖哪些分片编号由提交时的 Slurm array 人工指定。`freeze-thresholds` 是 calibration probability 全部完成后的单次汇总脚本，不按 GPU 类型复制。不增加共享包装脚本、阶段分派器或自动分片分配器；允许在各正式脚本中明确重复少量共同路径和身份字段，以保证每个文件可以独立冷读。
