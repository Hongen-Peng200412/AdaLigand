Question: AdaLigand Stage1 的正式训练应如何分离 Slurm 资源申请、三个学习版训练脚本、release/launch 证据和无卡配置比较？
Decision: 唯一的 `stage1_train.sbatch` 通过 `sbatch stage1_train.sbatch --sh=Find_1.sh` 申请资源并选择 `训练与运行/sh/` 中的正式训练脚本。`Find_0.sh`、`Find_1.sh` 和 `unet_c1.sh` 默认只执行正式训练，只描述运行环境、模型配置、数据路径、训练参数和正式产物，不申请资源、不实现锁循环，也不提供 `--resolve-only` 或其他无卡配置产出模式。`releases/` 保存排队前冻结的确切代码版本，`launches/` 保存启动参数、最终解析配置、脚本副本和 Git 身份，`src/train.py` 的运行快照保存实际运行时代码；复杂支撑机制放在远离三个模型脚本的辅助目录。配置比较仅由需要时创建的一次性临时脚本完成，不进入正式启动接口、正式运行目录结构或三个学习版脚本。
Reason: 用户希望一次 `sbatch` 提交即可启动训练，同时让三个模型脚本成为可直接阅读和修改的训练定义；release、launch 和运行快照分别回答准备版本、启动决定和实际运行代码三个不同问题，不能合并，但其实现不应污染训练主线。

Question: GPU 类型、GPU 数量、CPU 数量、partition 和 QOS 应直接写在 `sbatch` 命令中、保存为 `stage1_train.sbatch` 默认值，还是由单独的提交辅助脚本转换？
Decision: 采用单独的 `submit_stage1.sh`。用户通过一次命令选择具体任务和资源；该脚本自动构造并执行唯一一次 `sbatch stage1_train.sbatch ...`，不得要求用户随后编辑 `stage1_train.sbatch`、三个模型脚本或动态命令文件。设计时审计 `与服务器交互/sbatch/` 中已有的 GPU 和 CPU 模板；如果职责能够统一，则同一提交接口同时支持 CPU、GPU 和 Slurm job array。
Reason: 直接暴露完整 Slurm 参数过长且容易配错，写死默认资源又会隐藏真实申请；薄提交层可以在不把训练逻辑耦合进资源模板的情况下统一参数校验、资源映射和一次命令提交。

Question: 统一提交器支持 `--array` 时，是否允许 `Find_0.sh`、`Find_1.sh` 和 `unet_c1.sh` 直接作为数组任务重复提交？
Decision: 统一提交器支持 CPU、A100、A800、H100、H200 以及可选的 Slurm `--array` 参数，但当前三个正式 Stage1 训练脚本禁止与 `--array` 同时使用。提交器必须在调用 `sbatch` 前拒绝这种组合；将来只有明确读取 `SLURM_ARRAY_TASK_ID` 并定义分片或参数变化语义的专用任务脚本才能使用数组。所有新增的 `.sh` 和 `.sbatch` 文件都加入详细中文注释，解释参数、资源映射、目录职责、执行顺序和安全检查。
Reason: Slurm array 只会重复执行同一个任务，不会自动切分 Stage1 数据；当前三个训练脚本若直接使用 array，会产生配置和随机种子相同的重复正式训练并浪费多张 GPU。

Question: 正式训练失败或被人工终止后，应立即释放 GPU、仅保留最小失败重试状态，还是保留现有完整锁体系？
Decision: 保留完整锁体系，包括 `pre_lock`、`try_lock`、`after_lock`、`kill_lock` 和同一 allocation 内的动态再次执行能力。同一个 Slurm Job 一般对应同一个任务，不把已经申请的资源任意改作无关任务。
Reason: 完整锁体系允许在排队获得稀缺 GPU 后控制启动时机、穿透高负载进程实施终止、检查失败并在原 allocation 内重试；任务身份原则上不变，以限制动态执行造成的审计漂移。

Question: 同一个 Slurm Job 内，四锁重试是否只能原样重跑或修复同一任务，还是可以把已经申请到的资源用于任意后续命令？
Decision: 保留四锁最初设计的完整动态能力。Slurm Job 只表示一份已经获得的 CPU/GPU allocation，不作为科学实验、模型或训练运行的唯一身份；获得资源后，用户可以通过动态命令文件依次运行同一任务的重试、其他训练、推理、诊断或其他命令。每次实际执行分别保存自己的 release、launch、最终配置和运行快照，同一 Job 内的不同执行不得互相覆盖。
Reason: 四锁的目的就是把稀缺资源 allocation 与具体命令解耦，使已经排到的卡能够灵活复用。只要把 Job 身份、每次命令执行身份和正式运行身份分开记录，动态复用不会造成 release、launch 或运行目录冲突；辅助运行系统可以保持复杂，项目负责人的主要学习范围仍是从 keep_list 到模型以及推理契约。

Question: 四锁应通过控制命令间接管理，还是继续以共享文件系统中可见的具体文件作为主要控制界面？
Decision: `pre_lock`、`try_lock`、`after_lock` 和 `kill_lock` 必须继续是图形化文件浏览器中可以直接看到、创建或删除的具体文件；动态命令也保留为可见的 `run_cmd` 文件。用户通过文件是否存在直观判断和控制 allocation 状态，不用 `stage1_control.sh start/retry/release` 等命令取代这套文件界面。
Reason: 文件锁是原四锁设计的核心交互方式，能够在共享文件系统和图形化页面中直接显示当前状态；把它包装成命令会隐藏状态并改变用户已经熟悉的操作语义。

Question: 新 allocation 获得资源后，应默认创建 `pre_lock` 等待人工放行，还是默认立即执行并仅在显式请求时创建 `pre_lock`？
Decision: 默认不创建 `pre_lock`，获得资源后立即执行提交时选定的初始动态命令；`submit_stage1.sh` 提供简单的 `--hold` 参数，只有带此参数提交时才在 allocation 启动后创建可见的 `pre_lock` 并等待用户删除。`try_lock`、`after_lock`、`kill_lock` 和 `run_cmd` 的文件语义不变。
Reason: 常规正式训练应通过一次提交自动开始，同时保留需要先占卡、检查 release、launch、资源和动态命令时的人工启动门。

Question: 正式 release、launch、训练运行和 allocation 状态应放在同步的 Pocket_Plus 仓库内部，还是放在仓库外的持久反馈根目录？
Decision: Pocket_Plus 的新正式反馈产物统一放在 `/home/penghongen/Feedback/Pocket_Plus` 下，不放进 `/home/penghongen/My_Project/Pocket_Plus` 同步仓库。当前三项正在运行的 AdaLigand Stage1 实验继续使用其既有旧目录；新体系不迁移、不覆盖，也不为旧目录增加兼容逻辑。实施完成后的 handoff 必须明确记录旧三项实验的实际产物目录与新体系的区别。
Reason: 代码同步脚本会上传并递归修改 Pocket_Plus 仓库权限，正式 checkpoint、W&B、release、launch 和锁状态不应与代码同步耦合；历史运行保持原位可以避免破坏正在进行的实验，新旧边界通过 handoff 说明即可。

Question: `/home/penghongen/Feedback/Pocket_Plus` 下是否还需要增加 `adaligand` 或 `AdaLigand_Stage1` 总目录？
Decision: 不增加。`/home/penghongen/Feedback/` 下的 `Pocket_Plus`、`Selector`、`Matcher` 是平行的应用目录；Pocket_Plus 自己直接管理 `releases/`、`launches/`、`logs/` 和 `allocations/` 等职责目录。正式训练产物完全沿用 `src/train.py` 已有的 `logs/` 行为，不再发明 `runs/` 层，也不据此引入项目总称。

Question: 正式提交前的 release 应由用户单独准备，还是由 `submit_stage1.sh` 在一次提交命令内自动创建或复用？
Decision: `submit_stage1.sh` 默认在调用 `sbatch` 前自动创建或复用当前服务器 Pocket_Plus 代码的冻结 release，并把确切 release 写入初始 launch 和动态命令；高级用户可以显式指定已有 release，但普通正式提交不需要第二条准备命令。release、launch、内容身份、原子发布和其他复杂实现不得进入三个模型脚本或人类学习主线，应放在主线外的辅助实现目录。
Reason: 一次命令提交可以避免排队期间代码漂移和手工选错 release；辅助机制允许复杂，但主线是否能让用户独立看懂并正确使用是最终验收条件，不能为了实现自动化再次污染训练脚本和阅读路径。

Question: allocation 的可见锁文件、动态命令和日志应如何分层放置，是否允许辅助实现自行增加状态文件？
Decision: `/home/penghongen/Feedback/Pocket_Plus/allocations/` 根目录直接放置 `pre_lock_<job-id>` 和 `try_lock_<job-id>`，便于用户在图形化文件页面中集中查看和操作；`<job-id>/` 子目录内放置 `after_lock_<job-id>`、`kill_lock_<job-id>`、`run_cmd_<job-id>.sh` 以及该 allocation 的标准输出和标准错误日志。不得未经用户允许增加 `last_exit_code` 或笼统的“其他执行记录”；若实现确实需要新增持久文件，必须先说明其必要性并取得用户确认。

Question: `releases/` 与 `launches/` 是否只需在实现中保留，还是必须证明二者职责不同并进入人类可读说明？

Reason: `release` 应回答“排队和执行使用哪一份冻结代码”，`launch` 应回答“这一次决定以哪些资源、脚本和参数启动什么”；只有目录结构和 README 都能让用户独立识别这一区别，保留两层证据才不是重复工程。

Question: allocation 子目录中的标准输出和标准错误日志是否需要增加跨命令追加分隔、轮转或执行编号等新机制？

Reason: 本次目标是把现有可用的训练运行方式重建为清楚、统一的学习版，不是重新设计日志系统；未经需要验证的新机制只会扩大修改面和用户需要理解的范围。

Question: `/home/penghongen/Feedback/Pocket_Plus` 下四类正式目录分别面向谁，其可读性和行为兼容性应达到什么标准？

Question: 自动创建 release 时，应以服务器实际代码内容、Git 身份还是修改后的代码同步体系作为权威依据？

Reason: 服务器同步副本会删除 `.git`，实际文件内容才是训练真正能够读取的代码；内容身份可以防止排队期间代码漂移和重复发布，同时把哈希限制在 AI 审计层，避免再次形成用户必须依赖哈希定位运行的复杂主线。

Question: 同一个 Slurm Job 通过修改 `run_cmd_<job-id>.sh` 连续执行多次命令时，`launches/` 应记录一次 allocation，还是记录每一次实际命令执行？
