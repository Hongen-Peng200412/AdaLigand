Question: AdaLigand Stage1 的正式训练应如何分离 Slurm 资源申请、三个学习版训练脚本、release/launch 证据和无卡配置比较？
Decision: 通用的 `task.sbatch` 申请资源并执行 `--sh` 选定的任务脚本，通用的 `submit_task.sh` 负责把人类可读资源参数转换成一次 `sbatch task.sbatch ...` 提交。`Find_0.sh`、`Find_1.sh` 和 `unet_c1.sh` 默认只执行正式训练，只描述运行环境、所选 experiment 配置、明确覆盖 experiment 的参数、数据路径和正式产物，不申请资源、不实现锁循环，也不提供 `--resolve-only` 或其他无卡配置产出模式。`releases/` 保存排队前冻结的确切代码版本，`launches/` 保存启动参数、最终解析配置和脚本副本，`src/train.py` 的运行快照保存实际运行时代码；复杂支撑机制放在远离三个模型脚本的辅助目录。配置比较仅由需要时创建的一次性临时脚本完成，不进入正式启动接口、正式运行目录结构或三个学习版脚本。
Reason: 用户希望一次 `sbatch` 提交即可启动训练，同时让三个模型脚本成为可直接阅读和修改的训练定义；release、launch 和运行快照分别回答准备版本、启动决定和实际运行代码三个不同问题，不能合并，但其实现不应污染训练主线。

Question: GPU 类型、GPU 数量、CPU 数量、partition 和 QOS 应直接写在 `sbatch` 命令中、保存为通用 sbatch 默认值，还是由单独的提交辅助脚本转换？
Decision: 采用通用的 `submit_task.sh`。用户通过一次命令选择具体任务和资源；该脚本自动构造并执行唯一一次 `sbatch task.sbatch ...`，不得要求用户随后编辑 `task.sbatch`、任务脚本或动态命令文件。设计时审计 `与服务器交互/sbatch/` 中已有的 GPU 和 CPU 模板；同一提交接口同时支持 CPU、GPU 和 Slurm job array。
Reason: 直接暴露完整 Slurm 参数过长且容易配错，写死默认资源又会隐藏真实申请；薄提交层可以在不把训练逻辑耦合进资源模板的情况下统一参数校验、资源映射和一次命令提交。

Question: 通用提交器是否应理解所选任务脚本的 `SLURM_ARRAY_TASK_ID` 语义，并替特定任务决定是否允许 `--array`？
Decision: 不应。通用提交器只负责把用户显式给出的 `--array` 资源请求传给 Slurm，不检查、不维护白名单，也不针对 `Find_0.sh`、`Find_1.sh` 或 `unet_c1.sh` 增加拒绝逻辑；数组索引如何影响实际命令完全属于所选任务脚本和用户调用的责任。所有新增的 `.sh` 和 `.sbatch` 文件仍加入详细中文注释，解释参数、资源映射、目录职责、执行顺序和安全检查。
Reason: 通用资源提交层不应理解具体训练任务的科学语义；把 Stage1 特例写进提交器会破坏整个文件夹复制到其他项目后直接使用的目标。

Question: 正式训练失败或被人工终止后，应立即释放 GPU、仅保留最小失败重试状态，还是保留现有完整锁体系？
Decision: 保留完整锁体系，包括 `pre_lock`、`try_lock`、`after_lock`、`kill_lock` 和同一 allocation 内的动态再次执行能力。同一个 Slurm Job 一般对应同一个任务，不把已经申请的资源任意改作无关任务。
Reason: 完整锁体系允许在排队获得稀缺 GPU 后控制启动时机、穿透高负载进程实施终止、检查失败并在原 allocation 内重试；任务身份原则上不变，以限制动态执行造成的审计漂移。

Question: 同一个 Slurm Job 内，四锁重试是否只能原样重跑或修复同一任务，还是可以把已经申请到的资源用于任意后续命令？
Decision: 保留四锁最初设计的完整动态能力。Slurm Job 只表示一份已经获得的 CPU/GPU allocation，不作为科学实验、模型或训练运行的唯一身份；获得资源后，用户可以通过动态命令文件依次运行同一任务的重试、其他训练、推理、诊断或其他命令。每次实际执行分别保存自己的 release、launch、最终配置和运行快照，同一 Job 内的不同执行不得互相覆盖。
Reason: 四锁的目的就是把稀缺资源 allocation 与具体命令解耦，使已经排到的卡能够灵活复用。只要把 Job 身份、每次命令执行身份和正式运行身份分开记录，动态复用不会造成 release、launch 或运行目录冲突；辅助运行系统可以保持复杂，项目负责人的主要学习范围仍是从 keep_list 到模型以及推理契约。

Question: 四锁应通过控制命令间接管理，还是继续以共享文件系统中可见的具体文件作为主要控制界面？
Decision: `pre_lock`、`try_lock`、`after_lock` 和 `kill_lock` 必须继续是图形化文件浏览器中可以直接看到、创建或删除的具体文件；动态命令也保留为可见的 `run_cmd` 文件。用户通过文件是否存在直观判断和控制 allocation 状态，不用 `stage1_control.sh start/retry/release` 等命令取代这套文件界面。
Reason: 文件锁是原四锁设计的核心交互方式，能够在共享文件系统和图形化页面中直接显示当前状态；把它包装成命令会隐藏状态并改变用户已经熟悉的操作语义。

Question: 新 allocation 获得资源后，应默认创建 `pre_lock` 等待人工放行，还是默认立即执行并仅在显式请求时创建 `pre_lock`？
Decision: 默认不创建 `pre_lock`，获得资源后立即执行提交时选定的初始动态命令；`submit_task.sh` 提供简单的 `--hold` 参数，只有带此参数提交时才在 allocation 启动后创建可见的 `pre_lock` 并等待用户删除。`try_lock`、`after_lock`、`kill_lock` 和 `run_cmd` 的文件语义不变。
Reason: 常规正式训练应通过一次提交自动开始，同时保留需要先占卡、检查 release、launch、资源和动态命令时的人工启动门。

Question: 正式 release、launch、训练运行和 allocation 状态应放在同步的 Pocket_Plus 仓库内部，还是放在仓库外的持久反馈根目录？
Decision: Pocket_Plus 的新正式反馈产物统一放在 `/home/penghongen/Feedback/Pocket_Plus` 下，不放进 `/home/penghongen/My_Project/Pocket_Plus` 同步仓库。当前三项正在运行的 AdaLigand Stage1 实验继续使用其既有旧目录；新体系不迁移、不覆盖，也不为旧目录增加兼容逻辑。实施完成后的 handoff 必须明确记录旧三项实验的实际产物目录与新体系的区别。
Reason: 代码同步脚本会上传并递归修改 Pocket_Plus 仓库权限，正式 checkpoint、W&B、release、launch 和锁状态不应与代码同步耦合；历史运行保持原位可以避免破坏正在进行的实验，新旧边界通过 handoff 说明即可。

Question: `/home/penghongen/Feedback/Pocket_Plus` 下是否还需要增加 `adaligand` 或 `AdaLigand_Stage1` 总目录？
Decision: 不增加。`/home/penghongen/Feedback/` 下的 `Pocket_Plus`、`Selector`、`Matcher` 是平行的应用目录；Pocket_Plus 自己直接管理 `releases/`、`launches/`、`logs/` 和 `allocations/` 等职责目录。正式训练产物完全沿用 `src/train.py` 已有的 `logs/` 行为，不再发明 `runs/` 层，也不据此引入项目总称。

Question: 正式提交前的 release 应由用户单独准备，还是由 `submit_task.sh` 在一次提交命令内自动创建或复用？
Decision: `submit_task.sh` 默认在调用 `sbatch` 前自动创建或复用当前服务器项目代码的冻结 release，并把确切 release 写入初始 launch 和动态命令；高级用户可以显式指定已有 release，但普通正式提交不需要第二条准备命令。release、launch、内容身份、原子发布和其他复杂实现不得进入三个模型脚本或人类学习主线，应放在主线外的辅助实现目录。
Reason: 一次命令提交可以避免排队期间代码漂移和手工选错 release；辅助机制允许复杂，但主线是否能让用户独立看懂并正确使用是最终验收条件，不能为了实现自动化再次污染训练脚本和阅读路径。

Question: allocation 的可见锁文件、动态命令和日志应如何分层放置，是否允许辅助实现自行增加状态文件？
Decision: `/home/penghongen/Feedback/Pocket_Plus/allocations/` 根目录直接放置 `pre_lock_<job-id>` 和 `try_lock_<job-id>`，便于用户在图形化文件页面中集中查看和操作；`<job-id>/` 子目录内放置 `after_lock_<job-id>`、`kill_lock_<job-id>`、`run_cmd_<job-id>.sh` 以及该 allocation 的标准输出和标准错误日志。不得未经用户允许增加 `last_exit_code` 或笼统的“其他执行记录”；若实现确实需要新增持久文件，必须先说明其必要性并取得用户确认。
Reason: `pre_lock` 和 `try_lock` 是用户最常集中观察和操作的 allocation 控制入口，放在上一层可以减少逐个进入 Job 子目录的成本；其他锁、动态命令和输出日志属于具体 Job 的详细状态，收在 Job 子目录中更清楚。未确认的内部状态文件会扩大用户需要理解和检查的表面，违背本次建立可读运行主线的目的。

Question: `releases/` 与 `launches/` 是否只需在实现中保留，还是必须证明二者职责不同并进入人类可读说明？
Decision: 两个目录必须同时满足三项验收条件：各自保存的事实有明确意义；二者保存内容和生命周期不重复；`训练与运行/README.md` 使用普通文字解释它们分别回答什么问题、何时产生、如何从一次 launch 找到对应 release，以及它们与 `src/train.py` 运行快照的区别。若任一条件不满足，本任务不得以“已完成”收口，需要重新整理实现。
Reason: `release` 应回答“排队和执行使用哪一份冻结代码”，`launch` 应回答“这一次决定以哪些资源、脚本和参数启动什么”；只有目录结构和 README 都能让用户独立识别这一区别，保留两层证据才不是重复工程。

Question: allocation 子目录中的标准输出和标准错误日志是否需要增加跨命令追加分隔、轮转或执行编号等新机制？

Reason: 本次目标是把现有可用的训练运行方式重建为清楚、统一的学习版，不是重新设计日志系统；未经需要验证的新机制只会扩大修改面和用户需要理解的范围。

Question: `/home/penghongen/Feedback/Pocket_Plus` 下四类正式目录分别面向谁，其可读性和行为兼容性应达到什么标准？

Question: 自动创建 release 时，应以服务器实际代码内容、Git 身份还是修改后的代码同步体系作为权威依据？
Decision: 以执行提交命令时 `/home/penghongen/My_Project/Pocket_Plus` 中实际存在的代码内容作为 release 的权威依据；使用内容哈希完成内部审计和已有 release 复用，但哈希不作为用户定位训练、运行产物或锁文件的主要编号。现有代码同步方式不因 release 改变，也不向服务器上传或保留 `.git`。如果同步代码中已有可信的 Git commit、分支或工作区状态来源说明，则把它们作为可选补充写入 release 证据；缺少 Git 身份不得阻止正式训练。README 必须把 release 解释为“排队前冻结的服务器代码”，普通提交不要求用户计算或填写哈希。
Reason: 服务器同步副本会删除 `.git`，实际文件内容才是训练真正能够读取的代码；内容身份可以防止排队期间代码漂移和重复发布，同时把哈希限制在 AI 审计层，避免再次形成用户必须依赖哈希定位运行的复杂主线。

Question: 通用提交文件夹应如何引用自身文件和项目代码，才能复制到其他项目后继续使用？
Decision: `submit_task.sh`、`task.sbatch` 及其辅助实现不得硬编码 Pocket_Plus、Stage1、本机绝对路径或固定安装位置；所有仓库内文件均从脚本自身位置推导，并以相对目录关联。`--sh` 默认相对于同一套 `训练与运行/sh/` 解析，也允许用户显式给出相对任务脚本路径。项目外的反馈根、环境和数据位置由调用参数、环境变量或具体任务脚本提供，不写死在通用提交器中。整个 `训练与运行/` 文件夹复制到其他项目后，只需提供新的任务脚本和外部参数即可复用资源申请、四锁与动态命令能力。
Reason: 通用性必须来自相对位置和清楚的职责边界，而不是在内部维护多个项目名称或绝对路径分支。

Question: 三个 Stage1 学习版脚本应把模型、Dataset 和损失分别展开成可编辑变量，还是以完整 experiment 配置为唯一主体？
Decision: 以完整 experiment 配置为自始至终的主体。每个学习版脚本只清楚选择对应 experiment，并列出该任务相对 experiment 有意施加的覆盖参数；覆盖值必须显式优先于 experiment。模型配置、Dataset 配置和损失权重不另设重复入口，全部由 experiment 提供，只有当前正式基线确实覆盖 experiment 时才作为明确 Hydra override 出现。脚本仍可通过 `--` 接受一次性 Hydra 覆盖，且该覆盖继续拥有最高优先级并进入 launch 证据。
Reason: experiment 应完整定义一次实验；在 shell 中平行维护模型、Dataset 和损失入口会制造两个配置来源，使脚本难读并增加配置漂移风险。

Question: 三个学习版训练的 `logs/` 名称如何在复用和同一 allocation 多次执行时避免碰撞？
Decision: 不改变 `src/train.py` 和 `ExperimentManager` 的现有目录行为。每次 launch 只向现有机制提供一个由任务标识、Slurm Job ID 和启动时间组成的可读唯一 `POCKET_RUN_STAMP`；三个学习版脚本不得继续写死旧 Job 的固定 stamp。checkpoint、W&B、配置、源码快照和日志仍完全由 `src/train.py` 在 `/home/penghongen/Feedback/Pocket_Plus/logs/` 下管理。
Reason: `POCKET_RUN_STAMP` 本来就是现有训练系统提供的跨进程唯一标识入口；按 launch 生成新值可以避免重试覆盖，而不需要发明新的运行目录概念。

Question: `releases/` 和 `launches/` 最少允许保存哪些内部文件？
Decision: 每个 release 最少包含完整冻结的 `Pocket_Plus/` 和一个说明内容身份、创建时间、源位置、排除项及可选 Git 来源的 `manifest.json`。每个 launch 最少包含当次 `run_cmd.sh` 副本、记录 Job、release、任务脚本、资源、时间和已知训练日志路径的 `launch.json`，以及训练实际产出后可关联或复制的 `resolved_config.yaml`；非训练命令没有解析配置不算错误。不建立笼统的“其他记录”目录，新增其他持久文件前必须取得用户确认。README 必须用普通文字解释这些文件如何影响训练行为，而不是要求用户阅读 JSON。
Reason: 这组最小文件足以区分冻结代码、启动决定和训练产物，也能防止 AI 以“方便审计”为理由无限扩大用户无法理解的证据表面。

Question: 三个下载脚本的原始内容是否需要额外复制到新的留档目录？
Decision: 不创建额外留档副本；原始内容通过 Git 实现历史保存，学习版直接使用 `训练与运行/sh/Find_0.sh`、`Find_1.sh` 和 `unet_c1.sh`。实施前必须执行双线 Git 前置检查，只处理本任务文件；若现有移动、删除或未提交修改无法与本任务安全隔离，则停止并向用户展示关系，不擅自提交或整理其他改动。
Reason: Git 已能保存原始脚本历史，再维护一份手工留档会产生重复来源和残留；但不得以此为由吞并用户当前工作区中的其他改动。

Question: 在不申请 GPU、不运行训练 smoke 的前提下，应如何验证通用提交器、三个训练脚本、配置和 release？
Decision: 一次完成 shell 语法检查、可用时的 ShellCheck、使用假 `sbatch` 捕获 CPU/A100/A800/H100/H200/hold/array 等最终提交参数、在临时目录验证 release/launch/四锁且随后清理，以及通过一次性非正式工具组合三份 Hydra 配置并与三个服务器正式 resolved config 做字段级比较。正式脚本不增加无卡模式。服务器端另外创建一份可复用的真实 release，但不提交 Job；验证当前服务器项目代码到该 release 在排除缓存后无差异，并分别展示 Job 321743 的 Find_0 runtime、Job 321540 的 `Pocket_Plus_1909267`、Job 321107 的 `Pocket_Plus_9417bcf` 到新 release 的文件统计和可读 diff，将训练行为差异与路径、注释和运行支撑差异分开说明。
Reason: 静态、提交参数、辅助状态、最终配置和实际代码内容是互补的验证层；全部不需要占用 GPU，同时能回答学习版是否保持三项正式训练科学行为。
