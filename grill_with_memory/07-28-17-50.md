Question 1: 本轮实现是否只负责不依赖 Stage1 推理输出的 AnchorPocketDataset 和对应 Matcher？
Decision: 是。Stage1 推理产物加载系统不在本轮实现，只要求本轮接口为未来接入保留清楚边界。
Reason: 用户希望先完成能够独立训练、推理和测评的正式论文模块。

Question 2: AnchorPocketDataset 中的受体区域是否统一按候选框实际中心截取固定半径球？
Decision: 是。真实配体包络不作为第一版主路径。
Reason: 用户明确赞成固定中心球。

Question 3: 缺失的 4 个 PDB 和 60 个 occurrence 是否通过一次性实验清单处理？
Decision: 是。一次性生成并冻结清单，长期科学代码只读取清单，不包含复杂过滤逻辑。

Question 4: center、bias、context 候选框采样是否必须同时提供类别内部比例或上限，以及每个 PDB 或全数据集的总候选框比例或上限？
Decision: 本题最初设想的“两套独立角色比例/总量开关”已被 Questions 29–34 的 occurrence 级推理模拟规则取代。第一版不再暴露 `center:bias:context` 固定比例、`box_sample_fraction` 或 `max_boxes_per_pdb`：center 完全不进入正式配置；每个真实 occurrence 通过一次互斥的 miss/split/hit 抽样分别产生 0/2/1 个 bias 候选，默认概率为 0.30/0.20/0.50；context 数量从 $0$ 到 $\lfloor2.0N_{\mathrm{occ}}\rfloor$ 离散均匀抽取，并按 Question 32 处理零 A 候选。由这两个 occurrence 级机制共同决定单 PDB 候选总数。Question 37 的 `pdb_sample_fraction` 只选择用于小实验的完整 PDB 子集，不是候选框比例开关。
Reason: 当前目标是模拟 Stage1 对每个 occurrence 的漏检、误 split、合格检测和 PDB 级假阳，而不是复现训练 BOX 来源的固定角色配额。直接使用三个 occurrence 分类概率加一个 context 最大倍率，语义更接近推理且减少配置与采样分支。

Question 5: 第一版收紧范围是否意味着可以阻碍未来加入两阶段冻结训练、更多模态或更复杂结构？
Decision: 否。第一版可以不启用尚未决定的结构，但数据接口、模块边界和训练阶段边界必须允许后续加入；不得提前实现没有决定的通用框架。
Reason: 用户要求控制当前代码量，同时避免未来扩展必须推翻主干。

Question 6: O′ 是否采用归一化有符号距离余量 $1-d/\rho$？
Decision: 否。O′ 采用随候选框中心到 occurrence 质心距离单调下降的倒数函数；Questions 39–41 已将完整定义固定为 $O'=1/(1+d/6\ \mathrm{Å})$，在 $d<24$ Å 时精确监督，在 $d\ge24$ Å 时只约束预测不高于 0.2。O 的二值阈值独立为 12 Å。
Reason: 倒数函数能够平滑压缩距离，同时用户指出模型无法辨别候选框之外的精确距离，因此不能直接监督无限范围的真实距离。

Question 7: O、O′ 和模型可观察范围是否使用彼此独立的尺度，并对可观察范围外的距离使用截尾监督？
Decision: 是。二值标签使用 $O=\mathbb{1}[d<\rho]$；连续函数使用 $q(d)=1/(1+d/s)$，不要求 $s=\rho$ 或 $q(\rho)=0.5$；当 $d\ge d_{\mathrm{obs}}$ 时，只约束预测值不高于 $q(d_{\mathrm{obs}})$，不监督精确距离。
Reason: $\rho$ 表示二值任务边界，$s$ 表示连续分数的衰减速度，$d_{\mathrm{obs}}$ 表示输入允许模型区分的最大距离，三者承担不同职责。

Question 8: O 和 O′ 是否共享候选框—occurrence 配对表示，但使用两个独立输出头且第一版不加入一致性损失？
Decision: 是。O 使用分类头，O′ 使用连续分数头；两者只共享配对表示，不互相推导。第一版仅报告二者阈值判断的一致性指标，不把该指标加入损失。
Reason: 分类目标需要处理类别不平衡，连续目标需要表达距离排序和截尾监督；独立输出头可以避免两种目标的标度与权重互相绑死。

Question 9: O 与 O′ 的一致性指标是否单独实现为易读的指标模块？
Decision: 是。该模块只接收两个输出及其阈值，统计一致和分歧情况；不得混入模型前向、损失计算或匹配解码。
Reason: 用户此前没有使用过这种诊断，希望实现位置和行为可以独立阅读。

Question 10: 第一版是否保留已知 occurrence 数量、可交换 occurrence 槽位和同一配体身份内部的 Hungarian 分配？
Decision: 是。这是 Matcher 的核心语义，不得简化成只预测配体身份级分数。这里的身份内 Hungarian 是训练和带真实标签测评时用于对齐可交换 slot 与真实 occurrence 的监督排列；Question 90 已明确，正式无标签推理不运行需要真实 occurrence 的 Hungarian，而由独立 decoder 消费最终 O/O′ 输出。
Reason: 同一种配体可能在一个 PDB 中出现多次，真实 occurrence 没有可学习的固定顺序；槽位和身份内 Hungarian 分配共同表达数量与排列不变性。

Question 11: 收紧第一版启用范围是否允许过度删减或改写原有 Matcher 计划？
Decision: 否。原计划是用户设计的作品。首轮可以暂不启用尚未敲定的增强结构，但必须逐项保留其设计地位，并用清楚的代码模块边界支持后续加入；只有用户明确决定后才能拒绝或取代原设计。
Reason: 精简用于控制当前复杂度和审查负担，不用于阉割原计划的科学结构与增强路线。

Question 12: 实验密度图是否必须进入本轮不依赖 Stage1 推理输出的 Matcher 实现？
Decision: 是。当前范围必须包含实验密度图。Questions 14–19 与 67–70 已进一步固定：输入是候选中心原生 $48^3$ 单通道实验密度裁剪，经当前裁剪内分位截断和 z-score 后进入完整 `DensityMUNetLite-48-mini`；第一版只由 `MapSummaryHead` 消费四尺度特征并生成 `Map_repr`，不实现 A 调制或 map 派生点对象。

Question 13: 密度编码器是否同时建立 BOX 摘要、A 调制和 PP 构造三个独立消费者？
Decision: 本题原结论已被 Question 17 推翻。`MapBackbone` 仍只负责返回多尺度特征，但第一版唯一消费者是 `MapSummaryHead`；它生成直接参与 Matcher 的 `Map_repr` 摘要。第一版不实现 `MapObjectModulator`，也不实现 `MapPointHead → MapPointBuilder` 或 PP 构造。
Reason: 用户随后指出 $48^3$ map 视野与 $80^3$ A 语义并不完全一致，并决定先以摘要作为稳定入口；完整 decoder 仍保留空间特征，未来加入点对象时无需拆改 backbone。

Question 14: Stage2 的密度编码器输入尺寸是否固定为 $48^3$？
Decision: 是。使用 $48^3$ 代替 selector 当前的 $80^3$ 密度输入，以降低训练显存；Question 15 已确定它是 $80^3$ 合法候选内部的原生中心裁剪，不做覆盖原物理范围的重采样。

Question 15: Stage2 的 $48^3$ 密度输入是否为合法 $80^3$ 候选框内部的原生中心裁剪？
Decision: 是。从 $80^3$ 候选框三轴各去掉两侧 16 个体素，保持实际 `voxel_size_xyz` 和相同物理中心，不执行 $80\to48$ 重采样。

Question 16: Stage2 第一版是否采用 `DensityMUNetLite-48-mini` 作为 map backbone？
Decision: 是。输入为 $48^3$，最低分辨率为 $6^3$，瓶颈起始配置使用 4 heads、1 layer Transformer 和 128 维 FFN；主干不使用 Stage1 RAUNet。Questions 68 与 83 已修订通道语义：`[16,32,48,64]` 只是实现初期可运行的 profile 起点，正式训练宽度必须在完整阶段二真实训练步上实测后由用户写回配置，不能把该列表硬编码为最终宽度。

Question 17: 第一版 map 特征是否用于调制 A 和构造 PP，而不建立 BOX 摘要？
Decision: 否；该决定被用户最新设计取代。MapBackbone 仍只提供空间特征或多尺度特征，但第一优先消费者改为 `MapSummaryHead`。第一版不实现 `MapObjectModulator`，也不实现 `MapPointHead → MapPointBuilder`。
Reason: $48^3$ map 视野与 A 所属的 $80^3$ 候选框语义不完全一致，强行逐原子调制会引入覆盖和坐标边界问题；摘要向量更适合作为第一版的 map 信息入口。

Question 18: 第一版只有 `MapSummaryHead` 消费 map 特征时，是否仍保留并运行完整的紧凑 U-Net 解码路径？
Decision: 是。`MapBackbone` 保持为一个完整且不对外拆分 encoder/decoder 的 `DensityMUNetLite-48-mini`，返回 bottleneck 和多尺度 decoder 特征；当前仅由 `MapSummaryHead` 消费，未来空间点头可以直接复用 decoder 特征。这里的 “48-mini” 是默认配置名而不是在模型内部硬编码尺寸或通道：输入 shape、四级通道、bottleneck heads/layers/FFN/dropout、GroupNorm 组数和 activation-checkpoint 开关均由 Question 68 的显式配置传入。
Reason: bottleneck 适合提供全局抽象信息，decoder 特征保留不同分辨率的空间细节。现在让摘要头消费这些特征，可以避免解码器成为无监督的闲置结构，也避免未来加入新点时再拆分或重构主干。O/O′ 的全局监督不能替代未来点头所需的空间监督。

Question 19: 第一版 `MapSummaryHead` 是否使用四尺度 `mean + max → 分尺度投影 → 拼接 MLP` 汇聚，而暂不使用 learned-query 空间注意力池化？
Decision: 是。分别汇聚 bottleneck $6^3$ 与 decoder $12^3/24^3/48^3$ 特征；每尺度独立归一化和投影，随后拼接并由 MLP 生成单个 `map_summary`。
Reason: 平均池化提供整体分布和稠密梯度，最大池化补充稀疏显著结构；现有 bottleneck 已注入归一化 XYZ 位置编码。该方案开销小、行为易审查，并允许未来只替换独立的 `MapSummaryHead` 来引入带位置的 learned-query attention pooling。

Question 20: 粗分支接收多个候选侧 `_repr` 时，是否同时保留耦合候选表示与模态专属表示，而不在初始化后把所有来源压成一个表示？
Decision: 是。当前正式支持 `coupled_only` 与 `coupled_plus_modal` 两档：前者使用 `CCD_repr + BOX_repr`；后者使用 `CCD_repr + BOX_repr + A_repr + Map_repr`，并以 `coupled_plus_modal` 作为主要建模方案。`A_repr` 由 A 实体 readout 得到，`Map_repr` 直接由 `MapSummaryHead` 产生；二者在生成 `BOX_repr` 后仍作为持久粗表示参与后续层。未来 P、V、PP 各自增加显式 `_repr`。
Reason: 原计划的 2 类与 4 类方案本来就是“耦合表示”和“模态专属表示”并存的对照。`BOX_repr` 承担物理候选整体语义和跨候选竞争，模态专属表示保留来源证据；只做早期融合会不可逆地抹去 A 与 Map 的差异，只保留模态表示又缺少明确的候选级 explaining-away 单元。

Question 21: 多种粗表示在每个 `MatcherBlock` 中如何安排配体—候选侧跨类交互、同类 self-attn 与同候选 BOX 融合？
Decision: 先前把同候选 BOX 枢纽双向协调放进每个 `coarse_layer` 的三步结构被本决定取代。四组持久状态保持各自张量，不展平成统一状态序列；attention 内部可以临时拼接所需 K/V。每个 `MatcherBlock` 按以下顺序执行：

1. 每个 `coarse_layer` 只执行两步。第一步是配体—候选侧跨类交互：`CCD_repr` 查询临时拼接的 `BOX_repr/A_repr/Map_repr`，传入 K/V 类型信息并使用 `split_type_kv=False`；`BOX_repr`、`A_repr`、`Map_repr` 分别查询 `CCD_repr`。第二步是同类集合交互：分别对 `CCD_repr`、`BOX_repr`、`A_repr`、`Map_repr` 执行 self-attn。两个子步骤都从各自输入快照计算残差更新。
2. 完成全部 `coarse_layers` 后，具有未塌缩实体的 `_repr` 执行一次 Block 末尾实体回吸；第一版为 `CCD_repr` 与 `A_repr`。
3. 实体回吸之后，同一候选只执行一次 `BOX_repr_i = BOX_repr_i + TypedAttention(BOX_repr_i, [A_repr_i, Map_repr_i], split_type_kv=False)`。不再执行 `A_repr_i←BOX_repr_i` 或 `Map_repr_i←BOX_repr_i` 的反向枢纽更新。未来加入 P、V、PP 时，把 `P_repr_i/V_repr_i/PP_repr_i` 追加到同一 BOX 查询的 K/V 列表。
4. 随后产生该 Block 的 O/O′ 深监督输出。

`coupled_only` 只运行 CCD–BOX 跨类交互及两者各自的同类 self-attn，不运行没有独立模态表示的 Block 末尾 BOX 融合。Block 末尾 BOX 融合属于粗分支 `_repr` 运算而不是实体回吸，因此阶段一后 $n$ 个 coarse-only Block 即使跳过实体回吸，仍在 coarse loop 后运行该融合。不同候选之间不得直接执行无约束的跨模态 attention；候选侧同类 self-attn 继续使用已确定的候选中心距离 bias。
Reason: A 的未塌缩实体在 Block 末尾回吸后才包含该 Block 最新的图编码信息，因此让 BOX 在回吸之后读取 A/Map 更符合状态顺序。每个 coarse layer 内反复执行同候选双向枢纽会增加计算并持续把混合 BOX 信息写回模态专属状态；改为每个 Block 一次单向 BOX 查询，既保留候选级混合表示，又维持 A/Map 的来源专属性，并自然扩展到未来 P/V/PP。

Question 22: 与未压缩实体的回吸是否在每个 `MatcherBlock` 末尾按类型执行一次，而不是每个内部 `coarse_layer` 都执行或只在整个网络末尾执行？
Decision: 是，但本决定的对象范围被后续实体边界修订。只有拥有对应未塌缩实体的 `_repr` 才在每个 `MatcherBlock` 末尾回吸一次：第一版为 `CCD_repr` 回吸同一 occurrence 槽位的 ligand atom features，`A_repr` 回吸同一候选的 A atom features；未来的 `P_repr`、`V_repr`、`PP_repr` 分别回吸 P 伪原子、Stage1 带特征 blob-mask voxel、Stage2 U-Net 采样点云。`BOX_repr` 是候选受侧的混合粗状态，`Map_repr` 是 U-Net 直接产生的摘要，两者没有对应未塌缩实体，因此均不执行实体回吸。先前关于 `BOX_repr` 回吸 A/Map 的部分作废。
Reason: 每个 `MatcherBlock` 内部多个轻量粗层共享相同实体状态，所以实体支持的 `_repr` 只需在 Block 末尾回吸一次。`BOX_repr` 与 `Map_repr` 仍可通过 coarse layer 的表示间交互持续更新，但为它们虚构实体来源会重复已有融合路径并增加代码复杂度。

Question 23: 两阶段训练是否采用“阶段一先训练前 $m$ 个完整 Block 与后 $n$ 个粗分支外壳，阶段二再为后 $n$ 个 Block 补齐完整组件”的固定策略，并增加 Block 边界 O/O′ 深监督？
Decision: 是。Question 77 进一步确认阶段一与阶段二都属于本轮正式实现范围，而不是只为未来预留结构；Question 84 又明确了细分支的实际施加位置。阶段一前 $m$ 个 Block 注册并训练实体 trunk、粗分支和实体回吸，回吸来源不 detach；后 $n$ 个 Block 只注册并运行粗分支内部的 `_repr` 运算，不注册实体 trunk、实体回吸或细分支。阶段二冻结前 $m$ 个 Block，承接后 $n$ 个 Block 已训练的粗分支内部参数，再为后 $n$ 个 Block 新增实体 trunk 与实体回吸；新增 trunk 送入粗分支前 detach，但由阶段二新增监督训练。Question 89 进一步固定：后 $n$ 个 Block 的实体 trunk 不直接接续第 $m$ 个 Block 的节点、边状态，而由阶段二独立新 stem 从原始节点、边特征重新嵌入；第 $m$ 个 Block 的冻结节点、边状态只可经默认关闭、末层零初始化的 `FiLM_plus` 条件通道分别调制新 stem 状态。正式细分支只在后 $n$ 个 Block 的最终出口运行一次，而不是在四个后段 Block 后重复运行。阶段二最终 O/O′ 预测同时读取粗、细配对信息。`MapBackbone/MapSummaryHead/Map_repr` 始终不进入该 detach 边界。
Reason: 该策略先把完整的 $m+n$ 层粗集合推理训练成形，再在第二阶段补充细粒度容量，避免后 $n$ 个粗层与新增 trunk 同时从随机状态开始。当前不依赖 Stage1 推理产物的数据已经能够提供有意义的粗、细监督，因此没有必要把阶段二降为仅有接口而不可训练的未来占位。实现时阶段二重新构造模型并严格加载权重，不在运行中的模型或 optimizer 上动态注册模块。

Question 24: 粗分支深监督是否只挂在 `MatcherBlock` 边界，并同时监督 O 与 O′？
Decision: 是。阶段一在前 $m$ 个完整 Block 的出口边界以及后 $n$ 个粗分支外壳的出口使用低权重 O/O′ 监督；最后出口为主监督，其余为辅助监督。阶段二关闭冻结前 $m$ 个 Block 的辅助损失，保留后 $n$ 个粗分支的辅助损失。不得在每个内部 `coarse_layer` 后增加损失。Question 84 已进一步决定：Block 5–7 的深监督保持 coarse-only，细分支和 `FinePairAuxiliaryHead` 只在 Block 8 最终出口运行，不增加中间细分支深监督。
Reason: Block 边界会在阶段二成为新增 trunk 与回吸的稳定接口；O 与距离衰减 O′ 都适合粗表示学习。辅助损失总权重必须有固定上限并按深度分配，不能随 Block 数量无限增长。read-only 细分支不更新跨 Block 状态，在中间出口重复运行只增加昂贵的逐对监督而不形成细粒度迭代，因此第一版只保留最终出口。

Question 25: 各个 O/O′ 深监督出口是否独立执行身份内 Hungarian，同时在同一出口内让 O 与 O′ 共用一份联合成本分配？
Decision: 是。每个受监督的 `MatcherBlock` 和最终出口分别进行身份内 Hungarian，不复用最终出口的分配；同一出口使用归一化后的 O 成本与 O′ 成本加权形成一个联合成本矩阵，并把所得排列同时用于两个输出的损失。
Reason: occurrence 槽位在同一配体身份内可交换，中间出口不应被训练早期不稳定的最终分配绑定；但同一出口的 O 与 O′ 必须保持一致的槽位语义。归一化是分别校准两个成本分量的相对尺度后再组合，不是对最终联合矩阵做统一正比例缩放。

Question 26: O/O′ 的 Hungarian 联合成本是否取消额外动态尺度归一化，只按有效候选数量归约并使用固定权重？
Decision: 是。$C_O$ 与 $C_{O'}$ 分别对有效候选取平均，再以固定 `lambda_match_O` 和 `lambda_match_O_prime` 相加；第一版默认权重为 `1:1`。不引入 $s_O/s_{O'}$、逐矩阵 min-max、z-score、EMA 或 batch 自适应尺度。
Reason: O 与 O′ 的目标都位于 $[0,1]$，额外动态校准没有充分必要性，还会使分配规则随 batch 漂移。按 Mask3D 的成熟做法，匹配成本只采用自身自然归约和固定任务权重；若实测一个成本长期压倒另一个，再通过显式固定配置调整。匹配权重与正式训练损失权重必须分开。

Question 27: Hungarian 的 O 与 O′ 具体使用什么无梯度代理成本？
Decision: $C_O$ 使用对有效候选取平均的 sigmoid focal cost 与 Dice cost 的等权平均，其中 focal `gamma=2`；不使用普通 BCE。$C_{O'}$ 对可精确观察候选使用绝对误差，对 $d\ge d_{\mathrm{obs}}$ 的候选使用 $\max(0,\hat O'-q(d_{\mathrm{obs}}))$ 单边截尾绝对误差，并对有效候选取平均。最终按已确认的 `1:1` 组合 $C_O+C_{O'}$。
Reason: O 在全部候选—occurrence 组合中极度稀疏，focal 抑制大量易负样本，Dice 强调稀疏正候选的集合重合；O′ 的匹配成本必须服从与正式监督相同的远距离不可辨识边界。匹配代理成本在 `no_grad` 下计算，不要求与正式训练损失逐字相同。

Question 28: Hungarian 的 O focal 代理成本是否使用 `gamma=2` 且不使用 `alpha` 类别权重？
Decision: 是。采用对称 sigmoid focal cost：正负项只由 `gamma=2` 的难度因子调制，`alpha=None`。
Reason: Hungarian 只决定同身份槽位排列，不承担最终正负校准；Dice 已强化稀疏正候选。额外 alpha 会改变分配并引入敏感超参数。Question 42 后续也已把正式 O 训练损失固定为 `gamma=2, alpha=None`，但匹配代理成本与训练损失仍是参数分别声明的两个模块，不能互相隐式继承。

Question 29: 不依赖 Stage1 推理输出的 `synthetic_anchor` 候选生成中，每个 occurrence 是否只进行一次 `miss/split/hit` 三分类抽样？
Decision: 是。显式配置互斥的 `p_miss`、`p_split`、`p_hit`，并要求三者之和为 1；`miss` 不取 bias，`split` 固定取 2 个 bias，`hit` 固定取 1 个 bias。正式配置完全忽略 center。bias 与 context 均不按距离预先过滤，O 与 O′ 始终由候选框实际中心到各 occurrence 质心的距离派生。Question 30 已把 context 假阳数量固定为 $0$ 到 $\lfloor\text{max_context_ratio}\,N_{\mathrm{occ}}\rfloor$ 的离散均匀抽样，Question 34 的默认倍率为 2.0。
Reason: 三分类一次性表达单个 occurrence 的漏检、错误分裂和正常检测，避免条件 Bernoulli 带来的额外状态组合。候选来源只决定抽样方式，不直接写死监督标签。

Question 30: `synthetic_anchor` 中每个 PDB 的 context 假阳候选数量是否由单个最大倍率和离散均匀分布决定？
Decision: 是。配置非负浮点数 `max_context_ratio`；对含 $N_{\mathrm{occ}}$ 个 occurrence 的 PDB，先计算 $K_{\max}=\lfloor \text{max_context_ratio}\times N_{\mathrm{occ}}\rfloor$，再从整数集合 $\{0,\ldots,K_{\max}\}$ 均匀采样 context 数量。随后从原始 context 池无放回抽取，不做距离过滤；候选池不足时取完现有候选，并在实验清单中记录请求数量与实际数量。
Reason: 该定义只需一个倍率，同时允许合法的零 context PDB，并使假阳负载随 PDB 的 occurrence 数随机变化。`max_context_ratio` 表示上界倍率；平均 context 数约为该上界的一半。

Question 31: bias 与 context 候选构造 A 时，是否使用统一的固定球形受体区域半径？
Decision: 是。两类候选统一使用 `receptor_radius=18 Å`，不针对 context 单独改变受体视野。该半径与 O 的二值正标签阈值 $\rho$、O′ 的连续衰减尺度 $s$ 和可观察距离 $d_{\mathrm{obs}}$ 相互独立。
Reason: 统一半径避免候选来源通过不同受体视野进入模型。context 的完整 $80^3$ BOX 至少含 1000 个受体原子，但以候选中心截取的 18 Å 局部球仍可能为空，因此 Dataset 与模型仍须支持零 A 原子。

Question 32: 以 80% 概率跳过零 A 原子的 context 候选后，是否继续补抽直到达到目标 context 数量或候选池耗尽？
Decision: 是。先按 `max_context_ratio` 得到目标数量 $K$，再用普通随机数生成器随机排列该 PDB 的 context 候选并顺序扫描。18 Å 球内有 A 原子的候选直接接纳；零 A 原子的候选以 20% 概率接纳、80% 概率跳过。跳过项不占用 $K$，继续扫描后续候选，直到接纳 $K$ 个或候选池耗尽；不使用有放回抽样、哈希抽样或复杂资格检验。
Reason: 补抽使 `max_context_ratio` 继续控制最终 context 数量，而 80% 规则只改变空球在 context 中的组成比例。候选池耗尽时直接保留实际接纳数量。

Question 33: 模型是否禁止读取 `synthetic_anchor` 候选的 bias/context 合成来源？
Decision: 是。候选来源只用于 Dataset 抽样、数量审计和分来源指标，不进入 embedding、attention type、打分头或损失权重。候选集合生成后使用普通随机排列，不保留来源分组顺序；模型只读取候选的 A、Map、几何中心及其派生表示。O 与 O′ 仍只由实际距离派生。
Reason: 候选来源若进入模型或顺序，就会形成“bias 通常为真、context 通常为假”的标签捷径，并破坏与未来 Stage1 推理候选接口的兼容性。

Question 34: `synthetic_anchor` 首个正式训练配置使用什么 occurrence 三分类概率和 context 最大倍率？
Decision: 使用 `p_miss=0.30`、`p_split=0.20`、`p_hit=0.50` 和 `max_context_ratio=2.0`。
Reason: 每个 occurrence 的期望 bias 候选数为 $0.50+2\times0.20=0.90$，期望 context 候选数约为 $2.0/2=1.0$，因此总候选数平均约为 $1.9\times N_{\mathrm{occ}}$。该配置是受控合成误差设置，不声明为真实 Stage1 推理误差估计。

Question 35: 第一版 Matcher 是否必须支持单个 PDB 中上千个重复 occurrence？
Decision: 否。第一版建立“常规 multiplicity”实验清单；超过冻结上限的整个 PDB 写入独立 `oversized_count` 清单，本轮不训练且不在 PDB 内静默截断 occurrence。超大计数样本完整保留，供后续 count-compressed 模型或专项压力测评使用。
Reason: 当前早期 slot 展开、slot 索引嵌入、候选—slot 网格和身份内 Hungarian 均以小规模 $N_j$ 为前提。训练集实际最大为每 PDB 1912 个 occurrence，且少数高重复 PDB 集中了大量 occurrence；在 PDB 内截断会改变真实 count，并可能把遗漏 occurrence 附近的候选错误监督为负例。

Question 36: “常规 multiplicity”实验清单的单 PDB slot 上限是多少？
Decision: 使用 `max_slots_per_pdb=100`。按完整 occurrence 数量判断，超过 100 的整个 PDB 进入 `oversized_count` 清单；Dataset 不在运行时截断。叠加已确认缺失候选池的 4 个 PDB、60 个 occurrence 后，正式训练清单包含 12,881 个 PDB 和 180,382 个 occurrence；验证清单包含 188 个 PDB和 2,914 个 occurrence。
Reason: 该上限与原计划 `n_slots≤100` 的显存分析边界一致。在 `p_miss/p_split/p_hit=0.30/0.20/0.50`、`max_context_ratio=2.0` 下，每个 100-slot PDB 平均约有 190 个候选，理论最大为 400 个候选。

Question 37: 第一版是否实现只用于参数实验和消融的小数据集比例开关？
Decision: 是。配置 `pdb_sample_fraction` 和 `subset_seed=3407`；分母是完成缺失项与 `max_slots_per_pdb=100` 处理后的正式 PDB 清单。`pdb_sample_fraction=1.0` 时直接使用完整训练与验证清单，不生成额外子集文件；小于 1.0 时，训练集与验证集分别按 $\lfloor fN_{\mathrm{PDB}}\rfloor$ 无放回选择固定 PDB 子集，并写成可供多次参数实验复用的一次性小数据集清单。
Reason: Matcher 的一个样本是完整 PDB 候选集合，因此比例开关只选择 PDB，不再次截取 occurrence 或 bias/context 候选。正式主实验默认使用 1.0；缩小训练与验证两侧只服务大批参数实验的运行成本。

Question 38: `synthetic_anchor` 的训练候选是否逐 epoch 重新抽取，而验证候选固定一次？
Decision: 是。训练集在每个 epoch 重新抽取 `miss/split/hit`、bias 候选、context 数量、context 候选及最终候选顺序；若该次抽样最终没有任何候选，则按 Question 100 在样本收集边界跳过整个 PDB，后续不再补候选或建立空候选分支。验证候选只生成一次并写入实验清单；其中零候选 PDB 同样在生成验证样本清单时跳过，之后所有验证事件读取同一份非空候选关系。`pdb_sample_fraction` 只决定固定的基础 PDB 子集，不冻结训练 PDB 内的候选集合。恢复训练使用普通整数 seed、epoch 和清单索引复现，不使用 PDB 哈希，也不保存每个 epoch 的候选清单。
Reason: 逐 epoch 重抽使同一 occurrence 能在不同训练周期经历漏检、分裂和正常检测，并复用现有 bias/context 候选池的多样性；固定验证候选保证 checkpoint 和模型方案之间的指标可比较。

Question 39: O 的二值正标签距离阈值是多少？
Decision: 使用 $\rho=12$ Å，即 $O_{i,o}=\mathbb{1}[d_{i,o}<12\ \mathrm{Å}]$。该值不改变 18 Å 的 A 截取半径，也不绑定 O′ 的衰减尺度 $s$ 或可观察距离 $d_{\mathrm{obs}}$。
Reason: bias 到来源 occurrence 的主体距离约为 1–5 Å；12 Å 主要增加邻近 occurrence 和合并情形的正关联。原始候选全组合统计中，bias 正例比例从 $\rho=10$ Å 时约 1.03% 增至 12 Å 时约 1.31%，context 从约 0.083% 增至约 0.142%，增加正监督但仍保持 context 以负例为主。

Question 40: O′ 的连续距离衰减尺度是多少？
Decision: 使用 $s=6$ Å，即 $O'_{i,o}=q(d_{i,o})=1/(1+d_{i,o}/6\ \mathrm{Å})$；不要求 $q(\rho)=0.5$，并继续把可观察距离 $d_{\mathrm{obs}}$ 作为独立参数。
Reason: 该尺度使 $q(0)=1$、bias 主体距离约 2.08 Å 时 $q(d)\approx0.74$、bias 距离约 5.35 Å 时 $q(d)\approx0.53$，而在二值阈值 $\rho=12$ Å 处降至 $1/3$，可以在近距离范围保留较充分的连续区分度。距离只用于构造固定监督目标，反向传播对预测值求导，因此式中的除以 $s$ 不会直接把模型梯度再缩小 $1/s$；$s$ 只决定目标随距离变化的速度。

Question 41: O′ 的精确距离监督在多远处改为单边截尾监督？
Decision: 使用 $d_{\mathrm{obs}}=24$ Å。对 $d<24$ Å 的候选—occurrence 对精确监督 $q(d)$；对 $d\ge24$ Å 的配对只使用 $\max(0,\hat O'-q(24\ \mathrm{Å}))$，其中 $q(24\ \mathrm{Å})=0.2$。O 仍独立按 $\rho=12$ Å 监督，远距离配对继续是明确负例。
Reason: Stage2 实际读取目标约为 1 Å/voxel 的中心 $48^3$ 实验密度裁剪，24 Å 对应该裁剪的方向无关内接球尺度；不应把未输入网络的完整 $80^3$ 候选框当作 O′ 的精确可观察范围。单边截尾允许模型把更远配对统一预测到不高于 0.2，而不要求它区分局部输入之外的精确距离。实际密度裁剪与坐标换算仍必须读取每个样本的 `voxel_size_xyz`，不得用名义 1 Å 替代几何计算。

Question 42: 正式反向传播的 O 损失如何组合 Focal 与 Dice，并如何处理没有任何 O 正标签的 occurrence？
Decision: 使用 $\mathcal L_O=\mathcal L_{\mathrm{focal}}+\mathcal L_{\mathrm{dice}}$，两项固定等权。Focal 使用 `gamma=2`、`alpha=None`，并对全部有效候选—occurrence 配对取平均；Dice 按 occurrence 列计算，只对 $\sum_iO_{i,o}>0$ 的列取平均。全零列只接受 Focal 负例监督，不进入 Dice；若一个 PDB 没有任何含正标签的列，则该 PDB 的 Dice 项定义为零。不得加入动态正类权重或逐 batch 重标定。
Reason: Focal 负责抑制大量容易负例，Dice 为实际存在正候选的 occurrence 提供不会被候选总数轻易稀释的集合重合信号。`synthetic_anchor` 的 `miss` 会有意制造全零列；在这些列上使用 Dice 会使损失主要由平滑常数决定，并重复 Focal 已提供的纯负例监督。

Question 43: `synthetic_anchor` 的 `miss` 是否会从 Matcher 输入中删除对应 occurrence？
Decision: 否。对 Question 100 保留下来的非零候选 PDB，完整真实 occurrence 身份与计数始终构造成全部可交换 occurrence 槽位并输入 Matcher；`miss` 只表示该 occurrence 不贡献来源 bias-box，不删除槽位，也不删除该槽位与现有全部候选之间的 O/O′ 监督。只有整份 PDB 的最终候选数为零时，才在样本收集边界跳过该 PDB，而不是只删除发生 `miss` 的 occurrence。真实 occurrence 坐标与质心只用于构造训练标签，不作为推理输入特征。Question 90 进一步规定，无标签推理时若该 slot 对全部候选的 O 概率都低于固定阈值，decoder 明确返回 `unmatched`，不为了凑满 count 强迫选择假阳候选。
Reason: Matcher 在推理时接收已知的配体身份与真实计数，Stage1 只负责产生空间候选。即使 Stage1 漏掉某个 occurrence，该 occurrence 的查询槽位仍必须尝试解释其他 occurrence 的 bias-box 或 context-box；若没有近邻候选，其 O 列可以全零，但仍由全部现有候选产生 Focal 负例监督和 O′ 距离或截尾监督。

Question 44: 单个 PDB 与单个 batch 的 O/O′ 损失按什么层级归约？
Decision: 把每个 occurrence 当作一个独立损失单元：先在该 occurrence 对应的候选维上取平均，再把同一 PDB 的全部 occurrence 损失求和，因此单 PDB 的影响随 $N_{\mathrm{occ}}$ 呈 $O(N_{\mathrm{occ}})$ 增长。O 的 Focal 和 O′ 的逐元素损失均按此规则归约；O 的 Dice 仍按 occurrence 单独计算，仅对含 O 正标签的 occurrence 加入。一个 optimizer step 内的多个 PDB 损失直接求和。未来 A/B 逐元素损失沿用相同的“候选维平均、occurrence 维求和”规则。原定“每步 PDB 数固定”已被 Question 65 的 occurrence 预算装箱替代：每步 PDB 数可变，通常以 batch 内 occurrence 总数不超过 64 为软上限，单个 occurrence 数超过 64 的 PDB 独立成批。供反向传播的上述加权总和最后按 Question 66 除以配置中的 `occurrence_budget_per_batch`；当前固定除以 64，而不是除以当前 batch 的实际 occurrence 数。
Reason: 该规则保留每个真实 occurrence 的独立训练权重，不会把复杂 PDB 压成与单 occurrence PDB 等权；同时，候选维取平均可以避免 `synthetic_anchor` 每轮随机得到的 bias/context 候选数量直接成为整份 PDB 损失的随机倍率。Question 65 改以 occurrence 数直接控制每步主要配对工作量，比固定 PDB 数更能稳定不同 optimizer step 的规模。固定除以装箱上限只统一优化目标的数值尺度；不按当前实际数量归一化，因此小 batch、满 batch 和超过软上限的单 PDB 中，每个 occurrence 的固定系数保持一致。

Question 45: 正式训练的 O 与 O′ 主损失使用什么初始相对权重？
Decision: 第一版使用固定 `lambda_O=1.0`、`lambda_O_prime=1.0`，即 O:O′ 为 $1:1$。O 内部的 Focal 与 Dice 继续使用已经确认的固定等权。不使用逐 batch 方差、移动平均、梯度大小或不确定性加权等自动校准。正式训练日志按 Question 66 的最新精简规则只记录聚合后的 `loss_total`、`loss_O`、`loss_O_prime` 与 `loss_aux`，不再同时记录 O 内部 Focal/Dice 的未加权副本。
Reason: 第一版需要一个简单、稳定且易审计的基准；O 与 O′ 均已在候选维按 occurrence 单元归约，监督目标也都位于 $[0,1]$。损失权重的调整属于后续参数实验与消融，不应在首版通过动态规则隐式改变。这里的“四个日志量”只限制训练与验证的损失分项；Question 91 另行规定少量正式解码验证指标，不与损失日志混为一类。

Question 46: 两阶段 Matcher 的前段完整 Block 数 $m$ 与后段渐进补全 Block 数 $n$ 使用什么默认值？
Decision: 本项的 $m=2,n=4$ 暂定值已被后续图编码器深度决定取代；当前有效值为 $m=4,n=4$。
Reason: 后续决定让每个完整 `MatcherBlock` 对配体图和 A 图各执行一层 GatedGCN，并使用对称的四层前段与四层后段容量，因此旧值不再有效。

Question 47: 每个 `MatcherBlock` 内部执行多少次 Order B 粗表示迭代？
Decision: 第一版使用 `coarse_layers_per_block=2`。按 Question 21 的最新拓扑，每次内部迭代只执行 CCD 与候选侧表示的跨类交互以及各表示类型的同类 self-attn；同候选 BOX 融合不在该循环内，而在全部内部迭代和实体回吸之后每个 Block 只执行一次。O/O′ 深监督只挂在完成该融合后的 Block 边界。保留 1/2/3 层消融开关。
Reason: 两次内部迭代保留原计划“多次 `for layer in coarse_layers`”的推理结构；一次会把该循环退化成薄包装，三次以上则在缺少实证时增加深度。当前共有 8 个 Block，因此第一版共进行 16 次廉价粗表示迭代，并额外执行 8 次 Block 末尾 BOX 融合。

Question 48: Matcher 的两阶段 Block 数与实体图编码器采用什么第一版默认结构？
Decision: 先前暂定的 $m=2,n=4$ 被本决定取代。第一版使用 $m=4,n=4$，每个完整 `MatcherBlock` 对配体图和受体 A 图各执行一层 GatedGCN，因此阶段一前 4 个完整 Block 与阶段二后 4 个新增完整 Block 分别提供四层实体图传播；8 个 Block 各含 2 次 Order B，共执行 16 次粗表示迭代。配体与 A 使用相同的 GatedGCN 数据契约、层类和计算式，但按 Question 75 固定使用两个参数独立的编码栈；不提供共享权重开关。Question 52 已进一步收紧范围：PairFormer 只保留为未来设计选项，第一版不实现 `PairFormerAdapter`、后端注册表或任何未使用的配置分支。

GatedGCN 按 Question 76 一次性迁移 PocketXMol `BondFFN + NodeBlock + EdgeBlock` 的节点—边特征计算内核：节点使用边条件门控消息与 `scatter_sum`，动态边还会分别汇总两端相邻边的信息。第一版的配体图和 A 图坐标、拓扑与 31 维基础边特征固定，不执行坐标更新，不引入扩散时间；配体与 A 之间不建立依赖未知配体姿态的空间跨边，跨实体交互仍由 Matcher 的 `_repr` 与注意力完成。Stage3 将复用同一计算内核并另行增加坐标更新模块，但不预设与 Stage2 共享权重。
Reason: 四层是当前首版基线而非已实证最优值，并保留 2/3/4 层消融。$m=n=4$ 让两个阶段的新实体编码容量对称，也使完整 Block 数直接对应图传播深度。稀疏 GatedGCN 比对最多 100 个 occurrence 槽位逐一运行 PairFormer 更节省显存；迁移完整节点—边特征内核可以避免 Stage3 再次重写主干，而把 Stage2 不需要的坐标更新能力留在独立模块边界之外。

Question 49: 同一 CCD 身份的配体 GatedGCN 是否按 occurrence slot 重复计算？
Decision: 否。每个 `MatcherBlock` 对每种唯一 CCD 身份只计算一次配体节点与边状态，随后按真实 count 展开成 $N_j$ 个 slot，并在第一次候选交互之前注入 `slot_index_embedding` 与 count embedding。各 slot 的 `CCD_repr`、实体回吸、候选交互、打分和身份内 Hungarian 全部独立；细分支需要逐原子 query 时，在共享身份原子状态上广播加入对应 slot embedding。A 图仍按候选分别编码。
Reason: slot 必须在任何匹配交互之前分化，但相同身份的化学图计算与不可学习的 occurrence 编号无关。按身份编码一次、随后早期展开同时满足方案 1 的 slot 语义和“共享身份原子特征”的效率承诺，避免把同一 GatedGCN 对重复身份无意义地运行多次。

Question 50: 第一版 GatedGCN 是否在层间更新并传递边特征？
Decision: 是；本决定取代上一项中“不在层间动态更新边状态”的部分，并由 Question 76 把边更新明确为 PocketXMol `EdgeBlock` 的完整计算。每层同时接收并返回 `(node_features, edge_features)`，默认 `update_edge=True`。`NodeBlock` 将当前边状态与来源邻居节点状态分别投影后逐通道相乘，再用由当前边与邻居节点共同产生的 sigmoid 门调制消息，按目标节点执行 `scatter_sum`，加入目标节点自身投影并经 LayerNorm、激活和输出投影产生节点增量。`EdgeBlock` 对每条有向边保留当前边自身投影和两个端点投影，同时通过两个参数独立的 `BondFFN` 分别计算左右端的“边状态 × 端点节点状态”门控消息；这些消息先在对应端点汇总，再取回该边两端的汇总结果，形成一次线图式边—边传播。节点增量与边增量从同一层输入快照计算，再分别残差写回；第一版坐标和图拓扑固定，不引入扩散时间。`update_edge=False` 只作为消融开关。

实现布局保持直接：在一个图网络模块中放置迁移并适配后的 `BondFFN`、`NodeBlock`、`EdgeBlock`，再由一个很薄的 `NodeEdgeLayer` 完成一次节点与边同步更新。不得直接复用把多层更新包在内部循环中的 PocketXMol `NodeEdgeNet`，因为每个 `MatcherBlock` 必须在单层图更新之后插入 `_repr` 读出、粗分支和实体回吸。配体图与 A 图使用两个独立参数栈；唯一 CCD 编码与 slot 展开由单独的 `IdentitySlotExpander` 边界完成，不把身份去重、slot 广播、图更新和 Matcher 粗交互混入同一函数。
Reason: 多层门控消息传递中，完整 `EdgeBlock` 让边状态吸收两端局部边环境，避免四层都使用同一份初始门控依据。节点和边从同一快照更新可以保持层语义清楚；迁移逐层计算内核而不是整个 `NodeEdgeNet`，既保留 PocketXMol 的有效结构，也满足 Matcher 的逐 Block 交错运算与代码可读性。

Question 51: 配体图与受体 A 图的第一版固定拓扑如何构造？
Decision: 本决定已由 Question 74 统一修订。配体图与受体 A 图不再采用“配体仅化学键、A 为化学键加 radius”的两套建图哲学，而是共同使用 $E=E_{\mathrm{chemical}}\cup E_{\mathrm{radius}}$。无向化学键始终展开为两个有向消息边；radius 邻接使用 4 Å 截断、每个目标节点最多 48 个邻居并排除 self-loop。radius 只在同一图且同一 `geometry_group` 中构造：普通单组件配体全部原子同组，BRANCHED 配体按 `residue_id` 分组，候选 A 图内的真实受体原子全部同组。化学键允许跨组并始终保留；同一有向原子对的化学与 radius 关系合并成一条边。图拓扑在全部 GatedGCN 层间固定，动态边状态逐层更新。

两侧使用同一个 31 维原始边契约：5 维 `bond_order`（single、double、triple、dative、aromatic）、3 维 `bond_role`（backbone、disulfide、covalent-connection）、4 维环尺寸标记、`is_chemical`、`is_radius`、`distance_valid` 三个标量，以及 16 维距离 Gaussian RBF。受体的 backbone/disulfide/covale 均映射为 single bond order 并打开对应 role；radius-only 边的化学字段全零。当前受体没有可靠的四类环尺寸字段，因此对应四维为零。距离只对共享有效坐标系的端点计算：A、普通配体和 BRANCHED 组件内边设 `distance_valid=1`；BRANCHED 跨组件化学键设 `distance_valid=0` 且 RBF 全零。两侧均不输入绝对坐标或方向向量，原始边特征经配置化无偏置线性投影形成 64 维初始边状态。
Reason: 配体与 A 应共享同一个原子图数据和算子契约；在配体参考构象上加入稀疏局部 radius 边，可以吸收 Emap2lig 的内部几何先验而不恢复稠密 PairFormer。BRANCHED 的各 CCD 组件只有各自独立的 `ref_pos`，不能伪造跨组件距离；`geometry_group` 与 `distance_valid` 让同一套建图代码明确表达这一事实。统一边字段和合并规则减少两套实现的漂移，同时保持 $O(E)$ 稀疏计算、刚体不变性和简单可审查的代码。

Question 52: 第一版实体状态、边状态和粗表示分别使用多大隐藏维度，是否同时实现 PairFormer 后端？
Decision: 使用 `node_dim=128`、`edge_dim=64`、`repr_dim=256`。配体原子与 A 原子使用 128 维，动态图边状态使用 64 维；当前 `CCD_repr`、`BOX_repr`、`A_repr`、`Map_repr` 以及未来的 `P_repr`、`V_repr`、`PP_repr` 统一使用 256 维。粗分支 TypedAttention 使用 8 个 head、每 head 32 维；`MapSummaryHead` 直接输出 256 维。实体回吸与读出模块内部负责实体特征到 256 维的投影，调用侧不散布维度适配。

第一版代码只实现 GatedGCN 配体编码器，不实现 PairFormer、`PairFormerAdapter`、编码后端注册表或未使用的后端配置分支。长期模块只保留明确的配体图编码输入输出契约；未来确实实施 PairFormer 实验时再增加对应实现。
Reason: 大量 A 节点和图边使用 128/64 维可以明显降低激活与边状态显存，而数量较少的 `_repr` 保留 256 维容量。128/64 也与原计划所参考 PairFormer 的原子/原子对宽度自然兼容，但未来兼容不构成首版提前实现未使用后端框架的理由。

Question 53: 零 A 原子的候选如何生成并维持 `A_repr`？
Decision: 不向空 A 图伪造 dummy atom、dummy edge 或 self-loop。GatedGCN 与 ragged batch 正式允许某个候选的节点段长度为 0；`AReadout` 对非空图正常生成 256 维 `A_repr`，对空图直接返回一个可学习的 256 维 `empty_A_repr`。后续 Block 的 A 实体回吸在空图上产生零增量，使 learned-null 状态继续参与候选侧跨类交互、A 同类 self-attn、Block 末尾 BOX 对 A/Map 的单向融合以及候选竞争。不另加 `a_is_empty` 输入特征，O/O′ 标签与损失也不因 A 为空而改变。
Reason: 空 A 是候选局部输入的一种真实状态。learned-null 能让模型识别该状态，同时避免伪原子参与图消息或让全零向量与普通数值状态混淆；额外空标志会重复表达相同事实。

Question 54: `BOX_repr` 初始如何从 `A_repr` 与 `Map_repr` 构造，四类粗表示如何共同进入 `coupled_plus_modal` 档？
Decision: 使用 $\mathrm{BOX\_repr}^{(0)}=\operatorname{LayerNorm}(\operatorname{MLP}([\mathrm{A\_repr}^{(0)}\Vert\mathrm{Map\_repr}^{(0)}]))$。这里的“拼接”只指在特征维拼接同一候选的 `A_repr` 与 `Map_repr`，再经 MLP 产生该候选的 `BOX_repr`。不额外增加 learned BOX token，也不向该初始化加入候选来源、候选序号或绝对中心坐标；空 A 候选自然使用 `empty_A_repr`。生成 `BOX_repr` 后，`CCD_repr`、`BOX_repr`、`A_repr`、`Map_repr` 仍是四组独立状态，并按已经确认的 Order B 分别运算；不得把候选侧三组表示展平为 `[3N_candidate, 256]` 的统一 token 序列，也不为该路线增加 type embedding。`coupled_only` 只运行 `CCD_repr` 与 `BOX_repr`，`coupled_plus_modal` 额外运行独立的 `A_repr` 与 `Map_repr`。
Reason: `BOX_repr` 需要从初始化开始承担 A 与实验密度图的耦合候选语义，而模态专属状态又不能因此消失。两个模态向量用特征拼接和 MLP 完成耦合已经足够；把三种候选表示展开为统一 token 集合会改变此前已经确定的粗层运算结构，并引入没有必要的类型编码和索引管理。

Question 55: 第一版 coarse layer 的哪些 attention 使用候选间相对几何 bias？
Decision: 只在候选侧三类跨候选同类 self-attn——`BOX_repr↔BOX_repr`、`A_repr↔A_repr`、`Map_repr↔Map_repr`——加入由实际候选中心距离产生的 attention-logit bias。几何输入使用候选中心间距离的 RBF 编码，不输入绝对中心或方向向量，不用距离阈值屏蔽远端候选。`CCD_repr` self-attn 不使用空间 bias；CCD 与候选侧表示的 cross-attn 也不使用空间 bias，因为 CCD 没有密度图空间位置；Block 末尾同候选 BOX 查询 A/Map 的融合也不需要候选间几何 bias。本决定不改变四组独立状态及 Question 21 的最新 Block 顺序。
Reason: 候选侧同类集合推理需要识别相邻重复框、误 split 和远隔候选，候选中心距离提供平移、旋转与候选排列不变的几何依据。其余 attention 的两端不存在两份可比较的候选位置，强行加入该 bias 没有明确几何语义。

Question 56: `CCD_repr` 与 `A_repr` 的初始实体读出和后续 Block 末尾回吸采用什么结构？
Decision: 初始摘要保留原计划的单 learned-query attention readout。配体与 A 使用结构相同、参数独立的读出模块：一个 256 维 learned query 通过 8-head attention 读取投影到 256 维的 128 维节点状态，再经 LayerNorm/FFN 残差得到摘要；不增加多 query 或 SetTransformer。唯一 CCD 身份先读出一次 `CCD_identity_repr`，再按真实 count 展开 occurrence 槽位并加入 slot/count embedding。非空 A 正常读出，空 A 绕过 attention 并返回 `empty_A_repr`。初始读出后，`CCD_repr` 与 `A_repr` 成为持久残差状态；每个 Block 末尾不再用固定 learned query 重新初始化，而由当前 `_repr` 作为 query 回吸对应实体节点，再经 LayerNorm/FFN 残差更新。不同 occurrence 槽位以各自当前 `CCD_repr` 查询同一份身份原子状态，因此能够逐层分化。
Reason: 固定 learned query 适合从可变长度实体生成稳定的初始单向量摘要；后续若反复用固定 query 重建摘要，会抹掉 coarse layer 已经写入的槽位与候选交互状态。让持久 `_repr` 自己查询实体，可以保留历史并按当前匹配上下文选择需要回吸的节点信息。

Question 57: 哪些 `_repr` 拥有未塌缩实体并执行回吸，哪些实体在每个完整 `MatcherBlock` 中继续编码？
Decision: occurrence、A、P、V、PP 都是有未塌缩实体的对象，分别对应配体原子图、受体原子集合、Stage1 伪原子集合、Stage1 预测的带特征 blob-mask voxel 集合、Stage2 U-Net 自行采样的点云；它们分别产生 `CCD_repr`、`A_repr`、`P_repr`、`V_repr`、`PP_repr`，并允许当前持久表示在 Block 末尾查询各自实体。只有配体原子图与 A 原子图在每个完整 `MatcherBlock` 中运行 GatedGCN，持续更新节点与边状态。P、V、PP 自身已经携带特征；未来加入时只在表示前导做必要的小型投影或融合，例如融合 P 的多尺度特征，随后实体特征保持只读，而对应 `_repr` 仍可通过 coarse layer 及实体回吸演化。`BOX_repr` 与 `Map_repr` 没有对应未塌缩实体，不执行回吸，但继续参与粗表示运算。第一版尚不实现 P、V、PP，实际实体编码与回吸对象只有 occurrence 和 A。
Reason: 回吸应当有明确的一一对应实体语义。把昂贵的逐 Block 特征编码限制在配体和 A，可以控制实现与显存复杂度；P、V、PP 已有上游或本阶段生成的特征，固定实体加状态相关回吸足以保留未来扩展能力。`BOX_repr` 和 `Map_repr` 属于摘要或混合状态，为其增加伪实体回吸会重复已有表示交互。

Question 58: 每个 O/O′ 深监督出口如何从粗状态构造共享的候选—occurrence 配对表示？
Decision: 保留原计划的双方向粗匹配码。对每个候选 $i$ 与 occurrence 槽位 $o$，occurrence 方向由 `CCD_repr[o]` 查询候选 $i$ 的未塌缩 A 原子特征，得到 `recall_A[i,o]`；候选方向由 `BOX_repr[i]`、`A_repr[i]`、`Map_repr[i]` 分别查询 occurrence $o$ 的配体原子特征，得到 `precision_BOX[i,o]`、`precision_A[i,o]`、`precision_Map[i,o]`。`coupled_plus_modal` 把这四项按固定顺序拼接并送入 `PairCodeMLP`，形成 O 与 O′ 共享的 `pair_repr[i,o]`；随后使用彼此独立的线性头和 sigmoid 产生 $\hat O$ 与 $\hat O'$。`coupled_only` 只拼接 `recall_A` 与 `precision_BOX`，并构造与该配置输入维度匹配的 `PairCodeMLP`。

空 A 候选的 `recall_A` 定义为零码，避免对全 masked K/V 做 softmax；`precision_A` 仍由 learned `empty_A_repr` 查询配体原子。BOX 与 Map 没有未塌缩实体，因此不虚构其 occurrence→实体方向的 recall 码。未来加入 P/V/PP 后，每种有实体来源都增加 `CCD_repr→entity features` 的 recall 码，每种持久 `_repr` 都增加 `_repr→ligand atom features` 的 precision 码，并按配置声明的稳定顺序拼接。Question 85 已修订细分支融合位置：正式细分支不在 `PairCodeMLP` 前追加原子码，而是先独立得到 256 维 `fine_pair_repr`，再经零初始化 `fine_adapter` 作为残差加入 `coarse_pair_repr`。O/O′ 继续共享最终联合 `pair_repr`，但不共享末端输出头。
Reason: 双方向码保留原计划中“配体解释候选证据”和“候选解释配体原子”的不对称信息，同时使 Map/BOX 等无未塌缩实体的摘要仍能通过 precision 方向参与打分。rep×实体 attention 的 query 只有单向量，成本远低于逐原子×逐原子的细分支，并可直接用于所有 Block 边界深监督。

Question 59: 各 `MatcherBlock` 的 O/O′ 深监督出口是否共享同一套粗配对码构造与预测头参数？
Decision: 不共享；每个受监督的 `MatcherBlock` 使用参数独立的完整 `CoarsePredictionHead`。独立范围包括双方向码所需的 `CoarsePairCodeBuilder` attention 投影、`PairCodeMLP`、`OHead` 与 `OPrimeHead`，而不只是最后两层线性输出。底层 `TypedAttention` 使用同一个类实现，但各 Head 实例持有自己的参数。代码只定义一次 `CoarsePredictionHead`，再用 `nn.ModuleList` 为 8 个 Block 各实例化一次；不得复制 8 份前向代码，也不为第一版增加共享/独立双模式开关。每个出口继续独立执行 Hungarian 与损失计算。阶段二保留并严格加载全部 Head 参数；前 4 个冻结 Block 的 Head 同步冻结且不计算辅助输出，后 4 个 Head 承接阶段一权重并继续训练，最终推理使用第 8 个 Block 的 Head。
Reason: 独立 Head 允许不同深度的状态分布分别校准。通过单类加 `ModuleList` 实现，预计相对共享方案只增加约 10–20 行模块组织代码，远低于用户举例的 300 行显著增量；代价主要是模型参数与优化器状态，而不是代码复杂度。

Question 60: 8 个 `MatcherBlock` 出口的 O/O′ 深监督损失权重如何分配？
Decision: 最后一个当前有效出口作为主监督，出口权重固定为 1.0；其余当前有效出口共同分享固定 coarse 深监督总权重 `coarse_deep_total_weight=0.5`。辅助出口按其在当前有效辅助序列中的深度顺序 $k=1,\ldots,K$ 线性递增并归一化，即 $w_k=0.5\,k/\sum_{j=1}^{K}j$。阶段一 Block 1–7 按比例 $1:2:3:4:5:6:7$ 分享 0.5，Block 8 为 1.0；阶段二关闭前 4 个冻结出口，Block 5–7 按比例 $1:2:3$ 重新分享 0.5，Block 8 仍为 1.0。每个出口先形成 $\mathcal L_{\mathrm{head}}=\mathcal L_O+\mathcal L_{O'}$，其中 O 与 O′ 延续已决定的 1:1 权重，再乘出口权重。配置只暴露 `coarse_deep_total_weight=0.5` 与 `coarse_deep_schedule=linear_depth`，不手写八个数值。

Question 88 已修订日志归属：上述所有 coarse 出口的 O 损失只聚合进 `loss_O`，O′ 损失只聚合进 `loss_O_prime`；它们不再重复记入 `loss_aux`。正式训练不记录逐 Block 的 O、O′、Focal、Dice 或加权前后副本。
Reason: 辅助监督总量固定后不会因 Block 数增减而改变整体损失尺度；随深度线性增加使较成熟的中后层承担更多直接监督，同时仍给早期层提供梯度。阶段二按当前有效出口重新归一化，可保持辅助总权重恒定。

Question 61: 独立 `CoarsePredictionHead` 内部的 `PairCodeMLP`、O 输出头和 O′ 输出头采用什么结构与初始化？
Decision: `coupled_plus_modal` 将四个 256 维双方向粗码按固定顺序拼接成 1024 维输入，`coupled_only` 将两个粗码拼接成 512 维输入。`PairCodeMLP` 先对完整拼接维做 LayerNorm，再线性投影到 `pair_repr_dim=256`；随后执行一个 pre-norm 残差 FFN：`LayerNorm(256) → Linear(256,512) → SiLU → Linear(512,256) → Dropout(0.1)`，并把结果加回 256 维主路径。不使用 BatchNorm、额外 attention 或更深 MLP。`OHead` 由 256→1 线性层直接输出 `O_logit`，正式损失内部处理 sigmoid；`OPrimeHead` 由 256→1 线性层输出 `O_prime_logit`，再经 sigmoid 得到 `O_prime`。O 头使用 `O_initial_prior=0.01`，即偏置初始化为 $\operatorname{logit}(0.01)\approx-4.595$；O′ 头使用 `O_prime_initial_value=0.2`，即偏置初始化为 $\operatorname{logit}(0.2)\approx-1.386$。两个末端线性层权重使用 `Normal(0,0.01)`，不做全零初始化；第一版不依据逐批统计自动改变先验。
Reason: 单次投影加一个残差 FFN 已能在控制八套独立 Head 参数量的同时融合双方向码。O 的 1% 初始先验符合当前候选—occurrence 矩阵的稀疏正例量级；O′ 从截尾边界 0.2 开始，使远于 $d_{\mathrm{obs}}=24$ Å 的配对初始不产生大规模单边惩罚，而近距离精确监督可以把对应预测向上拉。小方差而非全零末端权重允许首步梯度进入 `pair_repr`。

Question 62: `MapBackbone` 是否沿候选轴分批运行，以及这是否等同于原计划的 Matcher“分 chunk 计算”？
Decision: `MapBackbone` 沿候选轴支持普通 micro-batch 前向，第一版配置默认 `map_candidate_chunk_size=64`，适配 A800 80 GB；模型和执行代码不得硬编码 64。该参数允许在显存实测后继续调大，设为 `null` 时一次处理当前 batch 的全部候选。实现先把同一训练 batch 内所有候选的中心 $48^3$ 密度裁剪展平为候选列表，再按配置上限调用同一套 `MapBackbone + MapSummaryHead`，拼接全部 256 维 `Map_repr` 后按候选归属还原，随后才运行完整 PDB 级 Matcher。各小批次保留正常 autograd 图，所有 PDB 的总损失只执行一次 backward；不得逐小批次反向、不得把它实现为梯度累积，也不得在语义上拆分 PDB、候选集合注意力、Hungarian 或损失。A800 80 GB 的第一版配置默认关闭该路径的 activation checkpoint；只在实测显存需要时通过独立开关启用，不做运行时自动调参。必须明确：在单次 backward 且未启用 checkpoint 时，各 micro-batch 为反向传播保存的激活仍会累计到 backward 前；候选分批主要约束单次卷积调用的临时张量与算子工作区，并不构成严格的训练激活显存上限。若 profile 显示保存激活才是瓶颈，应优先打开这一路径的 activation checkpoint，而不是误以为继续减小 micro-batch 就一定能按比例降低总显存。正式实现必须提供与训练逻辑分离的显存 profile 脚本，使 `map_candidate_chunk_size` 与 Question 68 的 U-Net 参数可以通过同一配置覆盖后实测。

这里的候选轴 micro-batch 不属于原计划的正式 Matcher“分 chunk 计算”。正式方案拆分的是 `[n_candidates,n_occurrences]` 配对网格的逐对计算阶段，需要让所有 chunk 共享只计算一次的实体主干与完整粗分支状态，并正确汇总共享状态的梯度后再向主干回传；它涉及 detach/leaf、共享计算图和多次局部 backward 的正确性契约。两者必须使用不同名称、配置和测试，不能因为实现了 `map_candidate_chunk_size` 就宣称正式 Matcher 分块能力已经完成。
Reason: 候选密度裁剪在生成 `Map_repr` 以前彼此独立，因此候选轴 micro-batch 只是约十余行量级的执行封装，不改变数学结果，也不要求复杂的梯度接力。默认 8 个候选对 A800 80 GB 过于保守；64 更符合当前硬件和 $48^3$ 轻量 U-Net 的规模，同时保留继续调大的显式旋钮。它在不开 checkpoint 时主要控制单次算子的峰值临时开销，而不是消除全部已保存激活。原计划的配对网格分块则跨越共享实体状态、逐对运算和损失回传，其复杂度与正确性风险都不能被这个局部执行优化掩盖。

Question 63: 第一版只监督 O/O′ 的 Matcher 是否暂不实现原计划的正式候选—occurrence 配对网格分块训练？
Decision: 本题原来的“暂不实现”结论已被 Question 77 与 Question 87 共同推翻。当前版本在本轮实现正式细分支，因此也实现 `[n_candidates,n_occurrences]` 配对网格分块。具体采用 Question 87 的“逐 chunk activation checkpoint、完整矩阵 Hungarian、单次总 backward”，不采用旧计划中的 detach-leaf 梯度接力、共享状态 `.grad` 手工汇总、多次局部 backward、`retain_graph` 管理或分块专用训练器。

Question 62 的 `map_candidate_chunk_size=64` 只拆候选密度 U-Net 调用；Question 87 的 `fine_pair_chunk_size=2048` 拆候选—occurrence 细配对网格。两者使用不同配置、函数和测试，不得混称。全局实体与粗状态编码只计算一次，完整候选集合推理与身份内 Hungarian 仍观察全部候选和 occurrence；细 chunk 只改变逐对只读计算的执行批量。
Reason: 正式细分支引入了候选×occurrence×原子的主要显存负担，但 PyTorch activation checkpoint 可以在一个普通 chunk 循环内重算细分支并自动把梯度汇入共享实体状态，无需实现原计划最复杂的手工梯度接力。这样既完成正式分块能力，也保留全局匹配语义和单次 backward 的易审查训练流程。

Question 64: 多 PDB batch 是否采用“独立编码器打包计算、Matcher 按 PDB 显式循环”的混合组织？
Decision: 是。`AnchorPocketDataset` 的单个样本始终是一份完整 PDB，不在 Dataset 或 `collate_fn` 中拆分其候选与 occurrence。`collate_fn` 返回字段明确的 `MatcherBatch`：把 batch 内全部候选的 $48^3$ 密度裁剪沿候选轴拼接；把配体图和 A 图分别拼成互不连边的稀疏图；使用少量名称直观的 `pdb_ptr`、`candidate_ptr`、`identity_ptr`、`occurrence_ptr` 等边界索引恢复归属。`MapBackbone` 按 Question 62 的候选 micro-batch 运行；GatedGCN 可对互不连边的图统一执行。相关模块不得使用会跨样本聚合统计量的 BatchNorm，因此这种打包不产生 PDB 间信息交换。

独立编码完成后，模型用一个短而显式的 PDB 循环取回该 PDB 的候选、CCD 身份、occurrence 槽位与实体状态，并分别运行全部粗分支注意力、`CoarsePredictionHead`、身份内 Hungarian 和损失。不同 PDB 不进入同一组集合注意力，不使用巨型 block-diagonal attention mask 模拟隔离，也不把候选数、occurrence 数或原子数补齐到整个 batch 的最大长度。一个 optimizer step 的各 PDB 损失继续按 Question 44 直接求和。

简洁易读是这一组织的核心验收指标。第一版不得为上述打包建立通用 ragged-tensor 框架、抽象分段执行引擎或多层批调度器；只实现当前字段所需的小型 `MatcherBatch` 数据类和直接的 pack/split 辅助函数。PDB 循环、归属边界及“不跨 PDB”的断言必须在主前向流程中清楚可见，而不是隐藏在难追踪的通用容器内。
Reason: 密度 U-Net 与互不连边的图编码器可以通过打包获得足够 GPU 工作量，而集合注意力和匹配按 PDB 循环最直接地保证语义隔离。它避免全 batch padding 浪费和复杂掩码泄漏风险；同时用少量显式索引代替通用变长框架，符合本项目把简洁、易读和可人工审查作为核心质量指标的要求。

Question 65: 第一版训练 batch 是否按 occurrence 数量预算进行简单的顺序贪心装箱？
Decision: 是。使用配置 `occurrence_budget_per_batch=64`。每个 epoch 先用普通随机生成器打乱基础 PDB 样本索引，并按 Question 38/100 完成该 epoch 的轻量候选抽样与零候选过滤；顺序装箱只接收保留下来的非零候选样本。随后按打乱后的相对顺序从前到后装箱：当前 batch 为空时加入下一个 PDB；只要加入下一个 PDB 后 occurrence 总数仍不超过 64，就继续加入；若会超过 64，则先产出当前 batch，再由该 PDB 开始下一个 batch。occurrence 数恰为 64 的 PDB 可以填满一个 batch；occurrence 数大于 64、但仍满足 `max_slots_per_pdb=100` 的 PDB 不拆分，直接独立成为一个超过软预算的 batch。最后一个未满 batch 仍正常产出，不丢弃已经保留的样本。

装箱只读取正式实验清单中固定的真实 occurrence 数，不读取每个 epoch 随机产生的候选数、A 原子数或密度图内容。第一版不增加候选/原子加权工作量、排序分桶、最佳适配装箱、动态显存探测、特殊超大样本队列或梯度累积。验证集使用相同的顺序贪心规则，但按固定验证清单顺序装箱，从而保持 batch 划分可复现。`occurrence_budget_per_batch=64` 是面向 A800 80 GB 的首个默认值，后续 profile 可以直接修改这个普通配置项。

该决定取代 Question 44 中原先的“每个 optimizer step 固定 PDB 数”。PDB 数现在随各样本 occurrence 数变化，而单个 PDB 始终完整保留，Matcher 仍按 Question 64 严格逐 PDB 隔离计算。
Reason: occurrence 数直接决定槽位数量，并近似线性决定候选—occurrence 配对工作量；当前 synthetic-anchor 设置下候选数的期望也随 occurrence 数近似线性增长。用一个 occurrence 软预算即可比固定 PDB 数更稳定地利用 A800 80 GB，同时只需一个短小、可人工验证的顺序循环。允许超过 64 的单 PDB 独立成批可避免破坏完整 PDB 语义或重新引入样本切分。

Question 66: occurrence 预算装箱下，反向传播的总损失使用什么归一化分母，正式训练记录哪些损失值？
Decision: 把一个 optimizer step 内按既定层级和深监督权重求得的损失总和，除以配置中的“预期装箱上限” `occurrence_budget_per_batch`；当前默认分母为 64。分母不使用当前 batch 的实际 occurrence 数：未装满的 batch 仍除以 64，单个超过 64 occurrence 的 PDB 独立成批时也仍除以 64。这样每个 occurrence 在最终求和中的固定系数都是 $1/64$，复杂 PDB 的总影响继续随 occurrence 数呈 $O(N_{\mathrm{occ}})$ 增长。

正式损失日志保持简洁，只记录四个已经使用相同固定分母缩放、且满足直接相加关系的聚合标量：`loss_total`、`loss_O`、`loss_O_prime` 和 `loss_aux`。`loss_O` 聚合最终出口与所有有效 coarse 深监督出口的加权 O 损失；`loss_O_prime` 同理聚合 O′；`loss_aux` 只聚合 Question 88 的加权 `loss_entity_aux` 与 `loss_fine_pair_aux`，不重复包含 coarse O/O′ 深监督。因此固定满足 `loss_total = loss_O + loss_O_prime + loss_aux`。不再额外记录原始未缩放总和、逐 Block 损失、逐 Block Focal/Dice 或新增辅助头内部子项；计算正确性由单元测试直接检查。Question 91 的 precision、recall、F1 与阈值属于独立的验证解码指标，不受“四个损失标量”限制。
Reason: 若除以当前实际 occurrence 数，16-occurrence batch 中单个 occurrence 的系数为 $1/16$，而 64-occurrence batch 中为 $1/64$，前者在一次更新中的权重是后者四倍；固定除以装箱上限则保持逐 occurrence 系数一致。对 AdamW 而言，固定缩放通常会使一阶矩和二阶矩同步缩放，归一化后的数据梯度更新近似不变；但 `eps`、梯度裁剪、混合精度以及解耦权重衰减与数据梯度的相对尺度意味着它并非严格数学恒等。这里采用固定分母主要为了稳定、可解释的数值尺度，而不是作为优化超参数。精简日志足以观察 O、O′、辅助监督与总目标，避免八个出口和多个损失分项造成无必要的记录膨胀。

Question 67: Matcher 的中心 $48^3$ 实验密度输入采用什么归一化规则？
Decision: 复用 Pocket_Plus 现有密度通道构造语义，但以 Matcher 实际可见的中心 $48^3$ 裁剪作为归一化范围。Dataset 先从每个候选对应的原始 experimental-density 完整图直接裁出同中心 $48^3$ 原始密度，再对该裁剪执行单通道 `exp_clipnorm_nopost`：按当前裁剪自身的 `[0.001,0.999]` 分位数截断极端值，对截断结果计算均值和标准差，输出 $(x-\mu)/(\sigma+10^{-8})$ 的 float32 `[1,48,48,48]` 张量。不得先对 $80^3$ BOX 归一化后再取中心 $48^3$，也不得用完整 PDB 的全图统计量归一化局部输入。

第一版 `MapBackbone` 只接收这一条 experimental-density 通道，不拼接 simulated density、exp–sim 差值、正差值、Gaussian/DoG/smooth 后处理通道、受体占据 mask 或监督标签。训练、验证以及未来接入 Stage1 推理候选时必须调用同一个明确的 Matcher 密度预处理函数和同一配置，不在不同 Dataset/入口复制公式。配置只暴露 `density_clip_percentile=[0.001,0.999]`；`exp`、`clipnorm` 与 `nopost` 是当前固定输入契约，不展开成未使用的 56 通道组合选择器。
Reason: Pocket_Plus 现有 Selector 已验证“先裁当前 BOX、再对裁剪执行 `exp_clipnorm_nopost`”的数据流。Matcher 实际只观察中心 $48^3$，因此应让截断、均值和标准差都由这份可见输入决定；若先归一化 $80^3$ 再裁剪，中心体素的数值会依赖模型看不到的外围 16-voxel 区域。单 experimental-density 通道保持本轮任务边界与代码清晰，也避免 simulated density 或标签派生通道引入训练—推理不一致。

Question 68: `DensityMUNetLite-48-mini` 是否沿用现有 Selector U-Net 的运算骨架，同时把尺寸、通道与 bottleneck 参数全部保留为显式可调配置？
Decision: 是。结构为单通道 $48^3$ 输入，经四级 encoder 得到 $48^3/24^3/12^3/6^3$ 特征，再经一层 bottleneck Transformer 和对称 decoder 恢复 $12^3/24^3/48^3$ 特征。`[16,32,48,64]` 只作为实现初期保证可运行的起始 profile 通道配置，不再视为可以未经显存实测直接提交正式训练的最终默认宽度。每尺度使用一个现有式 pre-activation `ResidualConvBlock3d`：`GroupNorm → SiLU → 3×3×3 Conv → GroupNorm → SiLU → 3×3×3 Conv + residual`；下采样使用 `kernel=2,stride=2` 的 `Conv3d`，上采样使用同参数的 `ConvTranspose3d` 并与同尺度 encoder 特征按通道拼接。bottleneck 起始配置为 4 heads、1 layer、FFN 128、dropout 0.1，沿用归一化 XYZ 经线性层生成的位置编码。第一版不加入 SE、attention gate、额外卷积层、分割头或 U-Net 内部深监督。

上述数值全部由配置提供，不得散落硬编码在模型前向或各子模块中。`MapBackbone` 构造函数显式接收 `input_channels`、`input_shape_zyx`、`channels`、`norm_groups`、`bottleneck_heads`、`bottleneck_layers`、`bottleneck_ffn_dim` 和 `dropout`；实现初期 profile 配置分别为 `1`、`[48,48,48]`、`[16,32,48,64]`、`8`、`4`、`1`、`128`、`0.1`。第一版仍固定为四个尺度，不为了可调通道额外实现任意深度 U-Net 生成器或 backbone 注册框架。构造时直接校验输入三轴可被 8 整除、四级通道都能被 `norm_groups` 整除、bottleneck 通道能被 head 数整除；错误配置立即失败，不静默改组数或宽度。

对外返回字段明确的 `MapFeatures`：`bottleneck`、`decoder_quarter`、`decoder_half`、`decoder_full`。字段按相对分辨率而非默认的 6/12/24/48 绝对尺寸命名，调整 `input_shape_zyx` 时无需改代码；张量通道数从 `channels` 读取，`MapSummaryHead` 也按配置构造各尺度投影，不把 `[16,32,48,64]` 复制为另一套常量。`map_candidate_chunk_size=64` 与 `map_activation_checkpoint=false` 同样只存在于配置。正式实现另提供独立显存 profile 脚本，允许覆盖这些 U-Net 参数和候选 chunk 大小后测量实际占用；正式模型内部不做自动探测或自动改参。

正式训练开始前必须固定 `occurrence_budget_per_batch=64` 与 `map_candidate_chunk_size=64`，在包含完整阶段二细分支、全部启用损失、反向传播和 AdamW step 的真实配置上逐次加宽 `channels`，使 A800 80 GB 得到较充分利用。实现初期 `[16,32,48,64]` 只作为搜索起点；profile 后选中的通道列表必须写入正式实验配置和运行记录，不能仍以体感偏小的起始值直接启动长训练。具体显存余量由用户按 Question 83 在每次验收命令中显式指定，不能固化在模型或 profile 脚本中。
Reason: 现有 Selector 的残差卷积、GroupNorm、对称 skip decoder 与最低分辨率 Transformer已经是清楚、可读的可靠骨架。把通道宽度留在配置中，可以在完整 Matcher 的实际显存占用明确后把剩余容量用于 Map 表示，而不必修改模型代码；限制为四尺度和一个直接构造类，则避免“可调”扩张成难读的通用网络工厂。

Question 69: 独立显存 profile 工具采用什么使用接口、测量过程和 OOM 记录契约？
Decision: 实现一个与正式模型和训练循环分离的可复用运维入口 `ops/profile_matcher_memory.py`。它复用正式 Matcher 配置、`AnchorPocketDataset`、occurrence 装箱、collate、模型、损失、混合精度与 AdamW 构造，不维护第二套伪训练实现。用户接口必须保持简单：接受一份与训练相同的配置，并允许用现有配置覆盖语法修改 `occurrence_budget_per_batch`、`map_candidate_chunk_size`、`fine_pair_chunk_size`、两条路径各自的 activation checkpoint、U-Net `channels`、bottleneck 参数、数值精度和要读取的真实 batch；另提供名称直接的 `--memory-limit-gib`，由用户在每次需要显存验收时显式填写，不在代码中预设 72 GiB 或其他硬阈值。省略该参数时脚本只测量并记录，不自行判定显存是否满足用户预算。`--help` 和项目运行说明必须给出一条可直接复制的标准测量命令与一条带显存上限的验收命令；参数只使用人能直接理解的通道列表、GiB、batch/PDB 选择和现有配置项，用户不需要阅读脚本源码，也不需要填写底层张量 shape。

一次运行只测一个明确配置和一个真实装箱 batch，不在脚本内部实现自动搜索、自动改参、组合 sweep 或显存自适应。脚本先执行一个包含 forward、loss、backward 和 `optimizer.step()` 的预热训练步，使 CUDA kernel 与 AdamW 一阶/二阶状态真实物化；预热成功后清零 CUDA 峰值统计并同步设备，再测量一个完整训练步。批量比较由用户重复命令或 Hydra multirun 完成。

该脚本同时承担正式训练前的 U-Net 宽度验收。首轮以 `occurrence_budget_per_batch=64`、`map_candidate_chunk_size=64` 和实现初期 `[16,32,48,64]` 通道启动，随后由用户显式覆盖 `channels` 并显式指定本次 `--memory-limit-gib`，重复运行后选出充分利用 A800 80 GB、同时满足用户本次显存余量要求的最大通过配置。脚本本身仍不自动搜索、不内置目标显存、不替用户改写正式配置；选定值由人明确写回实验配置与运行记录。

每次运行无论成功还是 CUDA OOM，都必须在本次运行输出目录写入一份小型 `memory_profile.json`。成功结果至少记录 `status="ok"`、GPU 名称、数值精度、关键可调配置、实际 PDB/occurrence/candidate/A-atom 数、`max_memory_allocated_gib`、`max_memory_reserved_gib` 和完整训练步耗时。脚本在预热前也重置一次峰值统计；若预热或正式测量抛出 `torch.cuda.OutOfMemoryError`，捕获该异常并记录 `status="oom"`、`oom_stage`、失败前可取得的 allocated/reserved 峰值、实际 batch 规模和配置，完成必要 CUDA 清理后以非零退出码结束。不得把其他异常捕获并写成 OOM；配置、数据或实现错误必须保留原始 traceback。控制台只打印与 JSON 对齐的一份简短结果摘要，不生成 CUDA memory snapshot 或冗长逐层日志。
Reason: 真实完整训练步才能覆盖 Map、图编码、Matcher、梯度和 AdamW 状态的总显存；只测 forward 或合成 U-Net 张量会低估正式占用。单配置、同训练入口和一个小 JSON 让脚本可以直接由人使用及横向比较，又不会形成第二套难维护的训练系统。把 OOM 作为结构化结果保存，可以在不同 U-Net 宽度、chunk 和 checkpoint 组合失败时仍留下可审计证据。

Question 70: `MapSummaryHead` 如何从四个可调通道的 Map 多尺度特征生成 256 维 `Map_repr`？
Decision: 对 `MapFeatures` 的四个字段按固定语义顺序 `bottleneck → decoder_quarter → decoder_half → decoder_full` 分别执行相同结构的尺度汇聚。对某尺度 `[B,C,D,H,W]` 特征同时沿三个空间维计算 mean 与 max，得到两个 `[B,C]` 向量；在特征维拼接成 `[B,2C]`，再执行 `LayerNorm(2C) → Linear(2C,scale_summary_dim) → SiLU`。四个尺度使用参数独立的投影模块，由一个直接的 `nn.ModuleList` 按上述固定顺序组织。

把四个 `scale_summary_dim` 向量拼接后，执行 `LayerNorm(4S) → Linear(4S,summary_hidden_dim) → SiLU → Dropout → Linear(summary_hidden_dim,repr_dim) → LayerNorm(repr_dim)`，输出单个候选的 `Map_repr`。默认配置为 `scale_summary_dim=64`、`summary_hidden_dim=512`、`repr_dim=256`、`dropout=0.1`；这些均为显式配置参数。四尺度输入通道直接由 `MapBackbone.channels` 按 `[bottleneck,decoder_quarter,decoder_half,decoder_full]=[c3,c2,c1,c0]` 派生，不在 SummaryHead 复制默认 `[16,32,48,64]`。构造时校验恰有四级通道以及所有正整数维度。

第一版不加入空间 attention、learned-query pooling、额外残差 FFN、坐标统计或多摘要 token。实现保持为一个尺度投影 `ModuleList` 和一个最终 MLP；mean/max 的次序、尺度次序及拼接次序都在前向函数中直接可见。
Reason: mean 提供整体密度分布与稠密梯度，max 保留局部显著响应；每尺度独立投影可以吸收不同通道宽度，最终 MLP 再完成跨尺度融合。该结构对 U-Net 通道修改自然兼容，同时比空间注意力汇聚更省显存、更容易阅读和测试。

Question 71: 第一版配体 GatedGCN 的节点输入是否直接复用 Emap2lig 的完整原子特征血统？
Decision: 是。第一版不再采用先前建议的“只输入 element、charge、chirality、in_ring”精简集合，而是直接复用 Emap2lig `LigandModelingDataset._process_features()` 的 149 维 `atom_feature` 契约：4 维 `atoms.name` 字符整数编码、128 维元素原子序数 one-hot、1 维形式电荷、7 维手性 one-hot、4 维 3/4/5/6 元环标记、1 维 `residue_id`，以及由元素原子序数查表得到的 `element_is_metal`、`covalent_r`、`vdw_r`、`atom_weight` 四个标量。该 149 维向量在每套阶段专属实体 stem 内都由一个直接的无偏置线性投影初始化为 `node_dim=128`，不再为各字段分别建立复杂 embedding 分支；Question 89 规定阶段一与阶段二的投影参数彼此独立，但二者读取完全相同的 149 维原始字段。

“完整原子特征”严格指 Emap2lig 实际送入模型的上述 149 维输入，而不是把 `LigandObject` 的所有落盘字段不加区分地喂入网络。`coords` 与 `is_present` 不进入 Emap2lig 的 `atom_feature`，在 Matcher 中也不作为配体身份输入；可读字符串 `atom_names` 与 `atoms.name` 信息重复，不另建第二份编码；`object_key` 只用于身份去重和索引，绝不作为数值特征。`ref_pos` 仍作为独立参考构象几何，而不拼入节点向量。Emap2lig 的 5 维键型和 4 维环标记被无损映射进 Question 74 的统一 31 维边契约；配体与 A 再共同使用该契约的 radius 来源标记、距离有效性和 16 维 RBF，最后投影为 64 维初始边状态。
Reason: 本项目的 `LigandObject` 本来就沿用 Emap2lig/AF3/Boltz 的配体输入血统，现有字段与 Emap2lig 源码逐项对齐；直接复用 149 维原子向量和 9 维化学键向量最安心，也减少重新发明特征契约和遗漏支化配体组件信息的风险。149→128 与化学键特征→64 的单次线性投影相对于后续八个 Matcher Block 的计算和显存开销很小。保留 Emap2lig 实际的字段边界还能避免把真实姿态占位字段或身份主键误当成输入。

Question 72: 是否同时复制 Emap2lig 对 `ref_pos` 构造的稠密全原子对几何表示？
Decision: 否，但 Question 74 已修订其中“配体不建立任何非键 radius 边”的旧表述。Question 71 复用 Emap2lig 的完整 149 维节点输入与基础化学键语义，但不复制其为 PairFormer 构造的完整 $N_{\mathrm{atom}}\times N_{\mathrm{atom}}$ pair 张量。第一版配体 GatedGCN 会与 A 图共用稀疏的 4 Å radius 建图：普通配体在完整参考构象内建立，BRANCHED 只在同一 `residue_id` 组件的有效参考坐标系内建立；真实化学键始终保留。只输入旋转和平移不变的距离 RBF，不把原始 `ref_pos` 坐标拼入节点，也不加入有方向的 `ref_pos_i-ref_pos_j`。

该决定不否认 Emap2lig 的实现事实：其 `ConformerEmbedder` 会对所有有效原子对加入相对坐标向量、$1/(1+\lVert r_i-r_j\rVert^2)$ 距离特征、pair mask 和两端节点投影；但这些运算服务于稠密 PairFormer。若未来正式实现 PairFormer 配体编码消融，则在该独立后端内恢复对应的全 pair 契约，不修改第一版统一的稀疏 GatedGCN 图契约。
Reason: 稀疏 radius 邻接可以在 $O(E)$ 开销内保留局部参考构象近邻，并使配体/A 两侧建图同构；它不等同于 Emap2lig 的稠密 pair 表示。以 `geometry_group` 限定半径边并对跨组件键显式标记距离无效，避免把 BRANCHED 各自独立的 CCD 坐标误当成联合构象。

Question 73: 第一版 A 原子的初始节点输入是否直接使用现有 49 维 `A_feat_L0`，并如何兼容未来 Stage1 字段？
Decision: 当前无 Stage1 推理产物版本只使用按 `A_global_index` 从该 PDB 唯一 `receptor_tokens.npz` 无损恢复的 `feat[N,49]`。这 49 维依次为元素 one-hot 6、残基 one-hot 25、残基理化标记 8、归一化原子质量 1，以及在完整受体上计算的 0–18 Å 九个邻居壳层 `log1p` 计数。当前不重复拼接已经在 49 维中表达的 `element` 或 `res_type`；`atom_name` 与 `is_backbone` 保留为辅助监督和审计字段，`res_index` 与 `chain_index` 只用于恢复化学关系，世界坐标只用于图几何；这些字段均不直接进入第一版 O/O′ 的 A 节点向量。Stage1 binding probability 或 Stage1 学习特征也不在当前默认输入中。

模型代码不得写死输入一定为 49 维。Dataset/特征装配层按配置中的有序来源列表构造一个连续的 `a_node_input[N,F_A]`；当前列表仅为 `a_node_feature_sources=[feat_l0]`。阶段一与阶段二实体 stem 内各有一个参数独立的 A 输入适配器；二者都只接收同一份已经拼好的张量，并使用配置显式传入的 `a_node_input_dim` 通过 `LinearNoBias(F_A,node_dim)` 投影到 128 维，启动和每批前向均校验实际末维与配置一致。近期增加“纳入 Stage1 推理产物”的长期并行训练版本时，只新增明确命名的来源读取与拼接，例如在配置列表中追加 `stage1_binding_probability` 或某个已冻结契约的 Stage1 A 特征，并相应改变 `a_node_input_dim`；不修改 GatedGCN、A readout、Matcher Block 或损失。

该扩展边界必须保持短小：只允许一个按显式列表依次取张量、检查原子数一致并 `torch.cat` 的 `AFeatureAssembler`，不建立通用特征插件注册表、自动扫描文件、动态字段反射、缺失字段静默补零或未启用来源的空参数分支。当前版本和 Stage1 版本分别使用清楚的实验配置与清单，共享同一模型实现。
Reason: `A_feat_L0` 是现有数据流水线和 BOX 契约已经冻结的可追溯受体基础表，足以作为当前正式版本的简单起点。把可变输入宽度隔离在“显式装配 → 单次投影”边界，可以长期并行训练基础版与 Stage1 增强版而不重写主干；同时避免现在为尚未冻结的 Stage1 字段搭建难读的通用框架。

Question 74: 配体与 A 是否使用统一的原子图建图、边合并和边特征契约？
Decision: 是。本决定取代 Question 51 的两套拓扑和 Question 72 中“配体不使用非键 radius 边”的部分。配体与 A 共用一个职责直接的 `build_molecular_graph()`：输入节点坐标、只用于几何有效性分组的 `geometry_group`、化学键及其属性；输出共同的有向 `edge_index`、31 维原始边特征和固定图拓扑。两侧都构造化学键与 4 Å radius 邻接的并集，每个目标节点最多 48 个 radius 邻居、排除 self-loop，并按有向端点合并重合边。

普通单组件配体的全部 `ref_pos` 属于一个 `geometry_group`；BRANCHED 配体按 `residue_id` 分组，因为各 CCD 组件的参考坐标只是独立拼接，并不处于可靠的联合构象；A 候选中的真实受体坐标全部处于同一个组。radius 边只允许连接同一图、同一组的节点。跨组真实化学键继续双向保留，但设 `distance_valid=0`、距离 RBF 全零；所有共享有效坐标系的边设 `distance_valid=1` 并计算距离 RBF。`geometry_group` 自身不作为模型输入。

共同的 31 维边字段固定为：`bond_order[5]`（single、double、triple、dative、aromatic）、`bond_role[3]`（backbone、disulfide、covalent-connection）、`ring_size[4]`、`is_chemical`、`is_radius`、`distance_valid` 和 `distance_rbf[16]`。配体原有 5 类键型与 4 类环标记直接映射；受体 single/double/triple/aromatic 直接映射，backbone/disulfide/covale 映射为 single 并打开对应 role。radius-only 边的化学字段全零；受体当前没有可靠的四类环尺寸字段，因此对应四维为零。两侧不输入绝对坐标或方向向量。31 维输入经配置化无偏置线性层投影到 64 维动态边状态；图结构固定，后续 GatedGCN 层继续按 Question 50 同步更新节点和边状态。

配体 149 维与 A 当前 49 维原始节点字段仍由每套阶段专属实体 stem 内各自短小的输入适配器投影到共同的 128 维 `GraphState.node`；原始字段不同不破坏图契约同构。阶段一与阶段二共用同一份原始节点张量、原始 31 维边张量和固定 `edge_index`，但使用参数独立的节点、边输入投影。适配后两侧共同使用 `GraphState(node[128],edge[64],edge_index)` 和 Question 76 定义的同一个 `NodeEdgeLayer` 实现，但按 Question 75 固定使用两个参数独立的编码栈。
Reason: 同一个图编码器应建立在同一个图数据和边语义契约上；仅因配体使用参考构象而完全删除其局部几何边，会造成没有必要的两套处理。稀疏、分组受限的 radius 图保留局部构象先验而不恢复 $N^2$ PairFormer；`distance_valid` 则诚实表达 BRANCHED 跨组件参考几何缺失。一个建图器、一个边装配器和一个图状态接口既统一建模，也符合代码简洁、可读和未来可扩展的要求。

Question 75: 配体图与 A 图的 GatedGCN 是否共享可学习参数？
Decision: 不共享，而且第一版不提供共享权重开关。两侧共用 Question 74 的建图器、31 维边语义、`GraphState` 接口、Question 76 的 `NodeEdgeLayer` 类和完全相同的计算式，但每个完整 `MatcherBlock` 明确持有参数独立的 `ligand_gnn_layer` 与 `receptor_gnn_layer`；同一阶段内的配体/A 节点输入投影、31→64 边输入投影、逐层 `NodeBlock`/`EdgeBlock` 更新和相应归一化参数均不共享。Question 89 又规定阶段一与阶段二的实体 stem 也不共享节点、边输入投影。实现不增加 shared/independent 分支、逐层共享选择、部分权重共享、模态门控或共享专用 checkpoint 转换。
Reason: 图契约同构不等于两个输入域相同。配体是较小、按身份复用并使用参考构象的化学图；A 是候选特异、规模更大并使用真实坐标的受体环境图，原始节点特征和图规模分布也明显不同。固定参数独立允许两侧分别适应其任务角色，额外参数与代码量都很小；删除不会使用的共享开关更符合简洁易读的核心要求。

Question 76: 是否一次性迁移 PocketXMol 的 `BondFFN + NodeBlock + EdgeBlock` 完整计算内核，包括两端相邻边聚合，并把 Stage2 与 Stage3 的坐标更新能力留在独立边界？
Decision: 是。本决定取代本题最初提出的“只保留端点条件边更新、不迁移 PocketXMol 完整 `EdgeBlock`”建议。当前 Matcher 一次性迁移并适配 PocketXMol 的节点—边特征计算内核：保留 `BondFFN` 中边状态与端点节点状态的逐通道乘法及 sigmoid 门控，保留 `NodeBlock` 的边条件邻居消息、目标节点 `scatter_sum`、自身投影、LayerNorm、激活和输出投影，也完整保留 `EdgeBlock` 在一条有向边左右两端分别汇总相邻边消息、再加入两端节点投影和当前边自身投影的边—边传播。节点增量与边增量继续从同一个层输入快照计算，再分别残差写回。

“一次性迁移”只指迁移可复用的图网络计算内核，不是原封不动复制 PocketXMol 整个 `models/graph.py` 或多层 `NodeEdgeNet`。实现只引入 `BondFFN`、`NodeBlock`、`EdgeBlock` 和一个很薄的 `NodeEdgeLayer`；不得把无关的 `NodeEncoder`、带边注意力的 `BondBlock`、`PosPredictor`、`RigidNet`、`TorsionNet` 等结构带入 Matcher。项目继续使用 Question 74 的统一建图器、31 维原始边特征和 `GraphState`，并由每个 `MatcherBlock` 各自组合一层图更新、粗表示计算和实体回吸，而不是把四层图更新封装进不可插入 Matcher 运算的内部循环。

Stage2 不编写、不注册也不运行 PocketXMol `PosUpdate`；配体参考坐标与 A 真实坐标只用于建立固定拓扑和静态距离特征，不在 Matcher 中更新，也不引入扩散时间。Stage3 将复用同一节点—边特征内核，再单独增加坐标更新模块；代码复用不意味着 Stage2 与 Stage3 必须共享权重。PocketXMol `PosUpdate` 与当前 Stage3 计划中的 Emap2lig `AtomDiffusion` 究竟互相替代、串联还是分担不同职责，留到 Stage3 设计时单独决定，在此之前不得默认同时启用两个坐标更新器。迁移上游 MIT 代码时保留必要的版权与许可证说明。
Reason: 完整迁移节点—边特征内核可以让 Stage2 立即获得动态边和局部边环境传播，并让 Stage3 以后只增加坐标更新能力而不重写图主干。只迁移逐层计算内核则保留了 Matcher 在每个图层之后插入 `_repr` 读出、粗分支和实体回吸的必要结构，也避免把与当前任务无关的生成、刚体和扭转模块变成未使用代码。

Question 77: 当前 Matcher 是否在本轮同时实现阶段一与阶段二、正式细分支以及相应辅助监督，而 Dataset 仍只实现不依赖 Stage1 推理输出的版本？
Decision: 是。本轮同时实现完整的 Matcher 训练阶段一和阶段二。阶段一继续按 Question 23 训练前 4 个完整 `MatcherBlock` 与后 4 个 coarse-only Block；阶段二冻结前 4 个 Block，并为后 4 个 Block 补齐配体/A 实体更新和实体回吸。Question 89 进一步规定这些后段实体更新从阶段二独立新 stem 的原始重嵌状态开始，不把冻结 Block 4 的节点、边状态当作唯一或默认输入；Block 4 状态只可通过默认关闭的零初始化 `FiLM_plus` 条件通道分别调制新 stem 的节点、边状态。Question 84 修订了本题中“为后 4 个 Block 补齐正式细分支”容易造成的歧义：后四个 Block 都补齐实体主干，但双向只读细分支只在 Block 8 的最终出口运行一次。阶段二最终 O/O′ 预测头同时读取粗配对信息与细分支产生的配对信息，使细分支获得主任务梯度。

本轮同时规划两个职责独立的轻量辅助模块：`EntityAuxiliaryHead` 直接监督未塌缩的配体与 A 图状态，为阶段二新增的实体 trunk 提供梯度；`FinePairAuxiliaryHead` 直接监督候选框—真实 occurrence 的细配对状态，为细粒度注意力和 readout 提供局部梯度。Question 88 已把两套“显式开关 + 权重”简化为唯一权重开关：对应 `*_weight>0` 时构造并计算，等于 0 时不构造、不读取专用标签，因此允许只启用其中一个或同时启用两个。实现必须共享简单的损失返回与汇总接口，不建立通用任务注册器或复杂插件系统。辅助目标只能使用当前已处理数据能够稳定提供的字段与由真实 occurrence 几何直接计算的标签，不得为了启用辅助头要求新增外部数据资源。

`AnchorPocketDataset` 的本轮范围保持不变：只实现 synthetic-anchor、完全不读取 Stage1 推理产物的正式版本。未来长期并行训练的 Stage1 增强版本通过清楚的候选来源与可选字段适配边界接入，但本轮不实现其读取、解析或采样逻辑。
Reason: 细分支本身可以收敛为少量双向注意力、readout 和预测头；新增代码的主要部分来自阶段切换、辅助标签与损失闭环，而不是另造一套模型。现有配体、A、真实 occurrence 和合成候选已经足以支持有意义的实体保持监督与细配对监督，因此现在完成两阶段闭环比留下难以续接的占位结构更合适。借鉴 Emap2lig 的重点是把简单辅助预测头直接挂在未塌缩实体或配对状态上，而不是照搬与当前数据不匹配的全部预测目标。

Question 78: 第一版正式细分支是否沿用原计划的“双向、只读配对”拓扑？
Decision: 是。对于同一 PDB 内的每个候选框 $i$ 与真实 occurrence 槽位 $o$，细分支从同一份未塌缩实体状态快照并行计算两个方向：

\[
H^L_{i,o}=L_o+\operatorname{CrossAttn}(L_o,A_i),
\qquad
H^A_{i,o}=A_i+\operatorname{CrossAttn}(A_i,L_o).
\]

第一条路径由该 occurrence 的配体原子查询候选框的 A 原子，产生 128 维 `fine_recall_atoms`；第二条路径由 A 原子查询配体原子，产生 128 维 `fine_precision_atoms`。两个方向不串行读取对方的更新结果，也不把配对特异的原子状态写回共享配体图或 A 图。两条路径各使用一个参数独立的轻量 `LearnedQueryReadout`：先在 128 维完成单查询池化，再把已经塌缩原子轴的摘要投影为 512 维 `recall_repr` 与 `precision_repr`；随后按固定顺序拼接成 1024 维并经 `FinePairCodeMLP` 投影为 256 维 `fine_pair_repr`。两个 readout 不共享参数，因为 recall 与 precision 的查询侧、集合规模和语义不同，而独立参数不会明显增加代码复杂度。具体 attention、可选 FFN 和读出 MLP 由 Question 86 固定。

阶段二最终 O/O′ 预测同时读取粗配对表示与 `fine_pair_repr`。`FinePairAuxiliaryHead` 可以在 readout 以前直接读取 `fine_recall_atoms` 或 `fine_precision_atoms`，从而为原子级注意力提供直接监督。当前实验配置只传入 A，但实现可以在不明显增加嵌套和代码量的前提下抽出一个“配体 token 集合 ↔ 单个受侧 token 集合”的平坦双向配对原语；当前 `FinePairBranch` 调用该原语一次，未来 P、V、PP 只需按稳定顺序增加同类调用并拼接各自读出码。不得为此建立插件注册系统、运行时类型发现、递归容器或多层通用调度框架。

本题固定的是数学拓扑，不要求一次性物化完整的候选×occurrence×原子中间张量。Questions 63 与 87 已固定执行方式：细配对网格按 `fine_pair_chunk_size=2048` 逐块运行 activation checkpoint，拼接完整配对矩阵后统一执行 Hungarian，并只做一次总 backward；不使用手工 detach-leaf 梯度接力。
Reason: 双向路径分别保留原计划中的覆盖召回与候选精确性语义，并让细粒度证据通过一个固定维度的配对表示进入主任务。只读设计避免某个候选—occurrence 配对污染其他配对共享的实体状态；从同一快照并行计算也比串行双向更新更容易理解、测试和分块。

Question 79: `FinePairAuxiliaryHead` 是否使用由真实 occurrence 与候选 A 的 4 Å 原子接触关系得到的双向边缘标签？
Decision: 是。对于候选 $i$、真实 occurrence $o$、候选 A 原子 $a$ 和配体模板重原子 $l$，在不参与反向传播的标签构造中定义

\[
C_{i,o}[a,l]
=
\mathbb 1\!\left[
\mathrm{present}_{o,l}
\land
\lVert x^A_{i,a}-x^{GT}_{o,l}\rVert\le 4\ \text{Å}
\right].
\]

`x^{GT}` 必须读取 `parse/{pdb_id}/ligand_coords.npz` 的 `coords_{cid}`，并以同文件的 `present_{cid}` 屏蔽沉积结构中缺失的模板原子；不得使用 `LigandObject.ref_pos` 代替真实坐标。A 坐标由候选保存的受体全局原子索引从 `receptor_tokens.npz` 的 `coords` 取得。真实配体坐标只用于生成监督标签，绝不进入 Matcher 输入或可学习特征。

`FinePairAuxiliaryHead` 不预测或保存完整原子×原子接触矩阵，只监督两个立即归约的边缘标签：

\[
y^{\mathrm{recall}}_{i,o,l}=\max_a C_{i,o}[a,l],
\qquad
y^{\mathrm{precision}}_{i,o,a}=\max_l C_{i,o}[a,l].
\]

`RecallAtomHead` 从 `fine_recall_atoms` 为每个配体原子输出一个 logit，`PrecisionAtomHead` 从 `fine_precision_atoms` 为每个 A 原子输出一个 logit；两个头均为独立的单层线性投影。监督覆盖所有有效候选—occurrence 配对，不只覆盖 O=1 的配对。`present=False` 的配体模板原子只从辅助损失中屏蔽，不从 Matcher 的配体输入中删除。空 A 候选的有效配体原子 recall 标签为零，precision 没有有效元素且该分项损失为零。

接触标签只在 `FinePairAuxiliaryHead` 启用时按当前配对执行单元即时生成，不新增离线缓存文件。实现把上述坐标、mask、半径到双向边缘标签的计算收敛为一个独立、无模型依赖的纯几何函数，例如 `build_contact_marginals()`；函数直接归约接触关系，不把完整接触矩阵返回给调用方。Stage2 的标签构造和未来 Stage3 的受体约束可以复用这一函数，但 Stage3 如何使用该标签仍由 Stage3 设计单独决定。函数保持普通张量输入和两个张量输出，不建立标签类层级、任务注册器或缓存管理器。4 Å 使用与现有 Stage D `binding_threshold` 一致的默认值，并作为普通显式参数传入，不散落硬编码。

现有 Stage D `binding_atom + instance_id` 可用于测试时交叉核验，但不直接充当本标签：它只保存每个受体原子最近的一个 occurrence，会丢失同一受体原子同时接近多个 occurrence 的逐配对事实。具体损失形式、归一化和权重另题决定。
Reason: 同一个接触关系沿两个原子轴归约，恰好对应细分支的 recall 与 precision 查询方向，能够直接约束 readout 前的逐原子表示。所需真实配体坐标、present mask、受体坐标和 A 全局索引都已存在，因此不扩展 Dataset 的外部资源依赖。独立纯函数既让 Stage2 实现保持短小，也保留 Stage3 复用同一几何事实的自然边界。

Question 80: `FinePairAuxiliaryHead` 是否使用同一个 masked sigmoid focal 函数监督两个原子方向，并沿既有 occurrence 层级归约？
Decision: 是。`RecallAtomHead` 与 `PrecisionAtomHead` 输出的二值 logit 共用一个职责单一的 `masked_sigmoid_focal_mean()`，固定 `gamma=2.0`、`alpha=None`。不额外叠加 Dice、普通 BCE、动态正类权重、逐 batch 类别比例校准或难例挖掘。

归约顺序固定如下：

1. 对每个候选—occurrence 配对，recall 在 `present=True` 的配体模板原子上取 focal 平均；
2. 对每个候选—occurrence 配对，precision 在该候选的全部有效 A 原子上取 focal 平均；
3. 对同一 occurrence 的有效候选取平均，避免每轮 synthetic-anchor 随机候选数改变该 occurrence 的辅助权重；
4. 同一 occurrence 的 recall 与 precision 损失直接等权相加；
5. 同一 PDB 的 occurrence 损失求和，使其影响继续随真实 occurrence 数近似线性增长；
6. 一个 optimizer step 内各 PDB 求和后，与其他损失一起按 Question 66 除以 `occurrence_budget_per_batch`，当前默认分母为 64。

空 A 候选的 recall 仍是有效的全零目标监督；precision 没有有效 A 原子，其配对分项严格定义为零并跳过空张量 reduction。若某个 occurrence 没有任何非空 A 候选，其 precision occurrence 分项为零。实现使用显式 mask 和短小 reduction helper，不通过伪原子、padding 正例或特殊损失类绕过空集合。

Question 88 已将外部权重固定为阶段二默认 `fine_pair_aux_weight=0.1`，并规定权重 0 即关闭模块。正式训练日志不持续记录 recall/precision 两个内部标量，只把加权后的结果并入 Question 66 的 `loss_aux`；两个方向的计算正确性由单元测试覆盖。
Reason: 原子维取平均使配体大小和候选 A 原子数不直接控制损失尺度，候选维取平均延续主任务的 occurrence 独立损失单元语义。大量错误配对会自然产生全零标签，focal 足以抑制容易负原子；再叠加 Dice 或动态权重会增加全零集合处理和调参复杂度，而不符合辅助监督应当轻量、易读的定位。

Question 81: `EntityAuxiliaryHead` 第一版监督哪些节点和边属性？
Decision: 第一版使用同一个短小的 `EntityAuxiliaryHead` 类分别实例化配体侧和 A 侧，两个实例参数不共享。每个实例只包含节点元素分类头和统一边类别头；A 侧实例额外包含结合原子二分类头：

```python
element_head: Linear(node_dim, 128)
edge_class_head: Linear(edge_dim, 6)
binding_head: Linear(node_dim, 1) | None
```

节点 `element_head` 在配体与 A 上都预测原子序数类别。配体标签来自 `LigandObject.atoms.element`，A 标签来自 `receptor_tokens.npz` 的 `element`。A 的 `binding_head` 预测 Stage D `atom_labels.npz` 中的真实 `binding_atom`；配体侧不注册该头，因为 occurrence 特异的配体—受体接触已由 `FinePairAuxiliaryHead` 监督。

边监督把最初提出的 `is_chemical` 二分类与“仅在化学边上预测五类 `bond_order`”合并为一个六分类问题，删除单独的 `edge_is_chemical_head`：

| 边类别 | 监督语义 |
| --- | --- |
| 0 | 没有化学键，即纯 radius 边 |
| 1 | single |
| 2 | double |
| 3 | triple |
| 4 | dative |
| 5 | aromatic |

一条边同时属于 chemical 与 radius 时，按其化学键类别 1–5 监督，不归入类别 0。受体的 backbone、disulfide 和 covalent-connection 边继续遵循 Question 74：在 `bond_order` 中映射为 single，同时在模型输入的 `bond_role` 字段保留真实角色；第一版辅助头不额外重预测 `bond_role` 或 `is_radius`。有向图中一条无向关系的两个方向分别接受相同类别监督。

第一版不复制 Emap2lig 的稠密原子对 distogram 或全原子对 bond-existence 预测，也不增加手性、环大小、残基类型、原子名等重复重建头。将来若实验发现某项语义容易丢失，可以在该显式类中增加对应线性层，但不得为此预先建立通用任务注册器。Question 88 已取消额外布尔总开关：`entity_aux_weight>0` 时构造并运行 `EntityAuxiliaryHead`，等于 0 时不构造且不读取专用标签。
Reason: 元素分类约束节点状态保留基本化学身份，六类边分类同时约束动态边状态区分非键几何邻接与具体化学键，A 的 binding 头则提供不属于当前输入的受体功能监督。六分类替代两个相互依赖的边预测后，不再需要先判断 `is_chemical` 再构造 bond mask，输出、损失和测试路径都更短，同时不改变 Question 74 已确定的图输入信息。

Question 82: `EntityAuxiliaryHead` 的三个出口是否使用固定的简单损失，并沿既有 occurrence 权重层级归约？
Decision: 是。节点元素分类使用普通 cross-entropy，并在每个实体的有效节点上取平均。六类边分类使用 `gamma=2`、`alpha=None` 的多分类 focal，并在每个实体的有效有向边上取平均；实现直接从逐元素 cross-entropy 得到 $p_t=\exp(-CE)$，再计算 $(1-p_t)^2CE$，不引入类别统计、负边采样或六个手写类别权重。A 的 `binding_atom` 使用与 Question 80 相同的 masked sigmoid focal，固定 `gamma=2`、`alpha=None`，并在该候选的有效 A 原子上取平均。

配体实体内部按

\[
\mathcal L_{\mathrm{ligand\ entity}}
=
\frac{\mathcal L_{\mathrm{element}}+\mathcal L_{\mathrm{edge}}}{2}
\]

等权平均；A 实体内部按

\[
\mathcal L_{\mathrm{A\ entity}}
=
\frac{\mathcal L_{\mathrm{element}}+\mathcal L_{\mathrm{edge}}+\mathcal L_{\mathrm{binding}}}{3}
\]

等权平均。若实体没有有效边，对应 edge 分项严格为零，不执行空张量 reduction；空 A 候选的全部 A 实体辅助损失为零。

PDB 层级继续保持 occurrence 独立权重：配体实体损失按 occurrence 求和；A 实体损失先对当前 PDB 随机生成的候选取平均，再乘该 PDB 的真实 occurrence 数，

\[
\mathcal L_{\mathrm{ligand}}^{PDB}
=
\sum_o \mathcal L_{\mathrm{ligand\ entity}}^{(o)},
\qquad
\mathcal L_A^{PDB}
=
N_{\mathrm{occurrence}}
\operatorname{mean}_i
\mathcal L_{\mathrm{A\ entity}}^{(i)}.
\]

两侧相加形成 `loss_entity_aux`；一个 optimizer step 内各 PDB 求和后，与其他损失一起除以 Question 66 的固定 `occurrence_budget_per_batch`，当前默认 64。Question 88 已将外部权重固定为阶段一与阶段二默认 `entity_aux_weight=0.1`，并规定权重 0 即关闭模块。正式日志只把加权结果并入 `loss_aux`，不持续记录三个内部任务。
Reason: 节点、边和 binding 先各自在自身变长实体轴上归一化，避免原子数、边数或任务数量直接决定权重。候选 A 先平均再乘真实 occurrence 数，可以消除 synthetic-anchor 候选数量的随机倍率，同时维持复杂 PDB 的总体影响约为 $O(N_{\mathrm{occurrence}})$。边类别中的纯 radius 类预计占多数，三行式多分类 focal 比普通 CE 更不易被容易背景边支配，又明显短于类别采样或动态权重方案。

Question 83: 正式训练前是否用完整阶段二的真实训练步反向选择 U-Net 通道宽度，并如何指定显存余量？
Decision: 基本按建议执行，但显存上限必须由用户在每次 profile 命令中人工显式指定，不能把 `max_memory_reserved_gib <= 72` 或任何其他数值写成代码、配置模板或验收逻辑的固定默认值。`72 GiB` 只可作为面向 A800 80 GB 的命令示例。`ops/profile_matcher_memory.py` 提供直接的 `--memory-limit-gib <GiB>`；传入时在 JSON 和控制台摘要中报告峰值是否小于等于该上限，省略时只报告实测 allocated/reserved 峰值而不判定通过或失败。

U-Net 宽度只在完整细分支、正式配对执行策略和全部默认启用损失已经实现后确定。profile 必须运行完整阶段二、正式混合精度、forward、loss、backward 和 AdamW step。固定首轮 `occurrence_budget_per_batch=64` 与 `map_candidate_chunk_size=64`，以 `[16,32,48,64]` 为起始通道配置，由用户显式给出更宽的 `channels` 重复运行；脚本不自动搜索、不自动改参、不替用户写回配置。

至少检查两类真实负载：一类是 occurrence 总数接近 64 且候选数、A 原子数较高的正常装箱 batch；另一类是实验清单中最重的 65–100 occurrence 单 PDB，若清单实际不存在则跳过。最终选择同时满足用户本次 `--memory-limit-gib` 的最宽通过配置，并把通道列表、显存上限、两个实际 batch 规模和 profile 结果写入正式实验配置与运行记录。

profile 入口必须可以不阅读源码直接使用：`--help` 解释每个参数的单位和作用，项目说明提供可复制的普通测量命令与带显存上限的验收命令；控制台只输出与 `memory_profile.json` 对齐的简短摘要。用户只需填写配置路径、通道列表、真实 batch/PDB 选择和可选 GiB 上限，不需构造张量 shape 或理解内部模块名。

如果重负载的主要显存来自细配对网格而不是 Map U-Net，不为“通过”而盲目缩小 Map 通道；先使用 Question 87 已确定的 `fine_pair_chunk_size=2048` 与细分支 activation checkpoint 重新 profile，必要时再显式调小该 chunk。`map_candidate_chunk_size=64` 只约束单次 U-Net 调用，未启用 Map 路径 checkpoint 时多个候选 micro-batch 的已保存激活仍可能累积，profile 结果必须按实际总候选数解释。
Reason: 两个 64 是首轮吞吐与执行粒度锚点，却不是总显存的严格上界；完整阶段二和超软预算单 PDB 才能暴露真实峰值。显存余量取决于用户当次硬件占用、可接受风险和实验目的，应由人明确选择。简单 CLI、真实训练入口和结构化结果可以让这一选择可重复，而无需在模型内部加入自动调参与隐式行为。

Question 84: 细分支与两个新增辅助头是否只挂在当前训练阶段最后一个完整实体 Block 的出口？
Decision: 是。阶段一的 Block 1–4 运行配体/A 图更新、粗分支和实体回吸，`EntityAuxiliaryHead` 只读取 Block 4 的最终配体与 A 实体状态；Block 5–8 继续 coarse-only，不运行细分支或 `FinePairAuxiliaryHead`。阶段二冻结 Block 1–4，Block 5–8 运行新增的配体/A 图更新、粗分支和实体回吸；Block 5–7 只保留 Question 24 已确定的 coarse O/O′ 深监督，`EntityAuxiliaryHead` 只读取 Block 8 的最终实体状态，双向只读细分支、`FinePairAuxiliaryHead` 和粗细联合的最终 O/O′ 头也只在 Block 8 出口运行一次。

`EntityAuxiliaryHead` 的配体侧实例与 A 侧实例各只有一套参数，不为四个 Block 复制四套辅助头。阶段一训练得到的这两套辅助头权重随模型权重进入阶段二，并在 Block 8 的新实体状态上继续训练；阶段二不再为冻结的 Block 1–4 计算实体辅助损失。`FinePairAuxiliaryHead` 只存在于阶段二最终出口。

实现不把数字 8 写进模型逻辑。逐 Block 配置保留原计划中一个直接的 `run_fine` 布尔开关，当前阶段二排程只有最后一个 Block 为 `true`；当前阶段的实体辅助监督由训练配置明确指向“最后一个运行实体 trunk 的 Block”。不实现多层细分支的专属权重调度、共享细分支循环或中间细配对日志。

本决定修订 Question 23 与 Question 77 中可能被理解为“阶段二后四个 Block 各运行一次正式细分支”的表述：后四个 Block 都补齐实体主干与回吸，正式细分支仅在它们的最终出口运行。
Reason: 双向细分支是 read-only，不把候选—occurrence 特异状态写回共享实体，也不为下一 Block 形成可继续迭代的细状态。在 Block 5–7 重复执行只会增加三份候选×occurrence×原子的深监督，计算和显存接近成倍增长；Block 8 的最终 O/O′ 与两个辅助损失仍可沿计算图训练 Block 5–8 的全部新增实体主干。最终实体状态上的一套辅助头也足以约束节点和边表示，同时保持代码与日志简洁。

Question 85: 阶段二最终 O/O′ 头是否通过零初始化的细表示残差继续复用阶段一 Block 8 的同一套预测参数？
Decision: 是。每个 `CoarsePredictionHead` 都拥有参数独立的 `PairCodeMLP`、`OHead` 和 `OPrimeHead`；Block 8 的这套参数就是阶段一最终出口。阶段二必须加载并继续使用阶段一 Block 8 的同一个 `PairCodeMLP`、`OHead` 与 `OPrimeHead`，不得因为加入细分支而另起一套全新的 O/O′ MLP。阶段二只冻结 Block 1–4；后四个 Block 的粗分支参数，包括 Block 5–8 的预测头，继续参与训练。

阶段二 Block 8 的联合表示按以下顺序生成：

```python
coarse_pair_repr = pair_code_mlp(coarse_codes)
fine_delta = fine_adapter(fine_pair_repr)
joint_pair_repr = coarse_pair_repr + fine_delta

O_logit = O_head(joint_pair_repr)
O_prime_logit = O_prime_head(joint_pair_repr)
O_prime = torch.sigmoid(O_prime_logit)
```

`fine_adapter` 只包含 `LayerNorm(pair_repr_dim)` 与 `Linear(pair_repr_dim,pair_repr_dim)`；线性层权重和偏置全部零初始化。阶段二起点因此满足 `joint_pair_repr == coarse_pair_repr`，Block 8 的 O/O′ 输出与阶段一接力值一致。第一步主损失可以更新 `fine_adapter`，而 `FinePairAuxiliaryHead` 从第一步直接训练细分支；adapter 打开后，最终 O/O′ 主损失也反向进入细分支。Block 5–7 的 coarse-only 预测头不增加 adapter。

本项目从此统一任务量命名：凡标识符中的 O、O′、A、B 明确指 Matcher 的特定预测量或损失量，都保留大写前缀。代码使用 ASCII 可读形式，例如 `O_logit`、`O_target`、`O_prime_logit`、`O_prime`、`A_logit`、`B_logit`、`loss_O`、`loss_O_prime`、`lambda_O`；类名使用 `OHead`、`OPrimeHead`。不得写成 `o_logit`、`o_prime`、`a_logit` 或 `b_logit`。普通英文单词、循环变量或不表示上述任务量的字母不受此规则影响。后续实现文档、配置、Docstring、测试和日志字段共同遵守；修订旧文档时也应在涉及当前正式接口的部分同步改正。
Reason: 零初始化 residual adapter 在不改变既有头输入维度的情况下接入细粒度信息，完整保留阶段一已经训练好的最终决策边界，并避免新建一套联合头及其 checkpoint 迁移逻辑。Block 8 粗头继续训练可以适应阶段二新实体 trunk 和细残差逐渐引入后的表示分布。任务符号保留大写则能把数学对象与普通变量一眼区分，减少长模型流程中的阅读歧义。

Question 86: 细分支是否复用统一 `TypedAttention`、保持 128 维原子状态，并把两个塌缩后的细表示各扩展为 512 维？
Decision: 是。配体与 A 的 `GraphState.node` 默认 128 维，细分支的双向逐原子 cross-attention 直接在该维度运行，不先把候选×occurrence×原子网格升到 256 或 512 维。recall 与 precision 各实例化一套参数独立的 `TypedAttention`；当前 ligand↔A 每次只有一种受侧实体，不传 type tensor、不执行 split softmax。`TypedAttention` 内部使用 PyTorch scaled-dot-product attention，由运行环境选择 flash、memory-efficient 或 math 后端，不另维护一套直接依赖 flash-attn 的细分支实现。

两个方向默认执行 pre-norm attention residual：

```text
x = x + Dropout(OutputProjection(
    SDPA(Q(LayerNorm(x)), K(LayerNorm(context)), V(LayerNorm(context)))
))
```

细 attention 后的 FFN 由显式配置 `fine_attention_use_ffn` 控制，第一版正式配置写明 `false`。关闭时不注册 FFN 参数；开启时追加 `x = x + FFN(LayerNorm(x))`，其中 FFN 为 `Linear(128,512) → SiLU → Dropout(0.1) → Linear(512,128)`。相应配置为 `fine_attention_ffn_hidden_dim=512`。实现只保留一个短条件分支，不建立有/无 FFN 两套类。

不向细 attention 提供配体—A 坐标 bias。配体 `ref_pos` 与候选 A 世界坐标不在同一姿态坐标系，二者直接距离没有物理语义；各自 GatedGCN 内部基于同一实体坐标系构造的 radius/RBF 几何继续保留。

两个参数独立的 `LearnedQueryReadout` 都先在 128 维以单 learned query 池化 pair-specific 原子状态，得到一个 128 维摘要，再在原子轴已经消失后执行 `LayerNorm(128) → Linear(128,512) → SiLU → LayerNorm(512)`。因此 `recall_repr` 与 `precision_repr` 各为 512 维，但不会把每个 A 原子或配体原子投影成 512 维。二者按固定顺序拼接为 1024 维，`FinePairCodeMLP` 使用

```text
LayerNorm(1024)
→ Linear(1024,512)
→ SiLU
→ Dropout(0.1)
→ Linear(512,256)
→ LayerNorm(256)
```

得到 256 维 `fine_pair_repr`，再按 Question 85 经零初始化 adapter 加入 `coarse_pair_repr`。默认配置为 `fine_node_dim=128`、`fine_num_heads=8`、`fine_dropout=0.1`、`fine_attention_use_ffn=false`、`fine_attention_ffn_hidden_dim=512`、`fine_readout_dim=512`、`fine_pair_repr_dim=256`。实际原子维度从 `GraphState.node_dim` 读取，并校验可被 head 数整除，不在前向硬编码 128。

空 A 候选不调用全 masked attention：recall attention 增量为零，因此 `fine_recall_atoms` 保留配体 query 状态；precision 没有原子输出，`precision_repr` 使用 512 维零向量。不增加 learned empty token 或专用空集合网络。未来 P、V、PP 复用同一个单实体双向配对原语；不同实体是否需要不同 attention 参数或维度届时显式决定。
Reason: 原子级 128 维控制最昂贵的逐对注意力成本，而在 learned-query 已经消除原子轴后扩到 512 维，可以用较小显存代价提高配对摘要与最终融合容量。默认关闭 FFN 保持首版轻量，显式开关又允许后续直接检验额外逐原子非线性是否有益。统一 `TypedAttention` 保留原计划的算子边界，也避免为细分支复制注意力内核。

Question 87: 正式候选—occurrence 配对网格是否采用“逐块 activation checkpoint、完整矩阵 Hungarian、单次 backward”的分块实现？
Decision: 基本按建议执行，但第一版 `fine_pair_chunk_size` 使用 2048，而不是最初建议的 256。对每个 PDB，Block 8 以前的实体主干、完整粗分支和小型 `coarse_pair_repr[n_candidates,n_occurrences,256]` 只计算一次；随后按 candidate-major、occurrence-minor 的固定顺序展平候选—occurrence 网格，每次把至多 2048 个配对交给同一个纯计算函数 `compute_fine_pair_chunk()`。

该函数读取共享的配体/A 实体状态、当前配对索引和对应 `coarse_pair_repr`，内部完成 Question 78/86 的双向细 attention、两个 readout、`FinePairCodeMLP`、Question 85 的零初始化 adapter、Block 8 的同一套 `OHead/OPrimeHead` 以及启用时的原子接触辅助损失。chunk 外只返回当前配对的一维小型结果：`O_logit`、`O_prime_logit`、已经在各自原子轴归约后的 recall pair loss 与 precision pair loss；不得把完整 `fine_recall_atoms`、`fine_precision_atoms` 或 `fine_pair_repr` 留到 chunk 外。

训练时默认 `fine_pair_activation_checkpoint=true`，使用

```python
torch.utils.checkpoint.checkpoint(
    compute_fine_pair_chunk,
    ...,
    use_reentrant=False,
    preserve_rng_state=True,
)
```

拼接全部 chunk 输出并恢复完整候选×occurrence 矩阵后，才统一执行身份内 Hungarian、O/O′ 正式损失以及 Question 80 的候选维/occurrence 维辅助归约。一个 optimizer step 最终只执行一次 backward；checkpoint 在反向时重算各细 chunk，并由 autograd 自动把梯度累加到共享实体状态和参数。不得实现 detach-leaf、手工 `.grad` 汇总、多次局部 backward、`retain_graph=True`、自定义梯度代理或分块专用 optimizer。

配置固定提供：

```yaml
fine_pair_chunk_size: 2048
fine_pair_activation_checkpoint: true
```

`fine_pair_chunk_size=null` 表示当前 PDB 整张细配对网格一次计算；正整数表示单次配对数，不自动根据显存改变。2048 是面向 A800 80 GB 的首轮正式值，仍可由 Question 69/83 的显存 profile 命令显式覆盖。推理不运行 activation checkpoint，但继续允许按同一 chunk 大小分块。运行时不捕获 OOM 后自动重试或静默缩小 chunk。

测试在关闭 dropout 的同一玩具输入上比较整图、普通分块和 checkpoint 分块的 `O_logit`、`O_prime`、FinePair 辅助损失、总损失及所有可训练参数梯度；使用适合浮点重排的明确容差。训练开启 dropout 时由 checkpoint 保留每个 chunk 的 RNG 状态，保证同一 chunk 的 forward 与 backward 重算一致，但不要求不同 chunk 划分产生逐元素相同的 dropout mask。
Reason: 细分支使配对网格成为正式显存负担，必须在当前版本实现分块；activation checkpoint 能以重算换保存激活，并在普通单次 backward 中保持共享实体梯度正确，避免旧计划中最难审查的手工梯度接力。2048 更符合当前 A800 80 GB 和仅末块运行细分支的硬件条件，最终仍由完整训练步 profile 决定是否调整。

Question 88: `EntityAuxiliaryHead` 与 `FinePairAuxiliaryHead` 是否默认各使用 0.1 权重，并以权重 0 作为唯一关闭方式？
Decision: 是。第一版不同时维护 `enabled` 与 `weight` 两套可能矛盾的配置。阶段一使用

```yaml
entity_aux_weight: 0.1
fine_pair_aux_weight: 0.0
```

阶段二使用

```yaml
entity_aux_weight: 0.1
fine_pair_aux_weight: 0.1
```

对应权重大于 0 时才构造预测头、读取或生成专用标签并计算损失；权重等于 0 时不构造对应头，也不触发其标签 I/O 或几何计算。由此可以只启用任意一个、同时启用两个或全部关闭。第一版不增加 loss ramp、自动梯度平衡、任务不确定性权重、逐 batch 重标定或根据损失数值自动调权；0.1 是可由实验配置显式修改的初始基准。

为让四个正式日志标量具有直接相加关系，损失归属固定为：

```text
loss_O:
    最终出口与 coarse 深监督出口的全部加权 O 损失

loss_O_prime:
    最终出口与 coarse 深监督出口的全部加权 O′ 损失

loss_aux:
    entity_aux_weight * loss_entity_aux
    + fine_pair_aux_weight * loss_fine_pair_aux

loss_total:
    loss_O + loss_O_prime + loss_aux
```

coarse O/O′ 深监督不再重复计入 `loss_aux`。Question 60 原来的 `aux_total_weight=0.5` 与 `aux_schedule` 分别重命名为 `coarse_deep_total_weight=0.5` 和 `coarse_deep_schedule=linear_depth`，只管理各 Block coarse O/O′ 出口。正式日志仍不展开 Entity/FinePair 内部子项。
Reason: 单个非负权重同时表达开关和强度，减少配置分支并自然支持消融。两个新增辅助损失都已按 occurrence 层级归一化，先用相同 0.1 可以建立清楚基线；后续调参不需要修改代码。把 coarse O/O′ 深监督归回对应主任务日志后，四个标量不重叠且可以直接核对总损失。

Question 89: 阶段二 Block 5–8 的实体状态是否由独立新 stem 从原始图重新嵌入，并只把冻结 Block 4 的节点、边状态作为可选的零初始化 `FiLM_plus` 条件？
Decision: 是。阶段二同时保留两条职责不同的实体路径：

1. 阶段一路径继续从原始配体/A 图进入 `phase1_entity_stem`，再运行冻结的 Block 1–4 实体 GatedGCN、初始实体读出、粗分支与实体回吸，以重建阶段一的持久 `CCD_repr/BOX_repr/A_repr/Map_repr` 并把它们继续交给 Block 5–8 的粗分支。阶段二不为粗表示重新建立第二套 seed。
2. 阶段二新增的实体路径从同一份原始配体 149 维节点、A 的 `F_A` 维节点、两侧 31 维原始边和同一份固定 `edge_index` 开始，经参数独立的 `phase2_entity_stem` 分别投影成 128 维节点状态与 64 维边状态，再依次进入 Block 5–8 新增的配体/A GatedGCN。Block 5 不直接读取 Block 4 的节点、边状态作为主输入；Block 6–8 正常接续前一个后段 Block 的阶段二节点、边状态。

`phase1_entity_stem` 与 `phase2_entity_stem` 不共享配体节点投影、A 节点投影或两侧边投影，但复用同一个 Dataset 字段契约、`AFeatureAssembler`、`build_molecular_graph()` 和图的节点/边顺序。不得为阶段二重建一份可能改变 radius 邻接或边排序的图；阶段二只在相同原始图张量上做新的特征投影。这样 Block 4 条件状态与阶段二主状态可以逐节点、逐边准确对齐。

保留一个普通配置 `phase2_condition_from_block4: false`。默认关闭时，不构造条件调制模块，阶段二实体路径就是纯粹的原始重嵌。启用时，冻结 Block 4 的节点、边状态显式 `detach` 后，仅作为条件分别调制阶段二新 stem 的主状态：

```python
phase2_node = node_FiLM_plus(
    main=phase2_stem_node,
    cond=block4_node.detach(),
)
phase2_edge = edge_FiLM_plus(
    main=phase2_stem_edge,
    cond=block4_edge.detach(),
)
```

节点与边都使用 Pocket_Plus 已有 `FiLMPlusCombine` 的同一计算式，而不是普通相加或单层 residual adapter：

\[
[\gamma,\beta]=
\operatorname{Linear}_2(
\operatorname{Dropout}(
\operatorname{SiLU}(
\operatorname{Linear}_1(\mathrm{cond})
))),
\qquad
\mathrm{out}=\mathrm{main}\odot(1+\gamma)+\beta .
\]

生成器末层 `Linear_2` 的权重与偏置全部零初始化，第一层使用普通初始化；因此启用条件的阶段二起点仍严格满足 `phase2_node==phase2_stem_node`、`phase2_edge==phase2_stem_edge`。第一版使用 `phase2_condition_mlp_ratio=2.0`、`phase2_condition_dropout=0.0` 和 `SiLU`：节点的 128 维条件经 256 维隐藏层生成 256 维 `gamma/beta`，边的 64 维条件经 128 维隐藏层生成 128 维 `gamma/beta`。这些维度从 `node_dim`、`edge_dim` 与倍率派生，不在前向硬编码。配体节点/边与 A 节点/边不共享调制参数；实现只定义一个短小的 `FiLMPlusCombine` 和一个各含 node/edge 两个子模块的 `GraphStateFiLMPlus`，再为配体与 A 各实例化一次，不建立调制插件系统。AdaLigand 迁移并测试 Pocket_Plus 的这一小型算子，不通过运行时修改 `sys.path` 依赖兄弟代码库。

阶段二的冻结与训练边界固定如下：

- `phase1_entity_stem`、阶段一初始 CCD/A 读出、slot/count embedding、Block 1–4 的实体 GatedGCN、实体回吸、粗分支和对应预测头加载阶段一权重并冻结；冻结实体路径可以在 `no_grad` 下运行。
- Block 1–4 的粗分支虽然参数冻结，但其输入含仍可训练的 `Map_repr`，因此不得把包含 Map 路径的整个 Block 1–4 前向包进全局 `no_grad`；梯度仍需穿过冻结算子回到 `MapBackbone/MapSummaryHead`。`MapBackbone` 与 `MapSummaryHead` 在阶段二继续训练，且只有一套，不按阶段复制。
- `phase2_entity_stem`、可选的四组节点/边 `FiLM_plus` 参数、Block 5–8 新增的配体/A GatedGCN 和实体回吸均为阶段二新参数并训练。后段实体状态送入粗分支回吸前仍按 Question 23 `detach`；它们由 Block 8 的 `EntityAuxiliaryHead`、细分支、`FinePairAuxiliaryHead` 以及粗细联合最终 O/O′ 路径训练。
- Block 5–8 已在阶段一训练的粗分支、`CoarsePredictionHead` 和 Block 8 的 `PairCodeMLP/OHead/OPrimeHead` 加载后继续训练。阶段一 `EntityAuxiliaryHead` 加载后在 Block 8 新实体状态上继续训练；细分支、`FinePairAuxiliaryHead` 与 `fine_adapter` 是阶段二新增参数。

阶段二建立新 run，只加载阶段一模型权重，不加载阶段一 optimizer、scheduler、step 或随机状态；随后按 Question 92 重新建立单参数组 AdamW，并按 Question 93 重新建立同构的 warmup-plateau scheduler。checkpoint 加载必须对共同参数严格匹配，只允许阶段二新 stem、Block 5–8 新实体组件、可选 `FiLM_plus`、正式细分支、`FinePairAuxiliaryHead` 和 `fine_adapter` 这些明确前缀缺失；任何共同参数缺失、shape 不一致或未列明的 unexpected key 都立即报错。单元测试至少验证：关闭条件时阶段二 stem 完全不读取 Block 4 状态；启用条件时零初始化输出与纯新 stem 逐元素相等；节点和边都能在训练后产生非恒等调制；冻结参数无梯度，而 Map、阶段二实体组件、后四个粗分支和相应预测头按上述边界获得梯度。
Reason: Block 1–4 是为阶段一粗分支塑形的实体编码链，最终节点、边状态可能已经丢掉阶段二细监督需要的信息，因此不能让 Block 5 把它们当作唯一输入。独立原始重嵌保证阶段二得到真正的新容量；可选 `FiLM_plus` 又能在不破坏该主路径的前提下利用 Block 4 已学到的信息。末层零初始化使“开启条件”在阶段二起点仍是严格 no-op，节点与边使用同一个小算子则同时保留两类状态信息而只增加很少代码和计算。

Question 90: 当前只依赖 O/O′ 的正式推理解码是否采用“每个 occurrence slot 独立选择、允许拒绝、允许同一候选被多个 slot 复用”的规则，并为未来 A/B 解码保留简单清楚的替换边界？
Decision: 是。最终 Block 8 输出原始 `O_logit[n_candidates,n_slots]` 与 `O_prime[n_candidates,n_slots]` 后，当前 `OOPrimeDecoder` 只执行：

```python
O_probability = torch.sigmoid(O_logit)
decode_score = O_probability * O_prime

for slot_index in range(num_slots):
    valid = O_probability[:, slot_index] >= decode_O_threshold
    if not valid.any():
        mark_slot_unmatched(slot_index)
    else:
        candidate_index = argmax_within_valid(
            decode_score[:, slot_index]
        )
        emit_selected_pair(slot_index, candidate_index)
```

`decode_O_threshold` 是普通显式配置；未携带验证校准结果的 smoke/debug 运行使用回退值 `0.5`。正式 checkpoint 按 Question 91 在完整验证集上扫描全局阈值，以最佳 F1 对应值覆盖该回退值并随 checkpoint 产物保存；正式推理和独立测评读取这一冻结值。任何情况下都不按单个 PDB、候选数量或当前分数分布动态调整。相同 `decode_score` 的极少数严格并列按输入候选顺序选择最前者，保证重复推理确定。当前 `AnchorPocketDataset` 及其独立推理入口按 Question 100 保证 `n_candidates>=1`，因此 `OOPrimeDecoder` 不实现零候选特判；未来 Stage1 推理产物路线自行定义缺失候选时的处理语义，不把该逻辑塞回当前 decoder。

每个 slot 至多选择一个候选，但候选侧没有唯一容量限制：同一个候选可以被同一 CCD 身份的多个 slot 或不同 CCD 身份的 slot 重复选择。重复选择原样保留，既不去重，也不执行 NMS 或全局一对一 Hungarian；这保留一个候选承载多个 occurrence 的 merge 可能性。一个 slot 对多个 split 候选都高分时，当前 O/O′ decoder 只保留 `decode_score` 最高者，不尝试合并候选。真正基于 A/B 不对称信号的 merge/split 判断、候选合并与 Stage3 编排留给未来 `ABDecoder`，当前结果不得宣称完成了 merge/split 分类。

训练期和带真实标签的测评期仍按 Questions 10/25 使用身份内 Hungarian，把可交换预测 slot 对齐到真实 occurrence；无标签推理没有真实 occurrence 索引，因此不运行该 Hungarian。已知 count 仍决定输入 slot 数量，但不强迫输出恰好相同数量的已匹配结果：合成训练中的 `miss` 会产生合法的全低 O 列，这类 slot 应返回 `unmatched`，而不是被迫选择 context 假阳框。输出同时记录候选复用次数作为诊断指标，但不据此改变结果。

推理代码按以下三层保持边界：

1. Matcher 模型前向只返回原始预测张量，不执行阈值、候选选择、去重或 Stage3 编排。
2. 独立的 `matcher/decoding.py` 定义当前短小的 `OOPrimeDecoder`。它只接收原始预测、slot/候选索引和 decoder 配置，不读取 Dataset 文件、不访问真实 occurrence 坐标，也不调用模型。
3. 推理入口只负责构造 decoder、调用它并序列化结果。decoder 输出统一为一个稀疏关系结果：`selected_pairs` 保存显式的 `(slot_index,candidate_index,O_probability,O_prime,decode_score)` 记录，`unmatched_slot_indices` 保存未匹配 slot。merge 可自然表现为多个 slot 记录复用同一 candidate；未来 split 可由同一 slot 的多条 pair 关系表达，因此无需把当前返回值固定成不可扩展的“一 slot 对一个整数”数组。

第一版不建立 decoder 插件注册器、运行时类型发现或通用图解码框架。配置只保留一个清楚的 `decoder.name: O_O_prime`，构造处使用直接、穷尽并对未知名称报错的分支；未来实现 A/B 时新增独立 `ABDecoder` 和一个显式分支，复用 `selected_pairs/unmatched_slot_indices` 结果契约。届时可以给原始模型输出增加实际需要的 A/B 张量，但当前不预先加入空 A/B 字段、假实现或无用参数。训练、验证和正式推理必须调用同一个 `OOPrimeDecoder`，不得各自复制乘积、阈值与 argmax 公式。
Reason: O 概率负责判断候选是否处于 12 Å 正关联范围，O′ 在通过 O 阈值的候选中提供连续距离排序；乘积是无需额外可学习参数的直接联合分数。允许 `unmatched` 才能让 30% synthetic miss 的训练语义在推理中真正生效，允许候选复用则不提前封死原计划的 merge 路线。把原始预测、当前 O/O′ 规则和推理编排分开，可以保持当前实现短小可读，并在未来加入 A/B 时只增加新的 decoder，而不侵入模型主干或重写现有推理入口。

Question 91: 阶段一与阶段二是否使用“在完整验证集上扫描 O 概率阈值后得到的最佳 occurrence 级 F1”共同选择 checkpoint 与正式推理阈值，并让验证、独立测评和推理复用同一个 O/O′ decoder？
Decision: 是。上一版建议的 `val/decoder_accuracy` 作废：不能把“某个 occurrence 没有正候选且 decoder 返回 unmatched”当作正确安置。当前 O/O′ 路线先在最终 Block 8 出口使用与正式监督相同的身份内 Hungarian，把同一 CCD 身份的可交换预测 slot 对齐到真实 occurrence；随后对每个全局阈值 $t$ 调用 Question 90 的同一个 `OOPrimeDecoder`，不得在验证代码中重写过滤、乘积和 argmax。

对阈值 $t$，在完整验证集上累计三个整数：

\[
TP_t=
\#\{\text{非空 slot，且所选候选对其已对齐 occurrence 满足 }O=1\},
\]

\[
P_t=\#\{\text{decoder 预测的非空 slot}\},
\qquad
G=\#\{\text{全部真实 occurrence}\}.
\]

由此定义

\[
\operatorname{precision}_t=\frac{TP_t}{P_t},
\qquad
\operatorname{recall}_t=\frac{TP_t}{G},
\qquad
F1_t=\frac{2\operatorname{precision}_t\operatorname{recall}_t}
{\operatorname{precision}_t+\operatorname{recall}_t}.
\]

若 $P_t=0$，正式日志中的 precision 与 F1 都定义为 0；Question 100 过滤后的有效验证样本清单中 $G$ 必须大于 0。一个选错候选的非空 slot 增加 $P_t$ 却不增加 $TP_t$，因此既形成 precision 意义下的错误预测，也意味着其 occurrence 未被正确安置。`unmatched` 不进入 $P_t$，但对应 occurrence 仍留在 $G$ 中并降低 recall。对于已经保留的非零候选 PDB，即使某个 occurrence 在当前候选集合中根本没有任何 $O=1$ 候选，也不得从 $G$ 排除或因正确拒绝而记为 TP；只有整份 PDB 零候选时才在评估入口之前跳过。该指标有意测量“至少存在一个候选时，本轮候选生成加 Matcher 解码”的完整安置结果，而不测量 Stage1 完全未产生候选的失败。

同一候选被多个 slot 复用时，每个 slot 按各自对齐 occurrence 独立判断：如果该候选对多个 occurrence 都满足 $O=1$，可以贡献多个 TP，保留 Question 90 的 merge 语义。当前 decoder 每个 slot 至多输出一个候选，所以 $P_t$ 就是非空 slot 数；未来 A/B 的多候选 split 结果不套用本题公式，而由独立 `ABEvaluation` 重新定义。

第一版使用固定全局阈值网格 `0.00,0.01,...,1.00`，逐阈值累计全验证集整数计数。多 GPU 验证先对每个阈值的 `TP_t/P_t/G` 做全局求和，再计算 precision、recall 与 F1；不得先算 batch、PDB 或 GPU 内 F1 后再平均。选择

\[
t^*=\arg\max_t F1_t.
\]

若多个阈值得到完全相同的最高 F1，固定选择较高阈值。checkpoint 主监控指标为 `val/F1_O_O_prime=max_t F1_t`，方向为 `max`；同时保存该 checkpoint 对应的 `val/precision_O_O_prime`、`val/recall_O_O_prime` 与 `val/decode_O_threshold=t^*`。每个 checkpoint 必须把自己的 $t^*$ 连同 `decoder.name=O_O_prime` 写入可随权重共同加载的解码配置或元数据。选定 checkpoint 后，正式推理与后续独立数据集测评直接使用该冻结阈值，绝不在测试数据上重新扫描。`0.5` 只作为缺少校准元数据的 smoke/debug 回退值。

第一版以最佳 F1 而不是 PR-AUC 作为 checkpoint 主指标。原因是 Question 90 的精确 decoder 会先按 O 概率阈值过滤候选，再在有效集合中按 `O_probability*O_prime` 选择；阈值改变时同一 slot 的所选候选也可能改变，因此直接套用假定“每个 slot 具有固定预测与固定置信度排序”的标准 PR-AUC 会偷偷改变当前推理解码定义。阈值扫描 F1 对这种候选切换仍有清楚含义，并且直接产出可部署的阈值。若未来需要 PR-AUC，必须在不改变 decoder 语义的前提下单独定义，不在首版 checkpoint 逻辑中混入近似曲线。

代码边界固定如下：

- `OOPrimeDecoder` 完全不读取真实标签，供验证、独立测评与正式推理共同使用。
- 当前路线的 `OOPrimeEvaluation` 只负责按阈值调用 `OOPrimeDecoder`、依据对齐后的 O 标签判断所选 pair 是否正确、累计 `TP/P/G` 并在全局汇总后计算指标。训练期验证和离线测评共同调用它；checkpoint 回调只读取它产生的 `val/F1_O_O_prime`，不复制任何公式。
- Question 9 的 O/O′ 一致性模块仍作为独立诊断存在，但不参与 checkpoint 选择或阈值扫描。
- 未来 A/B 路线新增参数和语义独立的 `ABDecoder` 与 `ABEvaluation`。它们可以复用最基础的 `selected_pairs/unmatched_slot_indices` 数据结构，但不得复用 O/O′ 的阈值循环、正确性判断或 F1 公式。decoder/evaluator 构造处只增加一个直接的显式分支，不建立插件注册系统。

Reason: 用户定义的 precision 衡量“模型声称已匹配的 slot 中有多少真的正确”，recall 衡量“全部真实 occurrence 中有多少最终被正确安置”；两者共同惩罚误配、漏配和候选生成阶段的漏检。以同一个 decoder 扫描阈值并按最佳 F1 选择 checkpoint，可以使验证时的模型选择、保存的部署阈值、正式推理和离线测评严格同构，同时把只适用于当前 O/O′ 输出的逻辑隔离在独立模块内，避免未来 A/B 路线被当前定义绑死。

Question 92: 阶段一和阶段二是否都使用一套新建的单学习率参数组 AdamW，而不在第一版区分新增参数与承接参数的学习率或 weight decay？
Decision: 是。阶段一与阶段二各自新建 optimizer；阶段二只加载阶段一模型权重，不加载阶段一 optimizer 状态。两个阶段的首版 AdamW 配置统一为：

```yaml
optimizer:
  name: AdamW
  lr: 5.0e-5
  betas: [0.9, 0.999]
  eps: 1.0e-8
  weight_decay: 0.01
```

每个阶段只把当前 `requires_grad=True` 的模型参数放入同一个参数组。阶段二中，新建的 `phase2_entity_stem`、可选 `FiLM_plus`、Block 5–8 新实体 GatedGCN 与回吸、正式细分支、`FinePairAuxiliaryHead`、`fine_adapter`，以及继续训练的 `MapBackbone/MapSummaryHead`、Block 5–8 粗分支与预测头、`EntityAuxiliaryHead`，全部使用相同的 `5.0e-5`。冻结的阶段一 stem、初始读出、Block 1–4 参数和对应预测头不得进入 optimizer。

第一版不建立“新增参数高学习率、承接参数低学习率”的差分参数组，不做 layer-wise learning-rate decay，也不为 bias、LayerNorm、learned query、slot/count embedding 或其他一维参数建立无 weight-decay 例外组。`weight_decay=0.01` 统一作用于单个参数组。decoder、阈值扫描和 evaluator 没有可训练参数，不进入 optimizer。

optimizer 构造后必须立即验证：参数组非空；组内不存在 `requires_grad=False` 参数；同一 `Parameter` 没有重复注册；optimizer 中参数集合与模型当前全部可训练参数集合严格相等。检查只在构造期执行并在失败时直接报错，不在每个训练 step 重复扫描。后续若实验明确需要差分学习率，再把它作为独立消融加入；当前实现不提前建立通用参数分组规则引擎。
Reason: 阶段二已经通过冻结 Block 1–4、独立原始重嵌、末层零初始化 `FiLM_plus`、零初始化 `fine_adapter` 和直接辅助监督控制接力风险；后四个承接的粗分支又确实需要适应新实体回吸与细残差，因此没有事实依据预先把它们固定到更低学习率。单一参数组沿用项目现有 AdamW 基准，减少一个新旧参数倍率超参数和易出错的名称分组逻辑；若训练证据显示新增与承接参数收敛速度明显冲突，再通过配置化实验引入两组学习率。

Question 93: 阶段一与阶段二是否使用同构的“线性 warmup + 监控验证集 O/O′ 解码 F1 的 plateau 降学习率”调度，并在固定次数的实际降学习率后结束当前阶段？
Decision: 基本按建议执行，但 plateau 的绝对改进阈值从最初建议的 `0.001` 改为 `0.003`。两个阶段各自新建 scheduler，配置为：

```yaml
scheduler:
  name: warmup_plateau
  warmup_ratio: 0.005
  warmup_start_factor: 0.33
  monitor: val/F1_O_O_prime
  mode: max
  factor: 0.3
  patience: 2
  threshold: 0.003
  threshold_mode: abs
  cooldown: 0
  min_lr: 0.0
  eps: 1.0e-8
  stop_after_lr_reductions: 3
```

每阶段的学习率从 `0.33 * 5.0e-5` 线性升到 Question 92 的 `5.0e-5`，warmup optimizer step 数默认为该阶段预计总 optimizer steps 的 0.5%。当 `warmup_ratio>0` 且预计总步数为正时，解析结果至少为 1 step，避免短 smoke 因四舍五入得到 0；测试或特殊运行仍可显式设置 `warmup_steps` 覆盖比例。warmup 期间不推进 plateau bad-validation 计数。

warmup 结束后，scheduler 在每次完整验证结束、Question 91 已完成跨 GPU 的 `val/F1_O_O_prime` 汇总后推进一次。`patience=2` 表示连续第 3 个验证事件仍未比既有最佳值提高至少 0.003 时，把当前学习率乘以 0.3。只统计实际发生并超过 `eps` 的学习率下降；第 3 次实际下降后结束当前阶段。当前阶段最终使用 `val/F1_O_O_prime` 最高的 checkpoint，而不是最后一步权重。第一版不叠加 cosine、OneCycle、周期重启或按训练损失推进的第二套 scheduler。

Matcher 与当前 Stage1 Find 一样，训练框架必须支持同一 epoch 内执行多次完整验证；不得把 scheduler、checkpoint 或阈值扫描写成只在 epoch 末调用。`patience` 始终按验证事件而不是 epoch 计数。Question 94 已把默认频率确定为每 epoch 5 次完整验证；改变该值时必须意识到它会同步改变一次 plateau 等待的实际 optimizer steps，scheduler 不做隐式补偿。

阶段二从阶段一最佳 checkpoint 建立新 run，只加载模型权重和与该权重对应的 O/O′ decoder 元数据；AdamW、scheduler、global step 与 plateau 历史全部重新开始。同一阶段因作业中断而恢复时则完整恢复模型、optimizer、scheduler、global step、最佳监控值、已发生的学习率下降次数和当前 checkpoint 的 decoder 校准信息，不得把中断恢复误当成阶段切换。
Reason: 两阶段都包含从头初始化的新容量，因此各自需要短 warmup；之后直接监控部署同构的 occurrence 级 F1，比根据总损失或预设 epoch 数降学习率更贴近最终任务。0.003 的绝对提升门槛过滤阈值网格和有限验证集造成的细小 F1 波动。明确区分“阶段切换只载模型权重”和“同阶段中断完整恢复”，可以同时保证课程接力干净和服务器作业可可靠续训。

Question 94: Matcher 是否默认在同一个 epoch 内执行 5 次完整验证，并让 scheduler、checkpoint 选择与 O/O′ 阈值扫描都按这 5 个验证事件运行？
Decision: 基本接受建议，但把最初建议的每 epoch 4 次改为 5 次。正式默认配置为：

```yaml
trainer:
  val_per_epoch: 5
```

一个 epoch 内的 5 个验证触发点按该 epoch 预计 optimizer step 的约 20%、40%、60%、80% 和 100% 放置；训练开始的 step 0 不额外验证。触发点必须由统一训练循环根据本 epoch 的预计 optimizer step 数计算，不得依赖“每读完固定数量的 PDB”或假定每个 PDB 都占一个 batch。Question 42 的 occurrence 预算装箱规则继续生效：普通 PDB 尽量装到 `occurrence_budget_per_batch=64`，超过预算的单个 PDB 独占一个 batch；这不会改变验证按 optimizer step 进度触发的原则。

每个验证事件都必须遍历完整且固定的验证清单，而不是轮流验证五个子集；完成所有 GPU 的结果汇总后，统一执行 Question 91 的 O/O′ 阈值网格扫描与 `TP/P/G` 汇总、生成 `val/F1_O_O_prime` 和对应部署阈值、推进 Question 93 的 plateau scheduler，并判断是否保存 checkpoint。checkpoint 文件名或唯一标识必须包含 `global_step`，不能只含 epoch 编号，以免同一 epoch 的多个验证结果彼此覆盖。阶段最佳 checkpoint 仍按所有验证事件中的最高 `val/F1_O_O_prime` 选择。

依据冻结数据清单，训练集约有 180,382 个 occurrence，按预算 64 粗略下界为每 epoch 2,819 个 optimizer batch；验证集约有 2,914 个 occurrence，单次完整验证粗略下界为 46 个 batch，实际数量可因按 PDB 贪心装箱而略高。五次验证处理的 occurrence 总量约等于训练集的 8.1%，且没有反向传播，因此作为首版默认频率可以接受。Question 93 的 `patience=2` 按验证事件计数，所以连续第 3 个验证事件仍没有至少 0.003 的绝对 F1 改善才会降学习率；在验证均匀分布时，最快大约经过 0.6 epoch 的训练进度发生一次下降，而不是等待 3 个完整 epoch。

smoke test、小型子集和显存测量运行可以显式覆盖为 `val_per_epoch: 1` 或关闭周期验证，但正式配置解析器不得因数据集小、epoch 短或触发点接近而偷偷改写用户配置。若预计 optimizer step 数不足以提供 5 个互不重复的中间触发 step，构造训练计划时应直接给出清楚的配置错误，要求调用方显式降低 `val_per_epoch`；不通过静默合并触发点改变 scheduler 的事件数。
Reason: Matcher 的训练 epoch 很长，而完整验证集相对较小；每 epoch 5 次完整验证能更早观察 O/O′ 解码质量并为 plateau scheduler 提供足够及时但不过密的反馈。把验证、阈值校准、checkpoint 与 scheduler 绑定在同一个完整验证事件上，能够维持训练期模型选择、离线评估和正式推理的同构性；同时保留显式覆盖项，方便后续小数据参数实验和 smoke test 使用较低验证频率。

Question 95: 阶段一与阶段二是否分别设置 `max_epochs=20` 的硬训练上限，并仍以 Question 93 的 plateau 降学习率次数作为正常停止机制？
Decision: 是。阶段一与阶段二是两个独立 run，各自最多训练 20 个完整 epoch；不是把 20 个 epoch 在两个阶段之间共同分配。正式配置语义为：

```yaml
phase1:
  max_epochs: 20

phase2:
  max_epochs: 20
```

`max_epochs=20` 只作为防止验证指标持续产生细小改善、使训练无限延长的硬保护上限。正常停训仍由 Question 93 的机制主导：warmup 结束后，按 Question 94 每 epoch 5 次完整验证推进 plateau；累计发生第 3 次实际学习率下降时结束当前阶段。第一版不额外设置 `min_epochs`，也不要求达到某个 epoch 后才允许 plateau 停训。阶段一结束并选出最佳 checkpoint 后，阶段二才按既定 model-only 接力规则建立新的 run，重新计算自己的 epoch、optimizer、scheduler 与停止状态。

单阶段在硬上限内最多产生 100 个周期性完整验证事件。达到第 20 个 epoch 时，即使尚未发生 3 次学习率下降，也在该 epoch 末结束；阶段最终产物始终是其全部验证事件中 `val/F1_O_O_prime` 最高的 checkpoint，而不是第 20 个 epoch 的最后权重。若 plateau 提前结束，亦使用此前保存的最佳 checkpoint。断点续训恢复原 run 的当前 epoch 与 global step，不把 `max_epochs=20` 重新计数。
Reason: 现有 Stage1 正式规划同样使用 20 epochs 作为硬上限，Matcher 没有证据需要在第一版另设更长的无界训练窗口。两个阶段都有各自新初始化的容量，因此各自拥有完整上限比合计分配更清楚；同时以验证 F1 驱动的学习率下降次数作为主要停止条件，可以让实际训练长度由任务收敛情况决定，而硬上限只承担安全兜底作用。

Question 96: 阶段一与阶段二的正式训练是否统一使用 BF16 混合精度与全局梯度范数裁剪，同时让会影响离散匹配和验证阈值的计算保持 FP32？
Decision: 是。两个阶段统一采用：

```yaml
trainer:
  precision: bf16-mixed
  gradient_clip_algorithm: norm
  gradient_clip_val: 0.5
```

模型主参数与 AdamW optimizer 状态保持 FP32；`MapBackbone`、GatedGCN、粗分支与细分支 attention、readout 和预测头的常规模型前向在 BF16 autocast 下执行。BF16 路线不启用为 FP16 下溢准备的动态 loss scaling，也不把 optimizer 状态转为 BF16。A800 正式训练不提供静默退回 FP16 的路径：若运行设备或软件栈不支持 BF16，启动时给出明确错误；仅 CPU smoke test 可以通过显式配置覆盖为 FP32。

下列计算在进入相应模块前显式转为 FP32，并以 FP32 完成，不依赖 autocast 的隐式算子选择：O focal loss、O′ 回归与截断约束、所有辅助损失的逐元素值和 occurrence 级归约、各 Block 的 Hungarian 成本矩阵与匹配求解输入、Question 90 decoder 的 sigmoid/乘积分数和候选比较、Question 91 全阈值扫描中的概率比较与 F1 计算。`TP/P/G` 本身以整数累计并跨 GPU 求和；最终 precision、recall、F1 使用 FP32 或更高精度标量计算。这样 BF16 只节省主要网络激活与矩阵运算成本，不允许其舍入改变监督配对、阈值边界或 checkpoint 排序。

每次 optimizer step 的梯度裁剪发生在当前完整反向传播完成之后、`optimizer.step()` 之前；对该阶段全部可训练参数共同计算一个全局 L2 梯度范数，并裁到 0.5，不按模块、参数组或 PDB 分别裁剪。训练日志只在既有简洁日志结构中记录必要的总梯度范数或异常信息，不为每个模块展开梯度统计。若未来加入梯度累积，裁剪只能在完成一次 optimizer step 所对应的全部累积反向后执行一次。

Question 50 的正式显存测量入口必须使用与目标训练相同的 BF16 autocast、真实 loss、反向传播、裁剪和 AdamW step，以便峰值与 OOM 结果具有代表性；CPU 单元测试不承担显存估计职责。
Reason: A800 原生适合 BF16，主要网络采用混合精度可以显著降低激活显存并提高吞吐，而 FP32 主参数与 optimizer 状态保留稳定更新。Hungarian、截断阈值和 O/O′ 解码包含对数值边界敏感的比较，将这些短小运算固定为 FP32，代码与成本都很小，却能避免精度模式改变监督或验证结论。全局范数裁剪 0.5 沿用现有 Stage1 的正式配置，并为注意力、图消息传播和多项辅助监督共同反向时提供统一保护。

Question 97: 第一版正式 Matcher 是否以单张 A800 80 GB 为唯一训练验收路径，而暂不把多 GPU DDP 训练、分布式变长装箱和跨卡等步数调度列入首版完成条件？
Decision: 是。阶段一、阶段二、正式显存 profile 和首轮训练/验证统一以单张 A800 80 GB 运行，标准配置为：

```yaml
trainer:
  accelerator: gpu
  devices: 1
```

Question 65 的 `occurrence_budget_per_batch=64`、Question 62 的 `map_candidate_chunk_size=64`、Question 86 的 `fine_pair_chunk_size=2048` 以及 Question 68 的 U-Net 通道宽度，都先在这张卡上共同 profile 并冻结正式实验配置。第一版不实现 DDP 训练 sampler，不把完整 PDB 跨卡拆分，也不通过重复、丢弃或填充 PDB 强行使不同 rank 具有相同 optimizer step 数。普通 DDP 无法分摊一个不可拆分超大 PDB 的单样本显存，因此不得把多卡数量当作跳过单卡峰值验收的方法。

模型、Dataset、collate、loss 和 decoder 代码仍保持普通设备无关写法：不在模块内部硬编码 `.cuda()`、具体 GPU 编号或 A800 名称；新张量跟随现有输入或参数的 device/dtype 创建。checkpoint 保存普通模型 `state_dict` 与既定训练/decoder 元数据，不固化单卡 wrapper 的参数名前缀；加载入口应能去除框架可能添加的已知外层前缀，但不建立宽松的任意 key 猜测器。

Question 91 中 `TP/P/G` 的验证汇总保留一个很薄的可选归约边界：单进程默认直接返回本地整数计数；只有调用方已初始化分布式环境时才执行整数 all-reduce。保留该边界不意味着首版承诺 DDP 训练，也不得为它提前实现分布式 ragged batch、全局 PDB 装箱或 rank 间候选通信。多 GPU 离线推理若近期需要，可以把互不重叠的 PDB 清单交给多个独立进程，最后合并结构化结果，而不依赖 DDP。

未来正式加入 DDP 时，必须作为独立增强重新决定：完整 PDB batch 如何在全局先装箱再分派、如何保证各 rank 等步数而不重复样本、`occurrence_budget_per_batch` 是每卡还是全局预算、DDP 平均梯度下固定损失分母和学习率如何缩放，以及验证与 scheduler 事件如何同步。首版不以隐式或未经测试的框架默认值回答这些问题。
Reason: 当前所有显存与 batch 决策均以单张 A800 80 GB 为事实基础，而完整 PDB 不可拆分、PDB 间 occurrence 数差异显著。把 DDP 作为首版要求会引入分布式变长装箱、等步数和损失尺度等新的建模/训练契约，并不能解决超大单 PDB 的峰值显存。单卡路径足以完成本轮正式训练目标，也最符合简洁易读的核心指标；保留设备无关实现和薄归约边界，可避免未来扩展时被不必要的单卡假设卡住。

Question 98: 训练集逐 epoch 重采 synthetic anchor 时，是否使用一个由普通整数 seed、epoch 和正式清单索引直接决定的简单随机规则，使采样不依赖 DataLoader worker 调度并能在同阶段断点恢复时重建？
Decision: 是。正式基础配置只暴露一个实验级整数：

```yaml
seed: 3407
```

设正式训练清单长度为 $N_{\mathrm{train}}$、当前 epoch 从 0 开始编号为 $e$、PDB 在该固定清单中的索引为 $i$。每个 epoch 的 PDB 顺序使用 `seed + epoch` 初始化一个普通随机生成器后打乱，再按 Question 65 顺序贪心装箱。该 epoch 中这个 PDB 的 synthetic anchor 随机生成器使用：

\[
\mathrm{sample\_seed}
=
3407+(e+1)(N_{\mathrm{train}}+1)+i.
\]

公式只使用整数加法和乘法，不使用 PDB ID、路径或内容哈希，不建立 seed 数据库，也不落盘每个 epoch 的候选清单。`AnchorPocketDataset` 的采样入口必须显式获得 `(epoch, manifest_index)`，而不是从 worker 内的全局可变计数器推断 epoch。一个 PDB 内只创建一个普通随机生成器，并按前向可读的固定次序完成：逐 occurrence 的 miss/split/hit 三分类、bias 候选选择、context 数量抽取、context 候选选择及 Question 29 的空 A 跳过/补取、最终候选顺序打乱；若候选非空，再抽取 Question 101 的一个训练期 Map 立方体旋转并用于该 PDB 的全部候选 Map。不得为各个小步骤再派生一层哈希 seed 或建立随机流注册框架。

Question 38 的验证规则保持不变：验证 synthetic anchor 在实验清单生成阶段以固定 seed 一次性抽取，先按 Question 100 丢弃零候选 PDB，再落盘固定的非空候选关系；正式训练过程中所有验证事件只读取同一份关系，不在 epoch 或验证事件之间重新采样，也不执行 Question 101 的训练期 Map 旋转。`pdb_sample_fraction` 产生的小训练清单使用该小清单自身固定的 $N_{\mathrm{train}}$ 和索引；清单内容及顺序必须写入实验产物，从而使公式含义可复现。

同一阶段断点恢复时，checkpoint 保存当前 `epoch`、`batch_index_in_epoch`、global step，以及 Python、NumPy、PyTorch CPU 与当前 CUDA 设备的随机状态。恢复入口用 `seed + epoch` 重建本 epoch 完整 PDB 顺序和 occurrence 装箱，跳过已经成功完成 optimizer step 的 batch；尚未处理的 PDB再由 `(epoch, manifest_index)` 重建完全相同的 synthetic anchor。checkpoint 只能在完整 optimizer step 和相关状态更新结束后的安全边界标记已完成 batch，不能把半次反向传播视为可恢复进度。

该规则使改变 `num_workers`、worker 分配或样本完成先后不改变训练候选。第一版不强制 `torch.use_deterministic_algorithms(True)`，也不承诺不同 CUDA、cuDNN、PyTorch 版本或不同硬件上的逐 bit 相同结果；目标是固定清单上的数据随机性可解释，以及同一环境内作业中断后能可靠续训。模型初始化与 dropout 等全局随机源仍由同一个实验 seed 初始化，并由 checkpoint 随机状态承接。
Reason: 训练候选需要逐 epoch 变化以覆盖 miss、split、hit 与不同 context 组合，但候选变化不应被 worker 调度或断点位置污染。使用清单索引和 epoch 的直接整数公式既能独立复现每个 PDB，又满足用户“不使用哈希或复杂检验”的要求；恢复时只需重建装箱并跳过已完成 batch，无需保存庞大的逐 epoch 候选文件。

Question 99: 当前不依赖 Stage1 推理输出的 Matcher，是否直接沿用新版 Stage1 Find 的 PDB 划分与完整 BOX 池，同时继续使用 Matcher 已经确定的 bias/context 合成规则？
Decision: 是。当前权威来源是新版、已筛除异常 PDB 的 Stage1 preparation 根目录；Matcher 从其 `box_pool/manifest.json` 读取 `splits.train` 与 `splits.validation` 的 PDB 成员关系，并读取各条目指向的 `train/{pdb_id}.npz` 或 `validation/{pdb_id}.npz` 完整 BOX 池。每个 PDB 的池包含 `occurrence_id`、`center_start_zyx`、`bias_start_zyx` 与 `context_start_zyx`。Matcher 不重新划分 PDB，也不扫描目录猜测成员关系。

Matcher 不复用 Stage1 Find 的请求层：不实例化 `Stage1TrainingRequestSet`，也不读取 `box_pool/validation_selection.npz` 作为 Matcher 验证输入。该文件冻结的是 Stage1 Find 的 `center:bias:context=1:5:3` 请求，其中包含 Matcher 已明确忽略的 center，不能代表 Matcher 的输入分布。Matcher 只复用完整 per-PDB BOX 池：center 完全忽略；bias/context 继续由 Questions 29–34 的规则组合，即每个真实 occurrence 以 `0.30/0.20/0.50` 的互斥概率产生 `0/2/1` 个 bias 候选，context 目标数量从 `0..floor(2.0*N_occ)` 离散均匀抽取，并按 Question 32 跳过 80% 的零 A context 后继续补取。训练逐 epoch 重采，验证由 Matcher 自己以固定 seed 生成并冻结一次。

bias 与 context 均按池内条目无放回选择；不按候选中心距离预筛，不执行跨来源空间去重，也不把来源类别传给模型。若两个不同池下标对应相同 `start_zyx`，仍把它们视为两个被抽中的原始候选条目；这延续现有 BOX 池“重复起点原样保留”的数据契约，并避免增加哈希、坐标去重或复杂资格检查。候选最终按 Question 33 随机打乱。

在上述 PDB/BOX 来源之上，一次性生成 Matcher 自己的版本化实验清单：应用 Question 36 的 `max_slots_per_pdb=100` 与已经确认的缺失 BOX 排除项，记录来源 manifest、保留项和排除原因。长期 `AnchorPocketDataset` 只读取该实验清单和它引用的完整 BOX 池，不在每次加载时重复实现过滤逻辑。Question 36 已冻结的训练 12,881 PDB / 180,382 occurrence 与验证 188 PDB / 2,914 occurrence 是执行 synthetic anchor 前的基础数据宇宙；Question 100 会使每个训练 epoch 的有效 PDB 数略有变化，并使冻结后的有效验证清单略小，不能把基础计数误写成每次实际送入模型的计数。Question 37 的 `pdb_sample_fraction` 仍只是对这份 Matcher 基础 PDB 清单生成小实验子集，不等于 Stage1 的 `box_sample_fraction`，也不改变 bias/context 组合规则。
Reason: 新版 Stage1 preparation 已经提供当前正式 PDB 划分和完整候选池，Matcher 没有必要重新生成 BOX；但 Stage1 Find 的请求表服务于逐 BOX 分类训练，比例和 center 语义与 Matcher 的 occurrence 级漏检、误 split、合格检测及 PDB 级假阳模拟不同。复用数据宇宙而不复用请求层，既沿用当前正式划分，也完整保留已经确认的 Matcher 输入分布。

Question 100: `synthetic_anchor` 最终产生零候选时，是否只在样本收集边界跳过整个 PDB，并让后续 batch、模型、损失、decoder 与 evaluator 都不支持零候选状态？
Decision: 是。完成 `miss/split/hit`、bias/context 选择、空 A context 跳过与补取后，若最终候选列表为空，就从该次训练 epoch 的有效样本中跳过整个 PDB；验证清单生成时采用同一规则，并把过滤后的非空候选关系冻结下来。不得重试随机抽样、强制补一个 bias/context、制造假候选或保留只含配体侧辅助损失的样本。后续 batch、模型、损失、`OOPrimeDecoder` 与 `OOPrimeEvaluation` 的入口契约统一为 `n_candidates>=1`，不再携带空 K/V、空候选损失或全 `unmatched` 的特殊分支。训练 epoch 的有效样本数可随重采结果略变；验证的 $G$ 只统计冻结后保留 PDB 的 occurrence。因此，当前指标明确衡量“至少存在一个候选时的 synthetic-anchor 加 Matcher”，不把 Stage1 完全没有产生候选的失败纳入当前路线。

Question 103: 是否按一次性给出的完整方案冻结粗分支最后一组微观结构，包括 attention 外层残差与 FFN、slot/count embedding、图边距离 RBF，以及候选中心 self-attn 的几何 RBF/BiasMLP？
Decision: 是。以下四部分共同构成第一版正式定义。

1. `TypedAttention` 只负责 Q/K/V 投影、scaled-dot-product attention、输出投影和调用方明确启用的 attention-logit bias；它不在内部隐藏残差、LayerNorm 或 FFN。每个 `coarse_layer` 先从同一个旧状态快照并行计算四组跨类增量，再从全部跨类更新完成后的状态计算同类 self-attn，最后对每组状态执行一次 FFN：

```text
x_cross = x + Dropout(
    CrossAttention(LayerNorm(x), LayerNorm(context))
)

x_self = x_cross + Dropout(
    SelfAttention(LayerNorm(x_cross))
)

x_out = x_self + Dropout(
    Linear(512 → 256)(
        SiLU(Linear(256 → 512)(LayerNorm(x_self)))
    )
)
```

所有增量 dropout 默认 0.1。CCD、BOX、A、Map 在同一层中的 LayerNorm、attention 和 FFN 参数彼此独立，不同 `coarse_layer` 也不共享参数，但代码只复用同一组职责清楚的模块类。不得在 cross-attn 与 self-attn 后分别放置两套 FFN。Question 21 的 Block 末尾 BOX 单向融合仍位于实体回吸之后，采用

```text
BOX_repr = BOX_repr + Dropout(
    TypedAttention(
        LayerNorm(BOX_repr),
        [LayerNorm(A_repr), LayerNorm(Map_repr)],
        split_type_kv=False,
    )
)
```

且不在该融合后再增加 FFN。Question 56 已决定的实体回吸自身 LayerNorm/FFN 保持不变。

2. slot 与 count 使用两张简单的 learned embedding 表：

```text
slot_embedding:  Embedding(100, 256)
count_embedding: Embedding(101, 256)

CCD_repr_0 = LayerNorm(
    CCD_identity_repr
    + slot_embedding[slot_index]
    + count_embedding[identity_count]
)
```

`slot_index` 是同一 CCD 身份内部的 `0..identity_count-1`，`identity_count` 是该身份的真实 occurrence 数；所有 CCD 身份共享这两张表。两种 embedding 只在初始身份展开时注入一次，不在每个 Block 重复添加。阶段二细分支需要槽位化配体原子时，使用一个无偏置的 256→128 线性投影把同一份 slot embedding 广播加到共享配体原子状态；不建立第二张 slot 表，也不把 count embedding 重复注入原子状态。

3. 配体图与 A 图共享的 16 维距离 RBF 使用

\[
\phi_k(d)=
\exp\left[
-\frac12\left(\frac{d-\mu_k}{\sigma}\right)^2
\right].
\]

16 个固定中心在 0 到图的 radius cutoff 4 Å 之间等距排列，\(\sigma=4/15\) Å；`distance_valid=false` 时 16 维全部为零。中心和宽度不学习，并从配置中的 cutoff 与 RBF 维数派生，forward 内不得重复写死数值。

4. 只对 Question 55 已指定的 BOX、A、Map 三类候选侧同类 self-attn 加入候选中心几何 bias。先由世界坐标中心距离 \(d_{ij}\) 计算

\[
u_{ij}=\frac{d_{ij}}{d_{ij}+12\ \mathrm{Å}},
\]

再用 32 个固定 Gaussian RBF 编码 \(u_{ij}\)：中心均匀覆盖 \([0,1]\)，\(\sigma=1/31\)。每个 BOX、A、Map self-attn 实例分别持有参数独立的

```text
BiasMLP: Linear(32, 64) → SiLU → Linear(64, 8 heads)
```

最后一层权重与偏置零初始化，输出逐 head 加到 attention logits。12 Å 是单独可调的数值分辨率尺度；它不参与监督、不对距离反向传播，\(u=0.5\) 不具有概率或标签含义。该编码不设置最大距离截断，不加入距离 mask、方向向量或绝对坐标。CCD self-attn、CCD—候选 cross-attn和 Block 末尾同候选 BOX 融合继续不使用该 bias。上述维数、dropout 与距离尺度在 Hydra 配置中各有一个权威默认值，不散落为 forward 字面量。
Reason: pre-norm 与持久残差保持深层粗表示稳定；每次粗迭代只放一套 FFN，既保留非线性容量又控制参数和代码量。单次 slot/count 注入让同身份可交换槽位在第一次候选交互前分化，而不反复扰动持久状态。图边 RBF覆盖实际 4 Å 局部建图范围；候选距离的有界变换则在没有人为远距离截断的情况下把更多分辨率分配给近邻重复框与误 split。零初始化 BiasMLP 保证几何 bias 在训练起点不改变普通 self-attn，随后再由监督学习其影响。
